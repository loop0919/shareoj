## 判定方法を選ぶ {#modes}

![判定方法の設定。①判定方法のタブ、②判定方法、③判定コードの言語、④判定コードの形式](/images/docs/checker.png)

作問画面のサイドバーで「生成・検証・判定」を開き、①「判定方法」を選びます。
②で選べる判定方法は次の3つです。

| 判定方法 | 使う場面 |
| --- | --- |
| 通常判定（空白区切りで比較） | 答えが1通りに決まる問題。出力と期待される出力を比べます。 |
| スペシャルジャッジ | 答えが複数ある問題や、小数の誤差を認める問題。検証コードが提出の出力を判定します。 |
| インタラクティブ（対話形式） | 提出と対話しながら進める問題。対話用ジャッジが提出とやり取りして判定します。 |

通常判定の比べ方は、[提出と判定結果](/docs/submissions#comparison)で説明しています。

スペシャルジャッジとインタラクティブでは、③で判定コードの言語を選び、その下にコードを入力します。
言語は、提出に使える言語から選びます。
解答の言語と同じでなくてもかまいません。

④「判定コードの形式」は、「現行形式（標準入力と終了コード）」と「testlib形式（Codeforces互換）」から選びます。
testlib形式を選べるのは、言語がC++23（GCC）とC++23（Clang）のときだけです。

問題ページには、スペシャルジャッジ問題かインタラクティブ問題かを表示します。
判定コードは公開しません。

## 現行形式の検証コード {#checker}

検証コードは、テストケースごとに提出の出力を受け取り、終了コードで結果を返します。

- 標準入力：提出の出力
- 第1引数：テストケースの入力ファイル
- 第2引数：期待される出力のファイル（空でもかまいません）
- 第3引数：提出のソースコードのファイル
- 第4引数：スコアのファイル（採点には使いません）

終了コードが0なら正解、それ以外なら不正解です。
assertの失敗などで異常終了した場合も不正解になります。
標準出力の内容は使いません。

次の例は、提出の出力と期待される出力をそれぞれ小数として読み、絶対誤差または相対誤差が $10^{-6}$ 以下なら正解とします。
値のあとに余分な出力があれば不正解です。

```cpp
#include <algorithm>
#include <cmath>
#include <fstream>
#include <iostream>
#include <string>

int main(int argc, char* argv[]) {
    std::ifstream answer(argv[2]);
    double expected, actual;
    answer >> expected;
    if (!(std::cin >> actual)) return 1;
    std::string extra;
    if (std::cin >> extra) return 1;
    return std::abs(actual - expected) <= 1e-6 * std::max(1.0, std::abs(expected)) ? 0 : 1;
}
```

検証コードは、提出が正常に終了したケースだけで実行します。
提出がTLEやREになったケースは、検証コードを実行せずにその結果になります。

## testlib形式 {#testlib}

C++23のGCC・Clangの両方で`#include "testlib.h"`を使用できます。 作問画面の判定方法でスペシャルジャッジまたは対話形式を選び、「判定コードの形式」を「testlib形式」にしてください。 既存の判定コードは「現行形式」のまま使えます。

次は、提出出力と正解ファイルから整数を1つずつ読み、比較するcheckerです。 `inf`はテスト入力、`ouf`は提出出力、`ans`は正解ファイルを読みます。

```cpp
#include "testlib.h"
int main(int argc, char** argv) {
  registerTestlibCmd(argc, argv);
  int actual = ouf.readInt();
  int expected = ans.readInt();
  if (actual != expected) quitf(_wa, "different answer");
  quitf(_ok, "accepted");
}
```

対話形式では`registerInteraction`で初期化します。 次の例は入力ファイルの整数を提出へ送り、その2倍が返ることを確認します。 `std::endl`で出力をフラッシュし、`ouf`で提出からの返答を読みます。

```cpp
#include "testlib.h"
#include <iostream>
int main(int argc, char** argv) {
  registerInteraction(argc, argv);
  int n = inf.readInt();
  std::cout << n << std::endl;
  int actual = ouf.readInt();
  if (actual != 2 * n) quitf(_wa, "expected twice n");
  quitf(_ok, "accepted");
}
```

`_ok`はAC、`_wa`と`_pe`はWA、`_fail`はJEです。
`_dirt`と`_unexpected_eof`もWAになります。
部分点（`quitp`や`_pc`）には対応していません。
現行形式と違い、testlib形式の判定コードが異常終了した場合はJEになります。

`tout`は一時ファイルで、内容を別のcheckerで判定する処理は行いません。interactor自身で正誤を決めてください。
Polygonパッケージの取り込みには対応していません。

## インタラクティブ問題 {#interactive}

インタラクティブ問題では、提出と対話用ジャッジを同時に実行し、互いの標準入出力をつなぎます。
提出の標準出力が対話用ジャッジの標準入力に、対話用ジャッジの標準出力が提出の標準入力に届きます。

テストケースの入力は、提出へ自動では送りません。
対話用ジャッジが入力ファイルを読み、必要な情報を提出へ出力してください。
現行形式の対話用ジャッジは、検証コードと同じ4つの引数を受け取ります。
提出も対話用ジャッジも、相手の応答を待つ前に出力をフラッシュする必要があります。

結果は次のように決まります。

- 提出がTLE、MLE、OLE、REになった場合は、その結果になります。
- 現行形式では、対話用ジャッジが0以外の終了コードで終了すると不正解です。testlib形式では、終了コードを[testlib形式](#testlib)と同じ規則で扱います。
- 対話用ジャッジが正常に終了し、提出も終了すると正解です。
- 対話全体の経過時間が上限を超えるとTLEです。上限は、実行時間制限に5秒を足した長さの3倍に1秒を足した長さで、応答を待つ時間も含みます。

提出結果の実行時間とメモリ使用量は、提出のプログラムだけの値です。
Rubyで解くときの注意は、[使える言語と実行環境の仕様](/docs/languages#libraries)に書いています。

## 判定コードの上限と診断 {#limits}

判定コードの上限は、各ケースでCPU時間5秒です。
メモリは、検証コードが512 MiB、対話用ジャッジが256 MiBまでです。
上限を超えた場合や、判定コードのコンパイルに失敗した場合はJEになります。
判定コードが原因でJEになると、提出全体がJEになり、ケースごとの結果は残りません。

判定コードが標準エラー出力に書いた内容は、提出結果の「ジャッジコードの診断（作問者のみ）」に表示します。
これを見られるのは、問題の作者とテスターだけです。
インタラクティブ問題では、ケースごとの対話の記録も表示します。

ただし、インタラクティブ問題のサンプル検証では、対話の記録と対話用ジャッジの標準エラー出力を、提出した人にも表示します。
サンプルケースで、解答の手がかりになる情報を標準エラー出力に書かないでください。

判定コードが空のときや、判定コードの言語がジャッジで使えないときは、問題を公開できません。
公開の条件は[問題の作成と公開](/docs/authoring#readiness)にまとめています。
作問CLIでは、`problem.toml` の `[checker]` または `[interactor]` で設定します（[作問CLI](/docs/cli#problem-toml)）。

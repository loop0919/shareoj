# コード実行 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 問題に結び付けずに、言語・ソースコード・標準入力を渡して出力を見る「コード実行」を、ヘッダーとコンテストのメニューから使えるようにする。

**Architecture:** コード実行は提出とは別の表 `code_runs` に保存し、提出と同じ送り出し（S3のジョブとSQSの指し示し）で採点台へ送る。採点台は `codeRun: true` のジョブを1回だけ実行して、標準出力・標準エラーの先頭を返す。送り出しは「新しい提出 → 5分待った作問の処理 → コード実行 → 作問の処理 → リジャッジ」の順で、新しい提出以外は送信中が2件未満のときだけ送る。画面は1つの部品 `CodeRunner` を `/run` とコンテストの `?view=run` で使い、最後の1件を `GET /my/code-runs/latest` で読む。

**Tech Stack:** Go（pgx、`api/internal/submissions`、`api/internal/httpapi`、`api/cmd/judge-bridge`、`api/cmd/judge-worker`）、PostgreSQL、Python（`judge/runner`、unittest）、Nuxt 4（Vue 3）、Playwright

**Spec:** [docs/adr/0031-run-code-without-problem.md](../../adr/0031-run-code-without-problem.md)（送り出しの順番は [ADR 0032](../../adr/0032-count-authoring-runs-separately.md) を一部変更する）

## Global Constraints

- 上限：ソース 131,072 バイト（提出と同じ検査：`problems.HasSource`、UTF-8、NUL不可）。標準入力 1,048,576 バイト（UTF-8、NUL不可）。CPU 5,000 ms、メモリ 512 MiB で固定し、利用者は選べない。
- 標準入力は `\r\n` と単独の `\r` を `\n` に直してから保存する。末尾に改行は足さない。上限の判定は直す前のバイト数で行う。
- 回数：アカウントごとに直近60秒で3回。提出、サンプル検証、作問の処理の枠とは別に数え、入力エラーは数えない。超過は `429 code_run_rate_limited` と `Retry-After`。
- APIの誤り：入力の誤りは `400 invalid_code_run`、最後の1件がなければ `404 code_run_not_found`。メンテナンス中は `503 judge_maintenance`、ジャッジ未設定は `503 judging_unavailable`、プロフィール未登録は既存の `403 profile_required`。
- 経路：`POST /my/code-runs`（202、`CodeRun`）、`GET /my/code-runs/latest`（200、`CodeRun`）。Nuxtの中継は `/api/my/code-runs`（POST）と `/api/my/code-runs/latest`（GET）。JSONの本文の上限は、GoとNuxtの両方で 3 MiB（`3 << 20`）。
- `CodeRun` のJSON：`{ id, status: 'QUEUED'|'RUNNING'|'DONE', result: CodeRunResult|null, createdAt }`。`CodeRunResult`：`{ verdict: 'AC'|'RE'|'TLE'|'MLE'|'OLE'|'CE'|'JE', expired?: true, exitCode?, cpuTimeMs?, wallTimeMs?, memoryBytes?, stdout?: TextPreview, stderr?: TextPreview, compileLog? }`。`TextPreview` は既存の `{ text, truncated }`。
- 判定：期待出力と比べない。正常終了は `AC`、ほかは `sandbox.failure_verdict`（ローカルは `Judge` と同じ分岐）の `OLE`→`MLE`→`TLE`→`RE`。標準出力 16 MiB 超、標準エラー 64 KiB 超は `OLE`（提出と同じ）。
- 返す出力：標準出力と標準エラーは、それぞれ先頭 65,536 バイトまでを `TextPreview` にする。結果のJSONが 245,760 バイト（240 KiB）を超えるときだけ、両方を先頭 16,384 バイトに縮める（結果キューの 256 KiB に収めるため）。
- 期限：送り出されないまま受け付けから10分たったら `{"verdict":"JE","expired":true}` で終える。送り出し後1時間たっても終わらなければ `{"verdict":"JE"}`。受け付けから1日たった行は消す。
- 送り出し：`spareInFlight = 2` は、送り出し済みで `status <> 'DONE'` の提出とコード実行を合わせて数える。5分を超えて待った作問の処理（`created_at <= clock_timestamp() - interval '5 minutes'`）はコード実行より先に送る。増設台の起動判定（`capacity.go`）と滞留時間の監視（`pendingAge`）にはコード実行を数えない。
- 採点台へのジョブ：`{"submissionId": <コード実行のID>, "attemptId": <judge_attempt>, "codeRun": true, "runtime": "<id>-isolate", "runtimeDigest": <image>, "source": ..., "stdin": <base64>, "timeLimitMs": 5000, "memoryLimitMb": 512}`。S3のキーとSQSの指し示しは提出と同じ形（`jobs/{id}/{attempt}.json`）。結果は `{"submissionId", "attemptId", "codeRun": true, "result": CodeRunResult}` で返し、進捗は送らない。ワーカーが読むジョブの上限は 2 MiB から 4 MiB（`4 * 1024 * 1024`）に上げる。
- 画面の文言：見出し「コード実行」、ボタン「実行」、結果の見出し「実行結果」、欄の見出し「標準入力」「標準出力」「標準エラー」「コンパイルのメッセージ」、省略の注記「長いため、先頭の64 KiBだけを表示しています。」、期限切れ「混雑のため実行できませんでした。時間をおいてもう一度実行してください。」。そのほかの誤りの文言は Task 6 にある。
- ブラウザの保存：下書きは `localStorage` の `openoj.code-run-draft` に `{ runtime, source, stdin }` のJSONで1つだけ置き、`/run` とコンテスト内で共有する。言語の初期値は、下書きの `runtime`、提出フォームの `openoj.submission-runtime`、`cpp23-gcc` の順。読み書きはすべて try/catch で包む。
- コマンドはworktreeのルートで `nix develop` の中から実行する。Goは `nix develop -c go -C api test ./...` の形にし（`bash -c` で `cd api && ...` を包むと、このセッションのworktreeの保護に止められる）、実DBのテストは先に `export TEST_DATABASE_URL='postgresql://openoj:openoj-local@127.0.0.1:15432/openoj?sslmode=disable'` を実行しておく（DBは起動済み）。ローカルのDockerテストは `TEST_JUDGE_CPP_IMAGE=python:3.14.7-trixie`。Pythonは `python3 -m unittest discover -s judge/tests -v`。Playwrightは `web` で `npm run build` の後に `npx playwright test <file> --output=<scratchpad>/pw`（`web/test-results` はroot所有）。
- コミットメッセージは `prefix: 対応内容`（日本語）。コードを変えたら `graphify update .` を実行する。

- [ ] **Step 1: マイグレーションを書く**

```sql
-- Code runs execute a source on a typed input without a problem (ADR 0031). They stay out of submissions, so no
-- submission list, standing, notification or rejudge can count them.
CREATE TABLE code_runs (
    id uuid PRIMARY KEY,
    owner_id text NOT NULL REFERENCES user_profiles(owner_id),
    runtime text NOT NULL,
    image text NOT NULL,
    source text NOT NULL,
    stdin text NOT NULL,
    judge_attempt uuid NOT NULL DEFAULT gen_random_uuid(),
    status text NOT NULL DEFAULT 'QUEUED' CHECK (status IN ('QUEUED', 'RUNNING', 'DONE')),
    result jsonb,
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    dispatched_at timestamptz,
    finished_at timestamptz
);
CREATE INDEX code_runs_owner_order ON code_runs(owner_id, created_at DESC);
CREATE INDEX code_runs_dispatch ON code_runs(created_at) WHERE dispatched_at IS NULL AND status <> 'DONE';
CREATE INDEX code_runs_in_flight ON code_runs(dispatched_at) WHERE dispatched_at IS NOT NULL AND status <> 'DONE';
```

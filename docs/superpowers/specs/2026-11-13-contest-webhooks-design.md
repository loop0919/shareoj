# コンテストのWebhookの設計

- 作成日: 2026-11-13
- 状態: 承認待ち
- 関連: [ADR 0023 順位表の凍結](../../adr/0023-freeze-contest-standings.md)、[ADR 0024 チーム戦とオンサイト参加](../../adr/0024-team-and-onsite-participation.md)、[ADR 0025 部分点](../../adr/0025-score-partially-with-test-groups.md)、[ADR 0022 共同作成者](../../adr/0022-share-contests-among-setters.md)

## 目的

コンテストの提出の判定が確定するたびに、主催者が登録したURLへ、その出来事をHTTPで送る。
この仕組みを**コンテストのWebhook**と呼ぶ。

主催者は、届いた出来事を使って自分の道具を作る。
最初に想定する使い道は観戦配信で、ACが出るたびに配信画面を更新する。
その先に、特殊ルールの自動集計やバーチャル参加のような応用を見込む。
ShareOJが用意するのは出来事の中身と届け方までで、何を作るかは主催者に任せる。

## 利用者と決めたこと

- 設定できるのは主催者だけとする。
  順位表を見られる人なら誰でも受け取れる、という形にはしない。
- 送るきっかけは、開催中の提出の判定が確定したときとする。
  ACだけでなく、WAやTLEなどの誤答も送る。
  誤答はペナルティの集計に使える。
- 中身には、提出者、問題、判定、得点と、その人またはチームの順位表の行を載せる。
  順位表の行には、全体の順位、オンサイトかどうか、チームが入る。
- 順位表の凍結後の提出は、`frozen`を真にして送る。
  本当の判定と最新の順位は伏せずに載せ、参加者に見せるかどうかは受け取った側が決める。
- 送る形式は、JSONとDiscordの2つとする。
  Discord形式は、DiscordのWebhook URLを貼るだけでチャンネルに文章が流れる。
- 送り先は1コンテストにつき3つまでとする。
  送り先が多いと、ShareOJが外へ出す通信が増えすぎるためである。
- 設定画面は、コンテスト編集画面に「外部連携」の区分を足して置く。
  利用者はモックで次の構成を見て、この形で進めると答えた：スイッチ、送り先のURL、形式、送る範囲、署名の鍵、テスト送信、最近の送信。

## やらないこと

- 画面側からShareOJへつなぎっぱなしにして受け取る方式（SSEやWebSocket）。
  サーバーを持たない配信画面は、主催者が中継を用意して受け取る。
- 提出の判定以外の出来事（開始、終了、結果の公開、質問）。
  必要になったら`event`の種類を足す。
- 順位表全体を1通に載せること。
  全体が要る受け手は、スタッフ向けの順位表を取りに行く。
- Discord以外のサービス専用の形式（Slackなど）。
- 提出のソースコードを載せること。
- 運営者（サイト全体の管理者）向けのWebhook。

## 守りたいこと

次の3つは、動いていても破れたら失敗とする。

- Webhookの送信が遅い、または失敗することで、判定の確定や順位表の表示が遅れてはならない。
- ShareOJが、内部のネットワークや第三者のサーバーへの攻撃の踏み台になってはならない。
- 送り先のURLと署名の鍵が、主催者以外に漏れてはならない。
  DiscordのWebhook URLは、知っていれば誰でも投稿できる秘密である。

## 送る出来事

以下、この節から「順序と重複」までは設計者の判断である。

### 対象の提出

次のすべてを満たす提出を対象とする。

- コンテストに属する提出である。
- 順位表に数える提出である。
  サンプルだけを試す提出のように、順位表の集計から外している提出は送らない。
- 開始から終了までに作られた。
  終了後の練習の提出は送らない。
- 提出者が順位表の対象である。
  スタッフの提出は送らない。

判定の確定が終了後になっても、提出が終了前なら送る。
判定の種類は絞らず、CEやJEも送る。

提出の判定が確定する場所は、いまのコードに4つある。
採点結果を受けて確定する処理（`FinishAttempt`）のほかに、JEを直接書き込む処理が3つある：送り出せないまま期限が切れた提出、送り出しに失敗した提出、開発用ランタイムの時間切れ。
JEも送るので、4つのすべてで出来事を記録する。

### リジャッジ

リジャッジで判定が確定し直したときも送り、`rejudge`を真にする。
順位が変わりうるので、JSON形式の受け手には必要である。

Discord形式では、リジャッジの出来事を送らない。
問題単位のリジャッジは数百件が一度に確定するので、チャンネルが埋まるためである。

### 送る範囲の絞り込み

送り先ごとに、次の2つを選べる。

| 設定 | 選択肢 | 初期値 |
| --- | --- | --- |
| 判定 | すべての判定、ACだけ | すべての判定 |
| 区分 | 全員、オンサイトだけ | 全員 |

「ACだけ」は、判定がACの出来事だけを送る。
部分点の問題で満点に届かない提出は送らない。
「オンサイトだけ」は、オンサイト区分を設けたコンテストでだけ選べる。
絞り込みで外れた出来事は、送信の記録にも残さない。

Discord形式で「ACだけ」を選んだ送り先には、凍結後の提出の出来事を送らない。
Discord形式は凍結後の提出を判定なしで流すが、ACのときだけ流れると、流れたこと自体が判定を明かすためである。

## JSON形式の中身

```json
{
  "version": 1,
  "id": "evt_01JCD…",
  "event": "submission.judged",
  "sentAt": "2026-11-20T12:04:07Z",
  "contest": {
    "id": "0b6f…（UUID）",
    "title": "第1回テストコン",
    "url": "https://…/contests/…"
  },
  "submission": {
    "id": "5c1e…（UUID）",
    "url": "https://…/contests/…/submissions/…",
    "problem": { "label": "A", "title": "足し算" },
    "verdict": "AC",
    "score": "100",
    "fullScore": "100",
    "submittedAt": "2026-11-20T12:04:05Z",
    "judgedAt": "2026-11-20T12:04:07Z",
    "rejudge": false
  },
  "frozen": false,
  "by": { "handle": "loop" },
  "standing": {
    "rank": 1,
    "previousRank": 3,
    "onsite": true,
    "onsiteRank": 1,
    "team": null,
    "score": "300",
    "timeMs": 1845000,
    "problem": { "score": "100", "wrong": 1, "acceptedAt": "2026-11-20T12:04:05Z" }
  },
  "publicStanding": { "…": "standingと同じ形" }
}
```

- **`id`**：出来事ごとに一意の値。再送でも変わらず、受け手が重複を捨てるのに使う。
- **`contest.id`と`submission.id`**：APIが使うUUID。
- **`contest.url`と`submission.url`**：公開ページのURL。ページのURLはUUIDを短く書き直したIDを使うので、受け手が組み立てずに済むよう載せる。
- **`submission.problem.label`**：コンテスト内の問題の記号（A、B、…）。
- **`submission.score`と`fullScore`**：この提出の得点と、問題の満点。順位表と同じ表記の文字列（整数か小数2桁）。
- **`frozen`**：凍結後の提出で、かつ送る時点で結果確定していないときに真。
- **`by.handle`**：提出した本人。チーム戦でも本人のハンドルを入れる。
- **`standing`**：この判定を反映した、スタッフ向け（凍結しない）順位表でのその行。
- **`standing.rank`**：全体の順位。
- **`standing.previousRank`**：この提出を除いて集計したときの全体の順位。順位の変化の演出に使う。
- **`standing.onsiteRank`**：オンサイト区分の中の順位。オンサイトでない行と、区分のないコンテストでは`null`。
- **`standing.team`**：チームの行なら`{ "name": "たこやき", "members": ["taro", "hana"] }`、個人の行なら`null`。
- **`standing.problem`**：その問題のセル。得点、誤答数、満点に届いた時刻。
- **`publicStanding`**：参加者に見えている順位表でのその行。形は`standing`と同じである。凍結中（凍結の開始から結果確定まで）は凍結した順位表から作り、それ以外は`standing`と同じ値になる。

`publicStanding`を載せるのは、`frozen`が偽の出来事でも`standing`が凍結を破りうるためである。
凍結の直前に出した提出が凍結後に確定した場合や、凍結中のリジャッジでは、`frozen`は偽になる。
その`standing.rank`は、ほかの人の凍結後の提出を数えた順位である。
参加者に見せる受け手は`publicStanding`を使えば、凍結を気にせずに済む。

項目は後から足すことがある。
受け手は知らない項目を無視する、と仕様の文書に書く。
項目を消すか意味を変えるときは`version`を上げる。

### ヘッダーと署名

JSON形式は、次のヘッダーを付けて`POST`する。

| ヘッダー | 値 |
| --- | --- |
| `Content-Type` | `application/json` |
| `User-Agent` | `ShareOJ-Webhook/1` |
| `X-ShareOJ-Event-Id` | 本文の`id`と同じ値 |
| `X-ShareOJ-Timestamp` | 送信時刻（UNIX秒） |
| `X-ShareOJ-Signature` | `sha256=`に続けて、`タイムスタンプ.本文`を署名の鍵でHMAC-SHA256した16進 |

署名の鍵は送り先ごとにサーバーが作る。
主催者は設定画面で表示と作り直しができる。
作り直すと、古い鍵はその時点で使えなくなる。

## Discord形式の中身

Discordが受け付ける形（`content`を持つJSON）にして送る。
メンションは無効にする。
署名は付けない。

```text
✅ loop が A問題 を AC（100点）
順位 3位 → 1位 ／ オンサイト 1位
```

```text
❌ チーム たこやき（taro）が B問題 で WA
順位 5位 ／ B問題の誤答 2回
```

```text
🧊 凍結中　hana が C問題 に提出
```

- 凍結後の提出（`frozen`が真にあたる出来事）は、判定も順位も書かず、提出したことだけを流す。
  Discordのチャンネルは参加者が見ていることが多く、受け手の側で伏せる手段もないためである。
- 順位は、参加者に見えている順位表（JSON形式の`publicStanding`）のものを書く。
- 送信待ちの出来事が同じ送り先にたまったときは、2,000文字に収まる範囲で1通にまとめる。
  Discordは1つのWebhookが短時間に受け付ける数を制限しているので、提出が集中しても取りこぼしにくくする。
- チームの行は、チーム名と提出した本人を書く。
- 順位が変わらなければ矢印を省く。
- オンサイトの行は、オンサイト区分の順位を添える。
- ハンドルとチーム名は、Discordの書式として解釈されないようにエスケープする。

文面の細部は作り手に任せる。

## 送り先の設定

### 誰がいつ設定できるか

オーナーと共同作成者が設定できる。
共同作成者はオーナーとほぼ同じ操作ができる（ADR 0022）ので、そろえる。
テスターと作問者は、設定を見ることもできない。

下書きでも公開済みでも、開始後でも終了後でも変えられる。
凍結の設定と違い、開催中に送り先のURLを直せないと困るためである。

いまのコンテストの編集は、開始すると保存できなくなり、編集画面は「コンテスト管理」の区分だけを出す。
そこで、送り先の設定は、コンテスト本体の保存とは別のAPIで読み書きする（共同作成者の管理と同じ形）。
編集画面は、開始後も「外部連携」の区分を開けるようにする。

送り先のURL、署名の鍵は、コンテストを取得するAPIのうち、オーナーと共同作成者への応答にだけ含める。
ログ、エラーメッセージ、監視の通知には出さない。

### 送り先の項目

| 項目 | 内容 |
| --- | --- |
| 送り先のURL | 必須。下の条件を満たすもの |
| 形式 | JSONかDiscord |
| 判定の絞り込み | すべての判定か、ACだけ |
| 区分の絞り込み | 全員か、オンサイトだけ |
| 有効か | 送るかどうか。止めても設定は残る |
| 署名の鍵 | JSON形式のとき。サーバーが作る |

1コンテストにつき3つまで登録できる。

### 送り先のURLの条件

- `https`で、ポートは443だけとする。
- URLにユーザー名とパスワードを含めない。
- 長さは2,000文字までとする。
- Discord形式では、ホストが`discord.com`で、パスが`/api/webhooks/`で始まるものに限る。
- 保存時と送信時の両方で、ホスト名を引いたアドレスを調べる。
  プライベート、ループバック、リンクローカル、マルチキャストなど、公開のインターネットでないアドレスなら拒む。
- 送信は、調べたアドレスそのものへつなぐ。
  調べた後に名前の引き先が変わっても、内部へ届かないようにするためである。
- リダイレクトには従わない。

### 画面

コンテスト編集画面に「外部連携」の区分を足す。
並びは「参加形式」と「コンテスト管理」のあいだとする。
オーナーと共同作成者にだけ見せる。

- 送り先の一覧と「送り先を追加」のボタンを置く。
  3つあるときは追加できない。
- 送り先ごとに、有効かどうかのスイッチ、URL、形式、送る範囲、署名の鍵（JSON形式のとき）、テスト送信、最近の送信、削除を置く。
- URLと署名の鍵は伏せて表示し、「表示」で見せる。
- 「オンサイトだけ」は、オンサイト区分を設けたコンテストでだけ選べる。

### テスト送信

見本の出来事を1通、その送り先へすぐ送り、結果を画面に出す。
APIはVPCの中にあって自分では送れないので、テスト送信もVPCの外の送信用Lambdaを通す。
画面は結果を数秒待って出す。
JSON形式では`event`を`ping`とし、`contest`だけを載せる。
Discord形式では「ShareOJからのテスト送信です」と流す。
同じ送り先へのテスト送信は、10秒に1回までとする。

### 最近の送信

送り先ごとに、直近20件の送信の結果を残して見せる。
1件は、時刻、出来事の要約（問題、提出者、判定）、結果（届いた、失敗とHTTPの状態か失敗の種類）からなる。
相手の応答の本文は残さない。

## 送信の仕組み

### 判定の確定から送信まで

1. 判定を確定する処理が、同じトランザクションの中で「送るべき出来事」を1行記録する。
   対象の提出で、コンテストに有効な送り先が1つ以上あるときだけ記録する。
   記録するのは提出のIDとリジャッジかどうかで、順位はここで計算しない。
2. VPCの中の処理が記録を読み、順位表を集計して、送り先ごとの本文を作る。
   絞り込みもここで行う。
3. 本文をキューに入れる。
4. VPCの外の送信用Lambdaが、キューから取り出して送る。
5. 送信の結果を、別のキューでVPCの中へ返し、送信の記録に書く。

送信をVPCの外に分けるのは、APIも判定結果を受けるLambdaもVPCの中にあり、外へ出られるのがIPv6だけだからである。
IPv4しか持たない送り先に届かない。
NATゲートウェイは費用がかかるので置かない。
VPCの外から送れば、データベースなど内部の資源へ届く道もなくなる。

手順1を確定と同じトランザクションにするのは、判定は確定したのに出来事が記録されない、という抜けをなくすためである。
順位の集計を手順2へ回すのは、確定の処理を遅くしないためである。

手順2と5をどの処理が担うか（判定結果を受けるLambdaに足すか、別のLambdaを置くか）と、何をきっかけに動かすかは、作り手に任せる。
目安として、判定の確定から送信の開始までを、混んでいないときで5秒以内とする。
判定結果を受けるLambdaには、採点結果のキューと1分ごとの定時起動がある。
期限切れのJEのように定時起動でしか確定しない出来事は、5秒の目安の対象外とする。

リジャッジかどうかは、提出がリジャッジ済みの時刻を持つかで分かるので、手順1で記録しなくてよい。

### 再試行と自動停止

- 1回の送信は、5秒で打ち切る。
- 2xxの応答を成功とする。
- 失敗したら、間隔を空けて2回まで送り直す（合計3回）。
  送り直しは1分以内に終える。
- 429の応答に`Retry-After`（Discordでは`retry_after`）があれば、それに従う。
  待ちが送り直しの期限を超えるなら、その出来事はあきらめる。
- 3回とも失敗した出来事は捨て、最近の送信に失敗として残す。
- 20件続けて失敗した送り先は、自動で止める。
  止めたことを、オーナーと共同作成者にベルで知らせる。
  主催者がスイッチを入れ直せば再開する。
- 429であきらめた出来事は、この20件に数えない。
  相手は生きていて、混んでいるだけだからである。
- 同じ送り先への送信は、1通ずつ順に行う。
  並べて送ると、相手の制限に当たりやすくなる。

ベルの通知は、いまは「誰の操作によるものか」を必ず持つ作りである。
自動停止には操作した人がいないので、操作した人のいない通知を作れるようにする。

送り直しを短く切るのは、配信画面に数分前のACが遅れて届いても使い道がないためである。

### 順序と重複

- 出来事は、確定した順に届くとは限らない。
  受け手は`submission.judgedAt`で並べ直す。
- 同じ出来事が2回届くことがある。
  受け手は`id`で重複を捨てる。
- 送れなかった出来事を、後からまとめて取り直す手段は用意しない。

この3点は仕様の文書に書く。

### 負荷

順位表は提出から都度集計する作りなので、出来事1件につき集計が1回走る。
`previousRank`は、同じ集計の中でその提出を除いて順位を付け直して求め、データベースを2回読まない。

問題単位のリジャッジでは、数百件の出来事が短時間に生じる。
同じコンテストの出来事をまとめて読んだときは、提出の読み出しを1回で済ませる。
参加者300人、提出3,000件のコンテストで、出来事1件あたりの集計時間を実装時に測り、設計書に書き足す。

ShareOJが外へ出す通信は、提出の数と送り先の数（3つまで）の積で抑えられる。
提出の数には、すでに提出の間隔の制限がある。

## 仕様の文書

公開の文書（サイトの「ドキュメント」）に、Webhookのページを足す。
主催者はこれを読んで受け手を作る。

- 設定の手順
- JSON形式の全項目と例
- 署名の確かめ方と、短いサンプルコード
- 順序、重複、再試行、自動停止
- 凍結の注意

凍結の注意は、ページの上のほうに目立つ形で置く。
内容は「`frozen`が真の出来事には本当の判定と順位が入っている。参加者に見える場所へ出すと、順位表の凍結が破れる」とする。
設定画面にも、凍結を行うコンテストでJSON形式の送り先があるときに、同じ注意を1行出す。

## 決定の記録と配布

- この設計の決定を、ADR 0038として`docs/adr`に書く。
- 採点ワーカーは変えないので、ワーカーの配布は要らない。
- 配布の順は、データベースの移行、API、判定結果を受けるLambdaと送信用のLambdaとキュー、Webとする。
  Webが先に出ると、設定を保存するAPIがまだない。

## テスト

- 対象の提出の条件（開催中、順位表の対象、練習は除く）ごとに、出来事が記録されるかどうか。
- 絞り込み（ACだけ、オンサイトだけ）と、Discord形式でリジャッジを送らないこと。
- 凍結中の`publicStanding`が凍結した順位表の行になること。Discord形式の「ACだけ」に凍結後の提出を送らないこと。
- JEを直接書き込む3つの処理でも出来事が記録されること。
- 本文の各項目。個人、チーム、オンサイト、部分点、凍結後の提出のそれぞれ。
- `previousRank`が、その提出を除いた順位になること。
- 署名が、文書のサンプルコードで確かめられること。
- URLの条件。内部のアドレス、リダイレクト、`https`以外、Discord以外のホストを拒むこと。
- 再試行、429の待ち、20件続けて失敗したときの自動停止とベルの通知。
- 送り先のURLと署名の鍵が、テスター、作問者、参加者への応答に含まれないこと。
- 送信が失敗しても詰まっても、判定の確定が遅れないこと。
- 画面。送り先の追加と削除、3つの上限、テスト送信、最近の送信。

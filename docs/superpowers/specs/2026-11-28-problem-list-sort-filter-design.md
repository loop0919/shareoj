# 問題一覧の並び替えと絞り込みの設計

- 作成日: 2026-11-28
- 状態: 実装済み（ブランチ feat/problem-list-conditions、2026-11-28）。まだ公開していない。
- 対象: 問題一覧（`/problems`）のWeb、公開の問題一覧のAPI。ジャッジとCLIは変えない。データベースは、索引を足すことはあっても、表の形は変えない。
- きっかけ: Issue #35（問題一覧のフィルターに「未ACの問題のみ」が欲しい）

## 目的

問題一覧は公開日が新しい順に並ぶだけで、絞り込みは「タグ」と「コンテストの問題かどうか」の2つしかない。
公開された問題が増え、解く問題を探すのに何ページも送ることになった。
Issue #35 は、まだACしていない問題を順に解いていく人（AC埋め）が、解いていない問題だけを見たいという要望である。

問題一覧で、並び順を選び、条件で絞り込めるようにする。
条件は折りたたんだパネルに入れ、ふだんは一覧の場所を取らないようにする。
選んだ条件は覚えておき、次に問題一覧を開いたときも同じ条件で始める。

## 利用者と決めたこと

- 画面イメージ3案を触って比べ、**1つのパネルにまとめて折りたたむ形**を選んだ。
  ほかの2案は、並び順と「未ACのみ」を外に出す形と、列見出しで並び替える形だった。
- 並び順に使うのは、公開日、正解者数、お気に入り数、難易度の4つ。
- 絞り込みに使うのは、解答状況、コンテスト、難易度の範囲、タグの4つ。
- 前回の条件は、次に問題一覧を開いたときも残す。
- 覚え方は「前回の条件を覚える」の節のとおりにする。
- Issue #30（コンテスト中にAC済みの問題を隠す）は別の画面なので、今回は入れない。

## 画面

### 閉じているとき

- 「問題」の見出しの下に、「絞り込み・並び替え」のボタンを置く。今の「コンテストの問題で絞り込む」の選択欄は、パネルの中に移す。
- 効いている条件があれば、ボタンにその数を出す。初期の並び順（公開日が新しい順）は数えない。
- ボタンの横に、効いている条件を1つずつ札で並べる。札の×で、その条件だけを外せる。
  札の例: 「未ACのみ」「コンテストの問題のみ」「難易度 Lv.3〜6」「正解者数が多い順」「タグ: DP」
- 「タグを表示」のスイッチと、その横の注意書きは、今と同じくパネルの外に置く。
- 一覧の行に出るタグを押したときは、今の並び順と絞り込みを保ったまま、そのタグで絞り込む（設計者の判断）。
  今のタグの検索欄がコンテストの条件を保つのと同じ扱いである。
  問題ページなど、一覧の外にあるタグのリンクは、今と同じくタグだけを付けて開く。

### 開いているとき

ボタンを押すと、ボタンの下にパネルが開く。札は出さない（同じ内容がパネルにあるため）。
パネルには次の欄を、この順に並べる。

| 欄 | 形 | 選べるもの |
| --- | --- | --- |
| 並び順 | 選択欄 | 公開日が新しい順（初期）、公開日が古い順、正解者数が多い順、正解者数が少ない順、お気に入りが多い順、難易度が高い順、難易度が低い順 |
| 解答状況 | 3つから1つ選ぶボタン | すべて（初期）、未ACのみ、AC済みのみ |
| コンテスト | 選択欄 | すべての問題（初期）、コンテストの問題のみ、コンテストの問題を除く |
| 難易度 | 下限と上限の選択欄 | Lv.1 〜 Lv.10（初期は Lv.1〜Lv.10） |
| タグ | 今のタグの検索欄 | 「タグを表示」がオンのときと、タグで絞り込み中のときだけ出す（今と同じ条件） |

- パネルの右下に「条件をすべて外す」を置く。押すと、並び順も絞り込みもタグも初期に戻る。
- 条件を変えたら、その場で一覧に反映する。「適用」ボタンは置かない。
- 条件を変えてもパネルは開いたままにする。ページを開き直したときは、閉じた状態から始める。
- 条件を変えたら1ページ目に戻す。
- 条件に合う問題がないときは「条件に合う問題はありません。」と出し、「条件をすべて外す」のボタンを添える。
- スマホ幅では、欄を縦に1列で並べる。

### 未ログインのとき

- 解答状況の欄は見せるが、選べない状態にし、「ログインすると使えます」とログインへのリンクを添える。
- URLに解答状況の条件が付いていても、当てない。札も出さない。

### 難易度の扱い

- 絞り込みと並び替えに使うのは、一覧に出している「作成者設定」の難易度である。投票の難易度は使わない。
- 難易度の範囲を初期（Lv.1〜Lv.10）から狭めたときは、難易度が未設定の問題は外れる。
- 難易度で並べるとき、未設定の問題は、高い順でも低い順でも最後に置く。

### AC済みの判定

解答状況の「AC済み」は、今の一覧で行を緑にしている判定（`GET /my/solved-problems`が返す問題）と同じにする。
絞り込んだ結果と、行の色が食い違わないようにするためである。

## 条件とURL

- 条件はすべてURLのクエリに入れる。今の `?tag=` と `?contest=` はそのまま使う。
- 並び順、解答状況、難易度の範囲のクエリ名と値は、実装者が決める。
  初期値のときはクエリに出さない。
- 知らない値や形の合わない値は、APIが400を返す（今の `invalid_contest` と同じ扱い）。
- ページ番号（`?page=`）と表示件数は、今の仕組み（ADR 0028）のまま使う。合計の件数とページ数は、条件を当てたあとの数にする。
- 検索エンジン向けの正規URL（canonical）には、今と同じくタグとコンテストとページだけを入れる。
  並び順、解答状況、難易度の範囲は入れない。

## 前回の条件を覚える

- 覚えるのは、並び順、解答状況、コンテスト、難易度の範囲。タグとページ番号は覚えない。
- 覚える場所はブラウザーごとのCookieにする。表示件数（`usePageSize`）と同じ考え方で、未ログインでも残り、サーバーが最初から同じ条件で描ける。
  別の端末やブラウザーには引き継がない。
- 覚えるのは、利用者がパネルか札で、覚える4つの条件のどれかを変えたときである。そのときの4つの条件をまとめて覚える。
  条件つきのURLを開いただけでは書き換えない。タグを変えたり外したりしただけでも書き換えない（設計者の判断）。
- タグのリンクから開いた一覧（`?tag=DP`だけ）で並び順などを変えると、その一覧の条件が新しく覚えられ、前に覚えていた条件は置き換わる。
  「最後に自分で選んだ条件を覚える」という決まりのとおりである。
- タグを外した結果、クエリが1つもなくなったら、上の決まりのとおり、覚えた条件が当たる。
- 当てるのは、クエリが1つもない `/problems` を開いたときだけである。
  覚えた条件があれば、その条件を付けたURLへ置き換える（履歴は増やさない）。
  サーバーが描くときも、ブラウザーの中で移動したときも同じにする。
- クエリが1つでもあるURL（共有されたリンク、タグのリンク）は、URLのとおりに開く。覚えた条件は足さない。
  ページ番号だけのURL（`/problems?page=3`）もこちらに入れ、初期の条件の3ページ目を出す（設計者の判断）。
- クエリのない `/problems` は「自分の一覧の入口」として扱う。メニューの「問題」と同じである。
  初期の条件の一覧を見ている人がこのURLを共有すると、開いた人には、その人が覚えた条件の一覧が出る。
  これは受け入れる。札とボタンの数で、条件が効いていることは分かる。
- 「条件をすべて外す」を押すと、覚えた条件も消す。次からは初期の条件で開く。
- 未ログインのときは、覚えた解答状況は当てず、ほかの条件だけ当てる。覚えた解答状況は消さない（ログインし直したら戻る）。

## API

- 公開の問題一覧（`GET /problems`）に、並び順と難易度の範囲の指定を足す。
- 並びが同じ値の問題は、公開日が新しい順、次にIDの順で並べる。ページをまたいでも順が変わらないようにする。
- 解答状況の絞り込みは、誰の解答かが要る。ログイン中の利用者として呼べる入口を足す。
  公開の入口（認証なし）には、解答状況の指定を足さない。
  入口の名前と形は実装者が決める。問題の詳細には、同じ処理を利用者つきで呼ぶ入口（`GET /my/problems/{id}/publication`）がすでにある。
- カーソル（`cursor`）での続き読みは、初期の並び順でだけ使える。ほかの並び順と一緒に指定されたら400を返す。
  Webはページ番号（`offset`）で読むので、影響しない。
- 作成者（`author`）の絞り込みは今のまま使える。画面には出さない。

## やらないこと

- コンテストの中の問題一覧でAC済みを隠すこと（Issue #30）
- 作成者で絞り込む欄、キーワードでの検索、タグを2つ以上使う絞り込み
- 投票の難易度での並び替えと絞り込み
- 条件をアカウントに保存して端末をまたいで引き継ぐこと
- 記事の一覧（`/blog`）の並び替えと絞り込み

## こうなったら失敗

- 条件が効いているのに、画面を見ても分からない。
  覚えた条件で問題が減っているのに気づかず、「問題が消えた」と受け取られるのがいちばん困る。
  閉じているときも、札とボタンの数で必ず分かるようにする。
- 条件つきのリンクを開いた人に、送った人と違う並びや絞り込みの一覧が出る。
  解答状況は人ごとに違ってよい。クエリのない `/problems` も、上に書いたとおり別扱いにする。
- 未ログインの人に、解答状況の絞り込みが効いているように見える。
- 並び替えや絞り込みで、ページを送ったときに同じ問題が2回出たり、抜けたりする。

## 制約

- 一覧はサーバーが最初から描く（SSR）。条件を当てた一覧も、JavaScriptなしで読める状態を保つ。
- 定期便の回に含まれる問題のタグは、今と同じく解説の公開まで返さず、タグの絞り込みにも掛からない。
- 一覧のページは、今は `tag` と `contest` が変わるとページごと作り直す作りになっている（`definePageMeta`の`key`）。
  条件を変えてもパネルが開いたままになるように、ここは作り直す。
- 並び替えは、条件に合う問題すべての正解者数やお気に入り数を数えることになる。
  公開された問題は、2026-11-28の時点で173問である。
  手元で、問題を1000問、提出を数万件に増やしたデータを作り、いちばん重い並び順でも一覧の問い合わせが200ミリ秒以内に収まることを確かめる（設計者の判断の目安）。
  収まらなければ、索引を足すマイグレーションは入れてよい。
  数えた値を列に持つような、表の形を変える直し方が要るなら、実装を止めて利用者に相談する。
  公開後に本番でも確かめる。
- デプロイはAPIが先、Webがあと（`Deploy dev`の順のまま）。
- 文言は、マイページの一覧に合わせて、欄の名前を「並び順」にする。

## 実装者に任せること

- クエリの名前と値、Cookieの名前と中身の形
- ログイン中の利用者として一覧を読むAPIの入口の名前
- パネル、札、3つから1つ選ぶボタンの部品の分け方。マイページの一覧に `FilterSelect` と `StatusFilter` があるので、使えるなら使う。
- 開閉の動き（アニメーションの有無）
- ADRを書く。一覧の作りは ADR 0028 が決めているので、条件を覚える仕組みを含めて新しい番号で残す。
- `api/README.md` と `web/README.md` の更新

## テスト

- API: 並び順ごとの順、同じ値のときの順、難易度の範囲と未設定の扱い、解答状況の絞り込み（AC済みの判定が `GET /my/solved-problems` と合うこと）、条件を当てたあとの合計、知らない値の400、カーソルと並び順の併用の400
- Web（モックのAPI）: パネルの開閉、条件を変えるとURLと一覧が変わること、札の表示と×、ボタンの数、「条件をすべて外す」、条件を変えると1ページ目に戻ること、条件なしの `/problems` で覚えた条件が当たること、条件つきのURLでは当たらないこと、未ログインの解答状況、スマホ幅で横にはみ出さないこと
- Web（実DB）: ログインしてACした問題が「未ACのみ」で消え、「AC済みのみ」で出ること

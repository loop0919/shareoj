# ジャッジの配送と切り替えをモデル検査する設計

- 作成日: 2026-11-15
- 状態: 承認待ち
- 関連: [提出も採点も止めないジャッジ更新の設計](2026-11-14-zero-wait-judge-rollout-design.md)（承認待ち、未実装）

## 目的

提出が採点されずに終わる経路と、ジャッジ更新で採点が止まる経路が、設計の上で存在しないことを確かめる。
テストと実機検証は、試した順番しか確かめられない。
重複配信、ワーカーの途中停止、切り替えの途中失敗がどの順で重なっても性質が保たれることは、モデル検査で全状態を調べて確かめる。

## 利用者と決めたこと

- いちばん困るのは、提出が採点されずに終わること。
- 次に、ジャッジ更新で止まる時間を小さくしたい。
- 2レーン切り替え（上の関連設計）を実装する前に、この検査を挟む。

以下は、この3点を除いてすべて設計者の判断である。

## 目標

- いまの配送（Outbox → 要求キュー → ワーカー → 結果キュー → Bridge → DB）について、下の「確かめる性質」を検査する。
- 2レーン切り替えの手順（`rolling`の手順3〜7、`rolling-revert`、`requeue-digest`）について、同じ性質を検査する。
- 見つかった穴は、2レーン切り替えの設計書と実装計画を直してから実装に進める。
- モデルをリポジトリに残し、配送や切り替えの設計を変えるときに回し直せるようにする。

## やらないこと

- GoやPythonのコードそのものの証明。検査するのは設計のモデルである。
- 「採点待ちが10秒以内」のような時間の検査。時間は実機で測る。
- isolate、判定の優先順位、誤差ジャッジ、部分点の集約。配送とは別の話で、この設計の対象にしない。
- `rollout.py run`と、いまの`rolling`（送り出しを止める方式）のモデル化。前者は受付を止めるので配送の競合がなく、後者は置き換えられる。
- `dispatchOne`の優先順位のうち、順番そのもの（新しい提出、コード実行、作問の実行、リジャッジの順）のモデル化。
  空きがあるときだけ送る制限は、提出を止めうるのでモデルに入れる。
- 製品コードの変更。実装の不具合が見つかったら報告にとどめ、直すかどうかは別に決める。

## 避けたい結果

- モデルが実装や設計書と違う動きを書いていて、検査が通っても何も保証しない。
- どの性質も破れないほどモデルが緩い（故障を起こしていない、性質が常に真になる書き方をしている）。
- 検査に何時間もかかり、設計を変えたときに回されなくなる。

## モデルにするもの

TLA+で1つの仕様を書き、TLCで検査する。
PlusCalを使うかどうかは実装者が決める。

### 状態

| もの | モデルでの持ち方 | 対応する実装 |
|---|---|---|
| 提出 | 種類（新しい提出か、空きがあるときだけ送るものか）、終わったか、試行ID（番号）、送り出し済みか、digest、確定した結果とその試行ID | `submissions`の`status`、`judge_attempt`、`dispatched_at`、`job.image` |
| Bridgeの設定 | 送り先レーン、digest、直前のdigest | Lambdaの環境変数 |
| Bridgeの実行 | 開始時に読んだ設定を持ったまま動く。設定が変わっても、終わるまで古い設定で送る | `dispatch`、`send`、`sendSubmission` |
| APIの設定 | 新しい提出とリジャッジに付けるdigest | `JUDGE_CPP_IMAGE` |
| レーンa、b | メッセージ（提出、試行ID、digest）の多重集合。メッセージごとの受信回数。処理中かどうか | SQSの要求キュー |
| DLQ | 受信回数が上限に達したメッセージ | 要求のDLQ |
| 結果キュー | 結果（提出、試行ID、判定）の多重集合。結果ごとの受信回数 | SQSの結果キュー |
| 結果のDLQ | 受信回数が上限に達した結果 | 結果のDLQ（`infra/judge/storage.tf`、上限3回） |
| ワーカー | digest、取るレーン、停止中・待機中・処理中 | `judge/runner/worker.py` |
| 切り替え | 手順の位置、戻したかどうか | `rollout.py rolling` |

コード実行、作問の実行、リジャッジは、どれも「空きがあるときだけ送るもの」として1種類にまとめる。
それ以外の経路は新しい提出と同じである。
進捗の通知（`progress`）は判定に影響しないので、モデルに入れない。

### 動作

- 提出する。APIの設定のdigestが付く。
- リジャッジする。終わった提出が、新しい試行IDとAPIのdigestで「まだ送り出していない」へ戻る。
- Bridgeが送り出す。空きがあるときだけ送るものは、送り出し済みで終わっていないものが2件以上あれば選ばない（`dispatchOne`の`spareInFlight`）。
  この件数には、DLQに落ちたものと、旧レーンに残っているものも入る。
  送り出しは次の3つを別の動作にし、間で失敗できるようにする。
  1. 行を選ぶ。直前のdigestの提出なら現在のdigestへ付け替える。digestが合わなければJEで確定する（`runtime_mismatch`）。
  2. レーンへメッセージを送る。
  3. 送り出し済みにする。
- ワーカーが受信する。受信回数が1増え、メッセージは処理中になる。
- ワーカーが採点して結果を送り、メッセージを消す。この2つも別の動作にする。
- ワーカーがdigestの違うジョブを受け取る。メッセージを戻して止まる（ADR 0014の安全策）。
- Bridgeが結果を反映する。提出が終わっておらず、試行IDが一致するときだけ確定する。それ以外は捨てる。
  反映に失敗した結果は結果キューへ戻り、受信回数が上限に達すると結果のDLQへ移る。
- 可視性期限が切れる。処理中のメッセージがレーンへ戻る。受信回数が上限ならDLQへ移る。
- 6時間切れ。終わっていない提出がJEで確定する。本来の判定と区別できるよう、理由を持たせる。
- 切り替えの各手順（待機、切り替え、APIの切り替え、旧レーンの排出、`requeue-digest`、旧ワーカーの停止、残りの台の起動）。
- `rolling-revert`の各手順。使えるのは、切り替えの後から旧ワーカーを止める前までとする。

### 故障

次を、回数の上限つきで、どの時点でも起こす。

- ワーカーが途中で止まる（結果を送る前、送った後で消す前）。
- ワーカーがSIGTERMで止まる。結果を送る前ならメッセージを戻す。
- Bridgeの実行が途中で失敗する（メッセージを送った後、送り出し済みにする前を含む）。
- SQSが同じメッセージを重複して配信する。結果キューの順序が入れ替わる。
- Bridgeが結果の反映に失敗する（DBの一時的な失敗と、何度やっても通らない結果の両方）。
- 切り替えツールが手順の間で止まり、同じ位置から再開する。

## 確かめる性質

### 常に成り立つこと

1. **結果は上書きされない**：確定した結果が変わるのは、リジャッジで新しい試行になったときだけである。
2. **古い試行の結果は反映されない**：確定した結果の試行IDは、確定した時点の提出の試行IDと一致する。
3. **提出は失われない**：終わっていない提出は、必ず次のどこかにある。未送出、レーンの中、ワーカーの処理中、結果キューの中、要求のDLQの中、結果のDLQの中。
4. **新旧のワーカーは同じレーンを取らない**：digestの違うワーカーが、同じレーンで同時に動かない。
5. **digestの違うジョブを採点しない**：ワーカーが採点するジョブのdigestは、ワーカーのdigestと一致する。
6. **安全策は発動しない**：2レーンの手順では、digestの違いによるワーカーの停止が起きない。
7. **手順が原因のJEはない**：切り替え、再開、`rolling-revert`のどこでも、Bridgeの`runtime_mismatch`によるJEが起きない。
8. **送り先にはワーカーがいる**：Bridgeの実行が送るレーンには、送るdigestと同じdigestのワーカーが割り当てられている。
   故障で止まった場合は除く。手順が止めた、またはまだ起動していないことによる不在を見つける。

### いつか成り立つこと

故障がやみ、ワーカーとBridgeが動き続けるという仮定のもとで検査する。

9. **6時間切れに頼らず終わる**：要求のDLQにも結果のDLQにも落ちていない提出は、本来の判定で終わる。
   空きがあるときだけ送るものも対象にする。
10. **旧レーンは空になる**：切り替えが完了または`rolling-revert`で終わったあと、使っていないレーンにメッセージが残らず、直前のdigestで送り出し済みのまま終わっていない提出もない。

どちらかのDLQに落ちた提出は、6時間切れでJEになるまで採点待ちのまま残る。
これはいまの設計どおりの動きで、性質9の対象から外す。
検査では、DLQに落ちるのが「同じメッセージの受信が上限回数に達したとき」に限られることを、性質3と合わせて確かめる。

DLQに落ちた提出が2件あると、空きがあるときだけ送るものは、6時間切れまで1件も送られない。
これは性質9を破るはずで、検査で反例が出ることを確かめたうえで、いまの実装の不具合として報告する。

### 破れることの確認

モデルが緩すぎないことを確かめるため、わざと設計を崩した設定を用意し、性質が破れることを確認する。

| 崩し方 | 破れるはずの性質 |
|---|---|
| 結果の反映で試行IDを照合しない | 2 |
| 切り替えの手順5で、古い設定のBridgeの実行が終わるのを待たない | 7 |
| レーンを1本にし、旧ワーカーを止めずにdigestを切り替える | 6 |

破れなければ、モデルか性質の書き方が間違っている。

## 検査の規模

- 提出2件、リジャッジは1件につき1回まで、故障は合計2回まで、DLQの受信上限は2から始める。
- ワーカーは旧1台、新1台、残り1台とする。
- 空きの制限を調べる設定は、切り替えを含めず、提出3件（うち1件が空きがあるときだけ送るもの）で別に作る。
- 手元の機械で1つの設定が10分以内に終わる大きさにとどめる。足りなければ、対称性の指定と、配送だけの設定・切り替えを含む設定の分割で減らす。
- 規模を上げた検査（提出3件、DLQの上限3）は、一度だけ回して結果を記録する。時間がかかってよい。

## 置き場所と実行

| もの | 場所 |
|---|---|
| 仕様と設定 | `judge/formal/`（`JudgeDelivery.tla`と、配送だけ、空きの制限、切り替えあり、崩した設定それぞれの`.cfg`） |
| 説明 | `docs/judge/formal-model.md`。`docs/judge/README.md`から張る |
| 実行 | `make judge-model`。全設定を回し、崩した設定は破れたときに成功とする |
| 道具 | `flake.nix`の開発シェルにTLA+のツールを足す。パッケージ名は実装者が確かめる |

`docs/judge/formal-model.md`には次を書く。

- 何を確かめていて、何を確かめていないか。
- モデルの動作と、実装の場所の対応表。
- 回し方と、回し直すとき（配送、試行ID、キュー、切り替え手順のどれかを変えるとき）。
- 検査した日、規模、結果。

CIには入れない。
モデルが古くなるのは設計を変えたときで、CIはそれを検知できないからである。

## 見つかったときの扱い

TLCが性質の破れを見つけたら、反例を日本語の手順に直し、次のどれかに分ける。

| 種類 | 対応 |
|---|---|
| モデルの誤り | モデルを直す |
| 2レーン切り替えの設計の穴 | 設計書と実装計画を直す案を作り、利用者に見せる |
| いまの実装の不具合 | 反例と該当するコードの場所を利用者に報告する。この作業では直さない |

モデルは、設計書といまの実装に書いてあるとおりに保つ。まだ承認されていない直し方を先にモデルへ入れない。
設計の穴か実装の不具合が見つかったら、そこで作業を止めて利用者に報告する。
利用者が決めたあと、直すなら設計書とモデルを一緒に直す。直さないなら、その反例を「破れると分かっている設定」として残し、`make judge-model`は破れたときに成功とする。

## 完了の条件

- 配送だけの設定、空きの制限の設定、切り替えを含む設定が、すべての性質を満たす。満たさないものは、上の表のどれかに分け、利用者が扱いを決めている。
- 崩した設定が、3つとも期待した性質を破る。
- `make judge-model`が10分以内に終わる。
- `docs/judge/formal-model.md`に結果が記録されている。
- 利用者に、見つかったことと、2レーン切り替えの設計を変える必要があるかどうかを報告している。

## 実装者に任せること

- TLA+の書き方（PlusCalを使うか、モジュールを分けるか）。
- 状態数を抑える抽象化の細部。ただし「モデルにするもの」の動作と故障は省かない。
- 公平性の仮定の置き方。置いた仮定は`formal-model.md`に書く。

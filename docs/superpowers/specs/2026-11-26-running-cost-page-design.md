# 運用費ページの設計

- 作成日: 2026-11-26
- 状態: 2026-11-27に公開。同じ日に、ページを収支の表に変えた（「2026-11-27の変更」の節）
- 対象: GitHub Actions、GitHub Pages、`infra/deploy-access/`。API、Web（`web/`）、ジャッジ、CLIは変えない。

## 目的

ShareOJはGitHub Sponsorsで支援を受け付ける準備をしている。
各プランの説明は「運用費は月に約80ドル」を前提に書いてあるが、その数字を確かめられる場所がない。

支援を考えている人が、実際にAWSへいくら払っているかを見られるページを作る。
手で書き換える形は続かないので、毎月、AWSの請求額を自動で読んで更新する。

## 2026-11-27の変更: 収支の表にする

公開したあと、利用者は別のサービスの収支報告（月ごとに収入、支出、残高が1行で並ぶ表）を見て、同じ形にしたいと考えた。
良いと感じた点は、収入と支出と残高が月ごとに一覧で見えることである。
この節は、下の節のうち、ページの形と内訳に関わる部分を置き換える。
金額の取得、置き場所、AWSの権限は変わらない。

利用者と決めたこと。

- ページを、月ごとの「収入・支出・残高」の表にする。
  画面イメージ3つを見比べて、支出も列で分ける形を選んだ。
- 残高は、2026年9月からの収入から支出を引いた累計である。
  収入がまだないので、マイナスから始まる。マイナスは運営者の持ち出しである。
- 収入の列は「GitHub Sponsors」の1つだけにする。
- 「先月の合計を大きく」と、データベースやジャッジサーバーなどの細かい内訳は、ページからなくす。
- 収入は、収入があった月に利用者が手で1行書き足す。
  その月に実際に入った額を正確に返すAPIが見当たらず、Sponsorsが審査中で試せる実データもないためである。
  自動化は、実際に支援が入って数字を突き合わせられるようになってから考える。
- 支出の列は「サーバー利用料／前払い／ドメイン／消費税」の4つにする。
  消費税を独立させるのは、AWSが消費税を別の行で請求していて、列ごとに正確には割り振れないためである。
- 「サーバー利用料」は、データベース、ジャッジサーバー、サイトとAPI、監視・セキュリティ、その他の合計である。
- 新しい月を上に並べる。収入のない月と、額のない列は空欄にする。
- 金額は米ドルのままにする。表の上に「残高のマイナスは、運営者が自分で負担している額です」と添える。
- 注記は、表の下に番号付きで並べ、その月の行に同じ番号を付ける。
- スマホでは表の中だけが横に動き、ページ全体は横に動かない。
- 収入の額は、その月に支援者が払った額（米ドル）とする。支援者の名前や人数は載せない。
- 収入は、支出が確定して行ができた月にだけ出る。

実装で決めたこと。

- 保存するデータの形は変えない。
  `costs.json`は今までどおり区分ごとの額を持ち、ページを組み立てるときに設定の`columns`で列にまとめる。
  列の組み合わせを変えても、保存済みの月を全部作り直せる。
- 収入は`cost-data`ブランチの`income.json`に置く。
  `main`に置くと、書き足すたびに`Deploy dev`が走るためである。
- `income.json`は人が手で書き、確認なしに公開される。
  月の形や額がおかしいときは、実行を失敗させ、ページを変えない。
- 前払いの額だけの自動の注記はやめる。「前払い」の列に額が出るためである。
- 注記の番号は古い月から付ける。月が増えても、付いた番号が変わらない。
- 表は、キーボードでも横に動かせる。

## 読む人

GitHub Sponsorsでの支援を考えている人。
AWSの知識は前提にしない。

## 利用者と決めたこと

- 一番上に、先月の運用費の合計を大きく出す。（2026-11-27の変更でやめた）
- 金額は請求書どおりにする。
  前払いした分を月割りにならした額にはしない。
  このため、Savings Planを前払いした2026年10月は、合計がほかの月より大きく出る。
- このAWSアカウントの請求は、全部ShareOJの分として扱う。
  タグやアカウントでの絞り込みはしない。
  絞り込むと、合計が請求書と合わなくなる。
- 内訳はページ上の表で見せる。
  AWSの請求書のPDFは置かない。
  請求書には、アカウントIDと請求先の氏名・住所が載っているためである。
- 2026年9月分から載せる。
  以降は月が自動で増えていく。
- ページの形は、画面イメージ3つを見比べて選んだ次の形にする。（2026-11-27の変更で、収支の表に置き換えた）
  先月の内訳だけ開いていて、その下に過去の月が「月と合計」の一覧で並ぶ。
  月を押すと、その月の内訳が開く。
- 金額は米ドル、消費税込みで出す。
  Sponsorsのプランがドル建てなので揃える。
- 内訳は、AWSのサービス名そのままではなく、読む人に通じる言葉で5〜8行にまとめる。（2026-11-27の変更で、支出の4列に置き換えた）
  AWSのサービス名は小さく添える。
- 前払いを含む月には、その額を1行で添える（例:「3年分のサーバー前払い $◯◯ を含みます」）。
- 更新は毎月8日ごろに行う。
  前月の請求額が確定するのが、月初の数日後のためである。
- ページの下に、最終更新日とSponsorsページへのリンクを置く。
- アカウントID、リソースのID、氏名、住所は、どこにも載せない。
- 公開は全自動にする。
  利用者の確認を挟まない。
  想定より高い月や、返金が入った月の数字も、そのまま公開される。
  利用者はこれを承知している。

## 作らないもの

- 請求書のPDF、またはその加工版。
- 前払いを月割りにした表示。
- 円での表示、為替の換算。
- 運用費に対する達成率の表示。
  受け取った支援額は、2026-11-27の変更で載せることにした。
- 途中の月（確定していない当月）の表示。
- share-oj.netの中のページ、フッターからのリンク。
  リンクは、Sponsorsを公開するときに別に足す。
- 高い月を検知して知らせる通知。

## 失敗とみなす状態

- アカウントID、リソースのID、ロールのARNが、ページ、保存したデータ、リポジトリ、ワークフローのログのどこかに出る。
- ページの合計が、その月の実際の請求額と合わない。
- 取得に失敗したとき、または金額が確定していないときに、0ドルや途中の数字が公開される。
- 更新で過去の月が消える。
- 月に一度の更新が`main`へのpushになり、`Deploy dev`が走る。
- 足したロールで、費用の読み取り以外の操作ができる。
- 足したロールを、このリポジトリの`main`以外（ほかのリポジトリ、ほかのブランチ、プルリクエスト）から引き受けられる。

## 金額の取得

Cost Explorerの`GetCostAndUsage`を使う。

- 粒度は月、指標は`UnblendedCost`とする。
  サービス（`SERVICE`）と料金の種類（`RECORD_TYPE`）の2つで分ける。
  料金の種類は、前払いをほかの料金と見分けるために要る。
- 期間は、2026年9月から実行日の前月までとする。
- Cost Explorerがさかのぼれるのは14か月ほどである。
  それより前を始まりに指定すると、月が減るのではなく、呼び出しが失敗する見込みである。
  始まりは、さかのぼれる範囲に収める。
- 実行のたびに、読める範囲の全部の月を読み直して上書きする。
  AWSの記録があとから直された場合に、それに合わせるためである。
- 読める範囲から外れた古い月は、保存してある値をそのまま残す。
- Cost Explorerが「見積もり中」（`Estimated`が真）と返す月は公開しない。
  その月を除いて更新するのではなく、実行を失敗させ、ページを変えない。
  請求額の確定は10日ごろまで遅れることがある。
  8日に確定していなくても、人の手なしで、その月のうちにページへ載ること。
  `Estimated`が確定の合図として使えるかは、次の確認のときに実物で確かめる。
- 呼び出しは1回0.01ドルかかる。
  1回の実行での呼び出しは数回までとする。

### 「請求書どおり」の確かめ方

この設計では、「請求書どおり」を次の意味で使う。
その月にAWSが請求した額の合計で、消費税を含み、クレジットと返金を引いたあとの額。

`UnblendedCost`の月の合計はこれに当たる、と見込んでいる。
Savings Planの前払いは、買った月に1行で出るはずである。
ただし確かめてはいない。

実装のはじめに、2026年9月と10月について、Cost Explorerの合計とAWSの請求額を突き合わせる。

- 比べる相手は、AWSの請求の画面に出る、その月の合計（米ドル）である。
  前払いは別の請求書になるので、その月に出た請求書を全部足した額になる。
  円で支払っている場合も、請求書に載る米ドルの額を使う。
- 差が0.05ドル以内なら合っているとみなす。
  Cost Explorerは丸める前の額を返し、請求書は行ごとに丸めるためである。
- それより大きくずれたら、実装を進めずに利用者へ戻す。
- この確認には利用者のAWSへのログインが要る。

## 内訳のまとめ方

この節の「行」は、2026-11-27の変更のあとは保存するデータの区分であり、ページには4つの列にまとめて出る。

サービス名から行への対応は、`main`に置く設定で持つ。
次は案で、実際のサービス名は、実装時にCost Explorerの出力を見て確定する。

| 行 | 入れるもの |
| --- | --- |
| サーバーの前払い | Savings Planの料金、リザーブドインスタンスの前払い |
| データベース | RDS |
| ジャッジサーバー | EC2と、そのディスク |
| サイトとAPI | API Gateway、Lambda、CloudFront、S3、認証 |
| 監視・セキュリティ | CloudWatch、GuardDuty、Security Hub、Config |
| ドメイン | Route 53 |
| その他 | 上のどれにも当たらないもの |
| 消費税 | Tax |

- 「サーバーの前払い」に入れるのは、Savings Planの料金（前払いと月払いの両方）と、リザーブドインスタンスの前払いである。
  リザーブドインスタンスの前払いは、サービスで分けるとRDSなどの中に入ってしまう。
  料金の種類で見分けて、この行に移す。
- 設定にないサービスが出たら「その他」に入れる。
  実行は失敗させない。
- 0ドルの行は出さない。
- 行の中のサービスごとの金額は出さない。
  添えるのはサービス名だけである。
- 合計は請求額に合わせる。
  行を丸めた結果、行の和と合計が1セントずれる場合の扱いは実装者が決める。

前払いの期間（3年分）は、Cost Explorerからは分からない。
月ごとの注記を`main`の設定に手で書けるようにする。
注記がない月でも、前払いの行が0でなければ、金額だけの注記を自動で出す。

前払いしたあとの月は、前払いで賄っているサーバーの料金が請求に出ない。
2026年11月からは「ジャッジサーバー」の行が小さくなり、合計も実際にかかっている額より小さく見える。
これは「請求書どおり」にした結果である。
読む人が安くなったと受け取らないよう、ページに常に出す注記を1つ置く（例:「メインのサーバー代は2026年10月に3年分を前払いしたため、以降の月の請求には含まれません」）。
文言は`main`の設定で持つ。

## ページ

1枚の静的なHTMLで、JavaScriptのフレームワークは使わない。

上から順に次を置く（2026-11-27の変更のあとの形）。

1. ページの題（「ShareOJの運用費」）と、何のページかを言う文。
   金額が米ドルであることと、残高のマイナスの意味を添える。
2. 収支の表。
   列は、月、収入（GitHub Sponsors）、支出（サーバー利用料、前払い、ドメイン、消費税）、残高。
   新しい月が上。
3. 注記。常に出す注記と、月ごとの番号付きの注記。
4. 最終更新日と、Sponsorsページへのリンク。

- スマホの幅で、ページ全体には横スクロールが出ない。表の中だけが横に動く。
- 明るい配色と暗い配色の両方で読める。
- 表は、キーボードでも横に動かせる。
- 金額は`$1,234.56`の形で、桁をそろえて右に寄せる。
- 色と書体は、share-oj.netと並べて違和感がない程度に寄せる。
  同じ部品は使わない。
- Sponsorsページは、まだ公開していない。
  公開までリンクは出さず、設定の1か所を変えれば出るようにする。
- 検索エンジンに載ってよい。

## 置き場所と更新の流れ

- ページは、このリポジトリのGitHub Pagesに置く。
  独自ドメインは付けない。
  Pagesはまだ有効にしていない。
- `main`に置くもの: ページの元、取得のスクリプト、内訳の設定、注記、ワークフロー、テスト。
- `main`に置かないもの: 月ごとの金額のデータ。
  これはページ用の別のブランチに積む。
  `Deploy dev`は`main`へのpushのたびに走るので、データを`main`に入れると、月に一度アプリが配布されてしまう。
- 保存するのは、ページに出す行の金額だけにする。
  このブランチも公開されるので、サービスごとの細かい金額は残さない。
  このため、あとで内訳のまとめ方を変えても、読める範囲から外れた古い月は元のまとめ方のまま残る。

ワークフローは次の順で動く。

1. 毎月8日（日本時間）に定期実行する。
   手でも実行できる。
2. `main`の内容と、保存してある金額のデータを取り出す。
3. AWSのロールを引き受け、Cost Explorerを読む。
4. データを更新し、ページを組み立てる。
5. データを保存し、ページを公開する。

- 3で失敗したら、保存も公開もしない。
- 定期実行の失敗は、GitHubの通知で利用者に届く。
  それ以上の通知は作らない。
- `main`のページの元や設定を変えたときに、ページをすぐ作り直せること。
  手での実行で足りる。

## AWSの権限

- 専用のロールを1つ足す。
  許可は`ce:GetCostAndUsage`だけにする。
- 定義は`infra/deploy-access/`に足す。
  既存の`github_deploy`ロールと同じく、GitHubのOIDCで引き受ける。
- 引き受けの条件は、専用のGitHub環境（例: `cost-report`）に限る。
  既存のロールが`environment:dev`で絞っているのと同じ形である。
- subjectは既存のロールと別の変数で持つ。
  今の`github_subject`は末尾が`:environment:dev`であることを検査しているので、使い回せない。
  このリポジトリのsubjectは所有者とリポジトリのIDを含む形なので、`infra/README.md`の手順で確かめた値を使う。
- 環境のsubjectにはブランチが入らない。
  「`main`からしか使えない」は、GitHubの環境の設定（配布できるブランチの制限）だけで守られる。
  Terraformでは守れないので、公開の順の中で、この設定が入っていることを確かめる。
- 既存のデプロイ用ロールは使い回さない。
  権限が広すぎる。
- ロールのARNはアカウントIDを含むので、ファイルに書かず、GitHubの環境のシークレットに入れる。
- 認証のステップでは、アカウントIDをログで伏せる設定を入れる。
- `infra/deploy-access/`の適用は、利用者が手元で行う。

## テスト

- 内訳のまとめ: 設定にあるサービス、ないサービス、0ドルの行、負の額（クレジット）を含む月。
- 合計: 行の和と請求額が1セントずれる月。
- 上書きと保存: 読み直しで値が変わった月、Cost Explorerが返さなくなった月が残ること。
- 見積もり中の月があるとき、何も書き換えずに失敗すること。
- ページ: 月が1つだけのとき、前払いの注記がある月とない月、手で書いた注記がある月。
- Cost Explorerの応答は固定のファイルで代用する。
  テストからAWSを呼ばない。
- 前払い: Savings Planの料金と、RDSの中に出るリザーブドインスタンスの前払いが、どちらも「サーバーの前払い」に入ること。
- 公開前に、作ったページとデータにアカウントIDらしい12桁の数字や`arn:`が入っていないことを機械的に確かめる。
- はじめて実行したあと、ワークフローのログに12桁の数字と`arn:`が出ていないことを確かめる。

## 文書

- `infra/README.md`に、足したロールと環境の説明を足す。
- 運用の手順（手での実行、内訳の設定の直し方、注記の書き方、Sponsorsのリンクの出し方）を`docs/`に1枚足す。
- ADRを足すかどうかは実装者が決める。

## 公開の順

1. `infra/deploy-access/`にロールを足し、利用者が適用する。
2. GitHubの環境とシークレットを作り、環境を`main`ブランチだけに制限し、Pagesを有効にする。
   リポジトリの設定を変えるので、利用者の了承を得てから行う。
   制限が入っていることを、設定を読み直して確かめる。
3. 「請求書どおり」の確認（9月、10月の突き合わせ）と、`Estimated`の確認を行う。
4. ワークフローを手で実行し、ページを確かめる。
5. Sponsorsを公開するときに、Sponsorsの紹介文からこのページへ、このページからSponsorsへリンクする。

## 実装者に任せること

- スクリプトの言語と置き場所。
  リポジトリで既に使っているものから選ぶ。
- ファイル、ブランチ、ワークフロー、GitHub環境、ロールの名前。
- Pagesの公開のしかた（ブランチから配るか、Actionsの成果物で配るか）。
  ただし、データがgitの履歴に残ることと、`main`にpushしないことは必須である。
- 保存するデータの形。
- 見積もり中だった月を、その月のうちに載せるやり方（数日続けて実行する、など）。
  変更がない日は、何も書き換えないこと。
- Pagesの公開とAWSの読み取りを、1つのジョブにするか分けるか。
  ジョブは環境を1つしか使えない。
- ページの文言、配色、月の開閉の作り。
- 行の和と合計が1セントずれるときの扱い。

# 配信モードの設計

- 作成日: 2026-11-24
- 状態: 実装済み
- 対象: Web（`web/`）だけ。APIとデータベースは変えない。

## 目的

スタッフ（コンテストの作成者、問題の作者、テスター）のアカウントで順位表を映して実況すると、映してはいけない画面が配信に出るおそれがある。
利用者が挙げた場面は次のとおり。

- マイページを開いてしまう。
- 未公開の問題の作問画面に飛んでしまう。
- 開催中に、全員分の提出一覧や、順位表の得点から他の人の提出を開いてしまう。

スイッチを入れたブラウザでは、こうした画面を開こうとしても中身が出ないようにする。

## 利用者と決めたこと

- 名前は「配信モード」。設定画面でオンとオフを切り替える。
- 状態はブラウザごとに持つ。
  配信中に別のブラウザや端末でリジャッジなどの運営の操作をするためである。
- 配信モード中は、スタッフ、作者、テスターとして見えるものを出さない。
  画面を1つずつ隠すのではなく、既定で閉じ、残すものを選ぶ。
- 提出、サンプル検証、自分の提出、コード実行は、配信モード中も使える。
  ただし、自分がスタッフのコンテストでは使えない（設計者の判断。「コンテストのページ」の節）。
- マイページと作問画面は、URLを直接開いても中身を出さない。
- 配信モード中は、どのページでもヘッダーに「配信モード」と出す。
- 通知のベルとブラウザの通知、ヘッダーの「作成」メニューは、配信モード中は出さない。
- 利用者が見た画面イメージは、設定の項目、ヘッダー、閉じた画面、順位表の4場面である。
  このうち順位表の場面にあった「自分の提出」は、スタッフには出せない（後述）。

これより下は、明記がない限り設計者の判断である。

## 作らないもの

- 認可の仕組みにはしない。
  配信モードは、本人が誤って映す事故を防ぐためのものである。
  APIは変えず、CLIやほかのブラウザからの操作にも影響しない。
- アカウント単位の設定にはしない。
- 配信ソフトとの連携や、配信中かどうかの自動判定はしない。
- 画面の一部だけをぼかす表示は作らない。

## 失敗とみなす状態

- 配信モード中に、スタッフ、作者、テスターだからこそ見られる内容が、画面またはWebサーバーの応答に出る。
- セッションを使う通信を新しく足したとき、何もしなくても配信モードで通ってしまう。
- 配信モードが入っていることに、画面を見ても気づけない。
- 確認なしに配信モードが切れる。
- 公開ページを開くたびに、閉じた通信のエラー表示が出る。
- 配信モード中に、提出、サンプル検証、自分の提出、コード実行が使えない。
  自分がスタッフのコンテストは除く。

## 状態の持ち方

- Cookie `openoj-streaming` に持つ。値は`1`で、オフのときはCookieを消す。
- テーマのCookie（`openoj-theme`）と同じく、画面のコードから読み書きできるCookieにする。
  期限は1年、`SameSite=Lax`、`path=/`とする。
- 配信モード中は、Webサーバーがページの応答でこのCookieを設定し直す。
  期限は最後にページを開いたときから1年になり、画面のコードが書いたCookieの期限をブラウザが縮めても切れない。
  `Secure`は、セッションのCookieと同じく、サイトのURLがhttpsのときに付ける。
- Webサーバーは要求ごとにこのCookieを読む。
  最初に返すHTMLの時点から配信モードの表示になり、閉じる前の画面が一瞬出ることがない。
- ログアウトしてもCookieは消さない。
  ログインし直したときに、配信モードが黙って切れないようにするためである。
- 画面のコードは、配信モードかどうかを1つのcomposable（仮に`useStreamingMode`）から読む。

### 切り替えたとき

- オンにもオフにも、切り替えた直後にページを読み込み直す。
  画面が覚えているスタッフ向けの内容を捨てるためである。
- オフにするときだけ確認を挟む。
- 切り替えたタブは、同じブラウザのほかのタブに`BroadcastChannel`で知らせる。
  届かなかった場合に備えて、ほかのタブは、読み込んだとき、戻る・進むのキャッシュから戻ったとき（`pageshow`）、表示に戻ったとき（`visibilitychange`と`focus`）、画面を移るときにもCookieを見る。
  配信モードを入れる前から開いていたスタッフの画面を、そのまま映さないためである。
- Cookieが読み込んだ時点と違うと気づいたタブは、まず画面全体を覆って中身を隠し、それから読み込み直す。
  エディタは未保存のときに読み込み直しを止める確認を出すので、読み込み直しだけでは中身が残ることがある。
  読み込み直しが止められたら、覆ったままにする。
  覆いには「読み込み直す」を置く。
  Cookieが読み込んだ時点の値に戻ったら、覆いを外す。未保存の編集を失わずに済む。
- 覆いはモーダルダイアログで、Escapeや背景の操作では閉じられない。
  閉じてしまっても、直ちに出し直す。
- 覆いが出ているあいだは、画面の中身も隠す。覆いが閉じても、中身は映らない。
- 覆いの文言は「配信モードの設定が変わりました。」で、ボタンは「読み込み直す」とする。

## Webサーバーでの閉じ方

セッションを付けてAPIを呼ぶ通信は、すべて`web/server/utils/private-api.ts`の`privateAPI`を通る。
ここで既定を「閉じる」にする。

- 配信モードの要求では、`privateAPI`は、呼び出し側が「配信モードでも使う」と明示した呼び出しだけを通す。
  それ以外は、APIを呼ばずに403と`{ code: 'streaming_mode' }`で断る。
- `token`を明示して渡す呼び出し（ログイン直後の確認）は対象外とする。
- ログイン、登録、確認コードの呼び出し（`/auth/*`）は、いまの作りではセッションのCookieがあれば付けて送る。
  配信モードでもログインできるように、これらは通す側に明示する。
- 明示のしかた（引数の名前など）は実装者に任せる。
  条件は、呼び出し1か所ごとに書くことと、書き忘れると閉じる側に倒れることの2つである。

公開の内容とスタッフ向けの内容を出し分けている経路は、いまも401と403で公開の経路に切り替えている。
そのため、閉じた呼び出しは公開の見え方に落ちる。
切り替えのない経路では、403がそのまま画面に返る。

画像の経路（`web/server/api/images/[id].get.ts`）だけは、403では公開の経路に切り替えない。
この経路は、配信モードのとき`/my/images/{id}`を呼ばず、初めから公開の経路で読む。

### 配信モードでも通す呼び出し

| 用途 | Webサーバーの経路 | 条件 |
| --- | --- | --- |
| ログイン中かどうか | `GET /api/auth/me` | |
| ヘッダーの名前とアイコン | `GET /api/my/profile` | 読み取りだけ。更新は閉じる |
| 提出とサンプル検証 | `POST /api/my/submissions` | |
| ログイン、登録、確認コード | `POST /api/auth/*` | |
| 自分の提出の詳細 | `GET /api/my/submissions/{id}` | APIが本人の提出だけを返す。下の「自分の提出の詳細」のとおり一部を落とす |
| コード実行 | `POST /api/my/code-runs`、`GET /api/my/code-runs/latest` | |
| 解いた問題の印 | `GET /api/my/solved-problems` | |
| お気に入りと難易度の投票 | `/api/my/favorites/{id}`、`/api/my/difficulty-votes/{id}` | 読み取りと更新 |
| 問題ページの「自分の提出」 | `GET /api/problems/{id}/submissions?mine=1` | 一覧だけ。`mine=1`以外と詳細は公開の経路 |
| コンテストのページ | `GET /api/contests/**` | 次の節の条件を満たすときだけ |

この表にない呼び出しは閉じる。
閉じるものの例は次のとおり。

- 下書き、作問、テストファイル、リジャッジ、公開と応募
- コンテストの下書き、管理、共同作成者、参加者の一覧、結果の公開
- 参加登録、チーム、会場の合言葉
- 質問（一覧も投稿も）
- 通知、コンテストの予定の読み取り
- プロフィールの更新、パスワード、アカウントの削除、外部サービス
- 画像の一覧と追加、記事の下書き、招待の受け取り
- 他の人の提出をスタッフとして読む経路（`/my/submissions/{id}/public`）
- 凍結なしの順位表（`live=1`）
- 作者とテスターが読める公開前の解説（`/my/problems/{id}/publication`）
- 下書きの問題を問題ページとして読む経路（`/my/problems/{id}`）
- 下書きに貼った画像を読む経路（`/my/images/{id}`）。公開の画像の経路だけを使う

### 自分の提出の詳細

APIは、提出した本人がその問題の作者かテスターのとき、判定コードの診断（`checkerLog`）を提出の結果に付ける。
テストの中身や判定コードが読み取れる内容なので、配信モードのWebサーバーは、この項目を落としてから返す。
残すのは、対話型と2ステップの問題のサンプル検証に付く診断だけである。APIはこれを誰にも出す。
ほかの提出では、サンプル検証でも落とす。作問者が自分の問題で試すと、作問者だけが読める診断が付くためである。
生成のジョブでは、結果のケースに作者が生成したテストの出力（`output`、`outputFile`）が付くので、これも落とす。
作者とテスターにだけ付く項目がほかにないかは、実装のときに`api/internal/submissions`を読んで確かめた。上の2つで全部である。

自分の提出の詳細は、URLを直接開けば、開始前のコンテストの問題へ試した提出でも問題名が出る。
配信モードで開ける一覧からはそこへ行けないので、これは閉じない。

### コンテストのページ

APIは、コンテストのスタッフに、開始前の問題、全員分の提出、凍結後の結果を返す。
一方、参加者が提出するには、参加しているかどうかをセッション付きで読む必要がある。
そこで`/api/contests/**`は、配信モードのとき次の順で扱う。

1. 順位表（`live=1`を含む）と解説は、常に公開の経路で答える。
   スタッフかどうかの確認も、しない。
   確認するのは、セッションの経路を使う要求（コンテスト本体、問題、提出、`mine`）だけである。
2. 上の1に当たらず、セッションがあれば、まず`/my/contests/{id}`を読み、見ている人がスタッフかどうかを確かめる。
   応答の`staff`、`setter`、`owner`、`canEdit`、`canViewLiveStandings`、`canRevealResults`のどれかが真ならスタッフとする。
3. スタッフなら、その要求を未ログインの人と同じに扱う。
   公開の経路で答え、`mine=1`と`mine=team`は403と`streaming_mode`で断る。
4. スタッフでなければ、いまと同じにセッション付きで読む。
5. 2の読み取りが401と403以外で失敗したら、公開の経路にも切り替えず、失敗として返す。
   スタッフでないと確かめられたときだけ、セッション付きの経路を使う。

スタッフの「自分の提出」を閉じるのは、開始前に試した提出の行に、まだ公開していない問題名が出るためである。

スタッフは、自分のコンテストでは終了まで提出欄も出ない。
提出欄は、参加者かスタッフにだけ出る。公開の見え方にするとスタッフであることが画面に伝わらないので、未ログインの人と同じく提出欄が消える。
スタッフとして試すときは、配信モードを入れていないブラウザを使う。
スタッフは開催中の順位表に載らず、参加者にもなれないので、ほかに失う機能はない。

## 画面

### 設定

- 設定の項目に「配信モード」を足す。並びは「プッシュ通知」の次、「アカウント削除」の前とする。
- スイッチ「このブラウザを配信モードにする」を置く。初期値はオフ。
- 説明は次の3点を短く書く。
  - 配信モードのあいだ、このブラウザでは表示しないもの（マイページと作問・管理の画面、スタッフだけが見られる提出と凍結なしの順位表、通知）。
  - 提出とコード実行は使えること。
  - ほかのブラウザや端末には影響しないこと。
- 配信モード中の設定画面は、「配信モード」の項目だけを出す。
  ほかの項目は、`?tab=`で指定されても出さない。
- 配信モード中は、設定画面の戻るリンクを「ホームへ戻る」とし、`/`へ向ける。
  ふだんの「マイページへ戻る」は、閉じたページへ行ってしまうためである。

### ヘッダー

- 配信モード中は、ヘッダーの右側に「配信モード」の印を出す。赤系の色で、テーマの切り替えより左に置く。
- 印は押せる。押すと、オフにする確認をその場で出す。
  設定画面はログインとプロフィールがないと開けないので、未ログインでも配信モードを切れるようにするためである。
- 「作成」メニューと通知のベルは出さない。
- アカウントメニューは「設定」と「ログアウト」だけにする。
- スマホ幅でも印が隠れないようにする。

### 閉じたページ

次のページは、配信モード中は中身を出さず、閉じた画面を出す。

- `/my`で始まるページ。ただし`/my/settings`と`/my/submissions/{id}`は除く。
  今後`/my`の下に足すページは、何もしなくても閉じる。
- `/problems/new`、`/problems/post`、`/featured/apply`、`/blog/new`、`/onboarding`
- `/contests/{id}/team`（チームの参加コードが出る）

閉じるかどうかは、URLの文字列ではなく、当たったルートの名前で決める。
大文字に書き換えたURLなど、綴りを変えても同じページに当たるものは、同じように閉じる。

閉じた画面はヘッダー付きで出す。
`/problems/new`、`/blog/new`、`/my/contests/new`、`/my/contests/{id}`はヘッダーなしのエディタ用の表示（`route.meta.editorLayout`）なので、閉じた画面を出すあいだはレイアウトがこの指定を無視する。

- 見出し：「配信モード中は表示できません」
- 本文：「このページは、配信に映らないように閉じています。」
- 操作：「ホームへ戻る」と「配信モードを切る」
  「ホームへ戻る」は、サイト内の移動ではなく、ホームのページを新しく読み込む。
  「配信モードを切る」は、ヘッダーの印と同じく、オフにする確認をその場で出す。

閉じ方は実装者に任せる。
条件は、URLを直接開いたときもサイト内のリンクで来たときも同じ画面になることと、ページ本体の読み込みが走らないことである。
既存の`app/error.vue`はレイアウト付きで描かれるので、使える。

実装では、ミドルウェアが閉じたページへの移動を止め、エラー画面に閉じた画面を出す。
さらに、ページを描く場所（`app.vue`の`<NuxtPage>`）も、閉じたルートではページの代わりに閉じた画面を描く。
エラーの状態が消えても、閉じたページは描かれない。

### 公開ページに置かれた部品

公開ページには、閉じた通信を使う部品がある。
配信モード中は、これらを描かないか、通信を出さない。
エラー表示を出さないためである。

- 定期便の、スタッフ向けの次回の内容（`FeaturedDelivery`）
- コンテストの参加登録の部品（`ContestParticipation`、`useContestJoin`）
- コンテストの「質問」（メニューの項目と`ContestClarifications`）
- 通知のベル、通知の読み取り、ブラウザの通知、開始と終了の知らせ（`useNotificationPolling`、`useEventAlarms`）

次の部品は、閉じたページの上でだけ描かれるか通信を出すので、変えていない。

- コンテスト一覧の、自分の下書きと自分のコンテスト（`ContestList`）
- コンテストのチームの部品（`ContestTeamPanel`）
- 開始と終了の知らせの履歴（`EventHistory`）
- 問題のリジャッジ（`ProblemRejudge`）

実装のとき、`/api/my/`を呼ぶ箇所を全部洗い、この一覧に漏れがないか確かめる。

参加者向けの会場の合言葉の入力欄は、コンテストの概要で描かない。
参加登録の部品があった場所には、ログイン中で参加していない人に「配信モード中は参加登録できません。」と出す。
スタッフは公開の見え方では参加していない人と区別できないので、スタッフにも同じ文が出る。
ほかは何も出さない。

スタッフのコンテストでメニューの「自分の提出」を開いたときなど、閉じた通信の結果を出す場所には、「配信モード中は表示できません。」と出す。
`streaming_mode`のコードで見分ける。

編集へのリンクなど、押した先が閉じたページになるだけの入口は、残してよい。

### オフにする確認

- 見出し：「配信モードを切りますか？」
- 本文：「マイページやスタッフ向けの画面が、このブラウザで見えるようになります。」
- 操作：「切る」と「キャンセル」

## テスト

`web/tests`のPlaywrightで、次を確かめる。
フィクスチャのAPIに、スタッフとして読めるコンテストと提出が足りなければ足す。

- 設定でオンにすると、読み込み直したあともヘッダーに「配信モード」が出る。オフにするには確認が要る。
- 配信モード中、閉じたページのそれぞれをURLで直接開くと閉じた画面になり、下書きを読む通信が出ない。
- 配信モード中、スタッフのコンテストで、全員分の提出一覧、他の人の提出の詳細、凍結なしの順位表が、未ログインのときと同じ応答になる。順位表の得点は押せない。
- 配信モード中、スタッフでない参加者は、コンテストで提出でき、自分の提出を見られる。
- 配信モード中、スタッフのコンテストの問題ページに提出欄が出ない。
- 配信モード中、作者が自分の問題へ出した提出の詳細に、判定コードの診断が出ない。
- 配信モード中、ログインしていれば画像が表示される。
- 配信モード中にログアウトしてログインし直せる。配信モードは入ったままである。
- 未ログインでも、ヘッダーの印から配信モードを切れる。
- 未保存のエディタを開いたタブは、別のタブでオンにすると中身が覆われる。
- 配信モード中、スタッフかどうかの読み取りが500で失敗したら、セッション付きの経路を使わない。
- 配信モード中、問題ページで提出、サンプル検証、「自分の提出」、コード実行が使える。
- 配信モード中、ベルと「作成」が出ず、通知の読み取りが出ない。
- 配信モード中、公開ページ（ホーム、問題一覧、コンテスト一覧、定期便）に、エラー表示が出ない。
- 表に載せていない`/api/my/`の経路が、配信モード中は403と`streaming_mode`を返す。代表として下書き一覧、通知、プロフィールの更新を確かめる。
- 別のタブでオンにしたあと、もとのタブに戻ると読み込み直す。

`privateAPI`の既定が閉じる側であることは、明示のない呼び出しがAPIに届かないことで確かめる。

## 実装者に任せること

- `privateAPI`で「配信モードでも使う」を明示する書き方。

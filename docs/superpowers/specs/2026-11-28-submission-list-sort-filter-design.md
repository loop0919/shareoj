# 提出一覧の並び替えと絞り込みの設計

- 作成日: 2026-11-28
- 状態: 設計。実装はまだ。
- 対象: 問題ページの「すべての提出」「自分の提出」、コンテストの「提出一覧」「自分の提出」のWebと、その一覧のAPI。ジャッジとCLIは変えない。データベースは、索引を足すことはあっても、表の形は変えない。
- きっかけ: Issue #36（提出コードのフィルター・ソート機能が欲しい）

## 目的

提出の一覧は、提出日時が新しい順に並ぶだけで、絞り込めるのはコンテストの「問題」だけである。
コンテストの問題のように提出が多い一覧では、目当ての提出を探すのに何ページも送ることになる。

利用者が挙げた使い方は次の4つである。

- いちばん短いコード、いちばん速いコードを見る。
- 特定の人の提出だけを見る。
- AC、WA、TLEなど、特定の結果の提出だけを見る。
- 特定の言語の提出だけを見る。

提出の一覧で、並び順を選び、結果・言語・提出者で絞り込めるようにする。
画面の形は、問題一覧（ADR 0045）で作った「絞り込み・並び替え」のパネルと札に合わせる。

## 利用者と決めたこと

- 入れる画面は、問題ページの「すべての提出」と、コンテストの「提出一覧」の両方。
- 条件は、並び順、結果、言語、提出者。コンテストでは、今ある「問題」の絞り込みもパネルの中へ移す。
- 画面の形は、問題一覧と同じ「絞り込み・並び替え」のパネルと札にする。
- 「自分の提出」の一覧にも同じパネルを出す。提出者の欄だけ外す。
- 条件はURLに入れる。次に開いたときまで覚えることはしない。
- メモリでの並び替えと、コード長が長い順・実行時間が長い順は入れない。
- ページ送りは今のままにする（問題ページは「前へ／次へ」、コンテストはページ番号）。

## 画面

### 置く場所

- 問題ページ: 「すべての提出」「自分の提出」の見出しの下、表の上。
- コンテスト: 「提出一覧」「自分の提出」の表の上。今の「問題」の選択欄があった場所。

閉じているときと開いているときの形、札、ボタンの数、「条件をすべて外す」、スマホ幅での並びは、問題一覧のパネル（`ProblemConditions.vue`）と同じにする。
札の×を押したあとと「条件をすべて外す」のあとは、問題一覧と同じく、フォーカスをボタンへ移す。

### 欄

パネルには次の欄を、この順に並べる。

| 欄 | 形 | 選べるもの |
| --- | --- | --- |
| 並び順 | 選択欄 | 提出日時が新しい順（初期）、提出日時が古い順、コード長が短い順、実行時間が短い順 |
| 結果 | 選択欄 | すべて（初期）、AC、WA、TLE、MLE、OLE、RE、CE。ほかにも一覧に出る結果の種類があれば足す |
| 言語 | 選択欄 | すべて（初期）、言語ごとのまとめ（「C++（すべて）」「Python（すべて）」など）、処理系ごと（「C++23 (GCC)」「Python (PyPy 3.11)」など）。今は提出に選べない処理系も、提出が残っているので出す |
| 提出者 | 入力欄 | ユーザーIDを打ってEnterで絞り込む。「すべての提出」「提出一覧」だけに出す |
| 問題 | 選択欄 | コンテストだけ。すべて（初期）と、コンテストの各問題。今の選択欄と同じ中身 |

- 条件を変えたら、その場で一覧に反映し、1ページ目に戻す。
- 条件を変えてもパネルは開いたままにする。ページを開き直したときは、閉じた状態から始める。
- 条件に合う提出がないときは「条件に合う提出はありません。」と出し、「条件をすべて外す」のボタンを添える。
  条件がないときの文言（「提出はまだありません。」）は今のまま。
- 札の例: 「コード長が短い順」「結果: AC」「言語: C++」「言語: C++23 (GCC)」「提出者: alice」「問題: A」

### 言語の決まり

利用者は、GCCとClang、CPythonとPyPyとCodonのように、同じ言語の処理系を「C++」「Python」としてまとめて絞り込めることを望んだ。

- 言語の選択欄は、言語ごとに区切って並べる。
  処理系が2つ以上ある言語では、先頭に「（言語名）（すべて）」を置き、その下に処理系を1つずつ並べる。
  処理系が1つしかない言語は、その処理系だけを並べる。
- 「（言語名）（すべて）」を選ぶと、その言語のどの処理系の提出も出る。今は提出に選べない処理系（C++17など）の提出も含む。
- 2026-11-28の時点で、処理系が2つ以上ある言語は、C、C++、Python、Java、JavaScript、TypeScript、Rubyである。CとC++、JavaScriptとTypeScriptは別の言語として扱う。
- 札は、まとめを選んだときは「言語: C++」、処理系を選んだときは「言語: C++23 (GCC)」のように出す。
- どの処理系がどの言語に入るかの対応は、1か所に持つ。処理系を足したときに、対応を書く場所が増えないようにする。
  今は処理系の表示名を、APIとWebがそれぞれ持っている。対応を足すついでにどこまでそろえるかは、実装者が決める。
- URLの値は、処理系が増えても意味が変わらないようにする。「C++（すべて）」のリンクは、あとでC++の処理系が増えたら、その提出も含む。
- 同じ処理系でも、保存されている識別子に実行環境の違いを表す接尾辞が付くことがある。列で同じ表示になる提出は、同じ選択肢で絞り込めるようにする。

### コンテストの「オンサイトのみ表示」

- コンテストの「オンサイトのみ表示」のスイッチは、順位表と共用の表示の切り替えなので、パネルの外の今の位置に残す（設計者の判断）。
- 札にせず、ボタンの数にも数えない。スイッチ自体が、オンになっていることを示す。
- 「条件をすべて外す」では切り替わらない。
- オンサイトだけがオンで、ほかの条件がないときに提出がなければ、今の文言のままにする。「条件に合う提出はありません。」は、パネルの条件が1つ以上あるときだけ出す。

### リジャッジとの関係

- リジャッジした提出は、結果が出るまで採点中になる。
  結果で絞り込んだ一覧からは、採点中の間は外れ、結果が出たあと、条件に合えば次の更新で戻る（設計者の判断）。
  実行時間で並べた一覧では、採点中の間は最後に回る。
- 絞り込みや並び替えをしていても、リジャッジの選択と実行は今のまま使える。「結果: WA」で絞り込み、ページの提出を全部選んでリジャッジする、という使い方ができる。
- リジャッジしたあとは、選んだ提出が一覧から外れても、今の「リジャッジしました」の表示は出す。
- リジャッジ中に3秒ごとに更新する動きは、今は「一覧に採点中の行が見えている間」だけ動く。
  条件つきの一覧では採点中の行が見えなくなるので、この一覧からリジャッジを頼んだあとは、頼んだ提出の結果が出そろうまで（長くても1分）3秒ごとの更新を続ける。

### 並び順の決まり

- 「実行時間」は、一覧の「実行時間」の列に出している値である。その値で並べる。
- 実行時間のない提出（採点中、CEなど）は、実行時間が短い順では最後に置く。
- 並びの値が同じ提出は、提出日時が新しい順、次にIDの順で並べる。ページを送っても同じ提出が2回出たり抜けたりしないようにする。
- 並び順を選んだだけでは、結果で絞らない。いちばん短いACのコードを見たいときは、「結果: AC」と「コード長が短い順」を組み合わせる。

### 結果の決まり

- 絞り込みに使うのは、一覧の「結果」の列に出している結果である。
- 採点中の提出は、結果で絞り込んだ一覧には出ない。
- 部分点の問題では、満点でない提出の結果がどう出ているかを確かめ、列の表示と絞り込みが食い違わないようにする。

### 提出者の決まり

- ユーザーIDの完全一致で絞り込む。前後の空白は除く。
- ユーザーIDとして使えない文字列は、一覧を開かずに、入力欄の横に理由を出す（問題一覧のタグの欄と同じ扱い）。
- 存在しないユーザーIDなら、条件に合う提出がない一覧になる。
- チーム戦のコンテストでも、提出した本人のユーザーIDで絞り込む。

### 「自分の提出」

- 提出者の欄は出さない。URLに提出者の条件が付いていても、当てない。
- チーム戦の「チームの提出」も「自分の提出」と同じ扱いにし、提出者の欄は出さない。

## 条件とURL

- 条件はすべてURLのクエリに入れる。クエリの名前と値は、実装者が決める。初期値のときはクエリに出さない。
- コンテストの「問題」の条件は、今のクエリをそのまま使う。古いリンクが開けなくならないようにする。
- 問題ページとコンテストのページには、提出の一覧のほかにもクエリを使う表示がある（問題ページの `view`、コンテストのタブやページ番号）。条件のクエリは、それらと名前がぶつからないようにする。
- 「すべての提出」と「自分の提出」を切り替えたときは、提出者を除いて条件を保つ。
- 知らない値や形の合わない値は、APIが400を返す。WebはURLの知らない値を初期値として読む（問題一覧と同じ）。
- 条件は覚えない。Cookieは足さない。

## API

- 問題の提出一覧と、コンテストの提出一覧（公開の入口と、ログイン中の入口）に、並び順、結果、言語、提出者の指定を足す。
- コンテストの一覧が返す合計の件数は、条件を当てたあとの数にする。
- 誰に何が見えるかの決まり（下書きの実行、凍結中の提出、定期便の公開前、開始前のスタッフ、オンサイトの絞り込み）は変えない。
  絞り込みと並び替えは、今の決まりで見える提出の中だけで行う。
- 一覧の1ページの件数は今のまま（問題ページは50件、コンテストは表示件数の設定）。

## やらないこと

- メモリでの並び替え、コード長が長い順、実行時間が長い順
- 条件を次に開いたときまで覚えること
- 提出者を2人以上指定すること、ユーザーIDの前方一致や候補の表示
- 問題ページの一覧をページ番号で送る形に変えること
- マイページの提出一覧（`/my/submissions`）や、コード実行の履歴
- 列見出しを押して並び替える操作

## こうなったら失敗

- 見えてはいけない提出が、絞り込みや並び替えで見える。または、件数や順番から、伏せている提出の存在や結果が分かる。
  今の作りでは伏せている提出は一覧に出ないので、その作りを崩さないことが条件である。
- 条件が効いているのに、画面を見ても分からない（札とボタンの数で必ず分かるようにする）。
- 並び替えた一覧でページを送ると、同じ提出が2回出たり抜けたりする。
- 提出が多い問題で、一覧が目立って遅くなる。
- コンテスト中の一覧は自動で更新される。更新のたびにパネルが閉じたり、条件や選んだリジャッジの行が外れたりする。

## 制約

- 速さは、本番に近い大きさのデータで測る。問題一覧のときは、提出の行を小さく作った計測が実際の遅さを見逃した（ADR 0045）。
  1つの問題に提出が5000件、1つのコンテストに提出が2万件ある状態を作り、提出の`job`と`result`は本番と同じ数KBにする。
  どの並び順と絞り込みの組み合わせでも、一覧の問い合わせ（コンテストは件数の問い合わせを含む）が200ミリ秒以内に収まることを確かめる（設計者の判断の目安）。
- 収まらなければ、索引を足すマイグレーションは入れてよい。表の形を変える直し方が要るなら、実装を止めて利用者に相談する。
- 実行時間は採点結果（`result`）の中にある。並び替えのたびに全部の提出の結果を読むと遅いので、索引で済むかを最初に確かめる。
- 索引に使う条件や関数を、あとで問い合わせの側だけ変えると索引が使われなくなる。問題一覧と同じく、それに気づけるテストを足す。
- 一覧の自動更新（15秒ごと、リジャッジ中は3秒ごと）は今のまま動かす。更新は今の条件のまま行う。
- 配信モード（ADR 0042）で閉じている一覧は、今のまま閉じる。
- デプロイはAPIが先、Webがあと。索引を作る間は提出の書き込みが待たされるので、コンテスト中を避けて配布する。
- 文言とパネルの部品は、問題一覧のものを使えるなら使う。同じ形の部品を2つ作らない。

## 実装者に任せること

- クエリの名前と値
- 問題一覧のパネルの部品を、提出の一覧と共用できる形に分け直すかどうか、分け直すならその形
- 言語と処理系の一覧と、その対応をどこに持つか（今は選べない処理系の扱いを含む）
- 結果の種類の一覧をどこに持つか
- 索引の形
- ADRを書く。`api/README.md`と`web/README.md`を更新する。

## テスト

- API: 並び順ごとの順と同じ値のときの順、実行時間のない提出の位置、結果・言語（まとめと処理系ごと、接尾辞の付いた識別子、今は選べない処理系）・提出者の絞り込みとその組み合わせ、条件を当てたあとの合計、知らない値の400、
  見え方の決まりが条件つきでも変わらないこと（凍結中の提出、下書きの実行、定期便の公開前の提出が、条件を付けても出ないこと）
- API: 速さ（本番に近い大きさのデータ、任意で走らせる形）と、索引が使われていることの確認
- Web（モックのAPI）: 2つの画面それぞれで、パネルの開閉、条件を変えるとURLと一覧が変わること、札の表示と×、「条件をすべて外す」、1ページ目に戻ること、
  「すべての提出」と「自分の提出」の切り替えで条件が保たれること、自動更新でパネルと条件が保たれること、コンテストの古い「問題」のリンクが開けること、スマホ幅で横にはみ出さないこと
- Web（実DB）: 提出を何件か作り、結果・言語・提出者で絞り込めることと、コード長・実行時間で並ぶこと

# 誤差ジャッジの設計

- 作成日: 2026-11-12
- 状態: 承認待ち
- 前提: [2ステップ形式（Run-twice）](2026-11-11-run-twice-design.md)の実装（ブランチ`feat/run-twice`）の上に作る

## 目的

答えが実数の問題を、検証コードを書かずに出せるようにする。
作問者は「絶対誤差または相対誤差が$10^{-6}$以下」のような条件を選ぶだけでよい。

いまの通常判定は、提出の出力と期待出力を空白で区切り、トークンの完全一致を見る。
実数の問題では、作問者がスペシャルジャッジの検証コードを毎回書く必要がある。

## 利用者と決めたこと

- 出力は、実数1個か、空白や改行で区切った実数の並びが多い。
  文字列が混ざることもある。
- 条件の種類は、絶対誤差、相対誤差、絶対誤差または相対誤差の3つとする。
- 許容誤差εは、$10^{-1}$から$10^{-12}$までの12個から選ぶ。
  初期値は$10^{-6}$とする。
- 期待出力は真の値からわずかにずれていることがある。
  真の値からε以内の解答が必ずACになるよう、εに余裕を上乗せして比べる。
- 余裕の初期値はεの0.1%とする。
  作問者は割合を変えられる。
  答えが無限小数になる問題が多いので、余裕は初期状態で効かせ、入力欄も最初から見せる。

## やらないこと

- 10のべき乗以外のε。
- トークンごとに条件を変える指定（1個目は整数、2個目は実数など）。
- 行の数や行内の区切り方の検査。
  通常判定と同じく、空白と改行を区別しない。
- 開発用Dockerワーカーでの対応。
- スペシャルジャッジ、対話形式、2ステップ形式との併用。

## 比べ方

以下は設計者の判断である。

提出の出力と期待出力を、通常判定と同じ規則でトークンに分ける。
トークンの数が違えばWAとする。
同じ位置のトークンを1組ずつ比べ、すべて一致すればACとする。

1組のトークンは、次の順に判定する。

1. バイト列として同じなら一致。
2. 両方が**数**として読めるなら、下の条件で比べる。
3. それ以外は不一致。

### 数として読むトークン

次の形の10進数だけを数とする。

```text
-?(数字+ または 数字+.数字* または .数字+)([eE][+-]?数字+)?
```

- 例：`3`、`-0.5`、`2.`、`.25`、`1e-3`、`6.02E+23`。
- 先頭の`+`、16進、`1_000`、`nan`、`inf`、`infinity`は数としない。
  これらは文字列として完全一致だけを認める。
- 400バイトを超えるトークンと、指数の絶対値が400を超えるトークンは、数としない。
  極端な値の計算で採点を止められないようにするためである。
- 整数も数である。
  期待出力が`3`のとき、`3.0000001`は条件を満たせば一致する。
- `-0`と`0`は同じ値として扱う。

### 条件

提出の値を$a$、期待出力の値を$b$、しきい値を$T$とする。

| 種類 | 一致の条件 |
| --- | --- |
| 絶対誤差 | $\lvert a - b \rvert \le T$ |
| 相対誤差 | $\lvert a - b \rvert \le T \times \lvert b \rvert$ |
| 絶対誤差または相対誤差 | 上のどちらかを満たす |

しきい値は、εと余裕の割合$m$（%）から決める。

$$T = \varepsilon \times \left(1 + \frac{m}{100}\right)$$

- $m$の初期値は0.1とする。
  εが$10^{-6}$なら、$T$は$1.001 \times 10^{-6}$になる。
- 相対誤差で$b$が0のときは、$a$も0の場合だけ一致する。
- 比較は、トークンの10進表記を正確な有理数として計算する。
  浮動小数点の丸めを判定に入れない。
  誤差が$T$以下なら必ず一致し、$T$をわずかでも超えれば不一致になる。

### 速さ

比較は管理ワーカーの中で動き、採点ホストは1スレッド分のCPUと1,536 MiBのメモリしか使えない。
提出は出力を自由に決められるので、すべての組を遅い経路へ送る出力も作れる（`0`に対する`0.0`の並びや、しきい値ちょうどの値の並びなど）。
次の3つで、提出が比較の時間を引き延ばせないようにする。

- 数の比較を始める前に、トークンの数を数える。
  数が違えばそこでWAとし、数の比較をしない。
  これで比較の量は期待出力のトークン数で決まり、作問者が決める量になる。
- 1組の計算量は、トークンの上限（400バイト、指数±400）で抑える。
- 出力をまとめてメモリに展開しない。
  比較中の追加のメモリは、出力の大きさに比例させない。

速さの目安は、すべての組がしきい値ちょうどになる100万組を、採点ホストで5秒以内に比べ終えることとする。
手元のテストでは、同じ入力に余裕を持たせた上限（30秒）を設け、実測値を記録する。
採点ホストでの実測は、配置時のsmokeで1回取り、仕様に書く。
目安に届かない場合は、届いた値を作問者向けドキュメントに書く。
ホストに追加のパッケージやコンパイル済みの補助プログラムを入れて速くすることは、今回はしない。

方法は実装者に任せる。
たとえば、浮動小数点で明らかに条件の内側か外側と分かる組はそこで決め、境界に近い組だけを正確に計算する。
正確な計算には、有理数のほか、十分な精度を指定した10進数や、桁をそろえた整数を使ってよい。
どの方法でも、結果は有理数だけで計算した場合と同じでなければならない。

作問者向けドキュメントには、期待出力の数が数百万個になると1ケースの比較に数十秒かかり得ることと、採点全体の上限（1,800秒）に含まれることを書く。

## 保存とAPI

下書きに`errorJudge`を加える。

```json
{"mode": "either", "epsilon": "1e-6", "marginPercent": "0.1"}
```

- `mode`は`absolute`、`relative`、`either`のいずれか。
- `epsilon`は`"1e-1"`から`"1e-12"`までの12個の文字列のいずれか。
- `marginPercent`は省略できる。
  省略と`null`は0.1として扱う。
  指定する場合は、0以上100以下の10進の文字列で、小数は6桁までとする（例：`"0"`、`"0.5"`、`"12.345678"`）。
  指数表記と符号は受け付けない。
- `checker`、`interactor`、`runTwice`、`errorJudge`は、同時に2つ以上を指定できない。
  すべてなければ通常判定とする。

コードを持たないので、公開準備の指摘は増やさない。
形の誤りは下書きの保存時に拒否する。

問題の公開APIは、`errorJudge`の`mode`と`epsilon`を返す。
`marginPercent`は返さない。

公開と提出の受付時に、`errorJudge`をテストケースと一緒に固定する。
ジョブにも同じ形で載せる。
リジャッジ、サンプル検証、部分点は通常判定と同じに動く。
生成用と入力検証用のジョブには付けない。
ローカルのDocker判定は、誤差ジャッジの問題への提出を受け付けない。
DBマイグレーションは不要である。

## ワーカー

通常判定の比較（`judge/runner/host.py`の`case_result`）を、ジョブに`errorJudge`があるときだけ上の比べ方に替える。
検証コードの実行はなく、資源上限は通常判定と同じである。
`errorJudge`の形が誤っているジョブは拒否する。

サンプル検証では、通常判定と同じく入力、期待出力、実際の出力を返す。

### 古いワーカーへの備え

誤差ジャッジを知らないワーカーは`errorJudge`を無視し、完全一致で採点する。
正しい解答がWAになるので、2ステップ形式の結果の印と同じ仕組みで防ぐ。

- ワーカーは、`errorJudge`のあるジョブの結果に印を付ける。
- bridgeは、`errorJudge`のあるジョブの印のない結果を、JE以外ならJEとして保存し、`platform`に記録する。
- 印は保存せず、APIの応答にも出さない。

印の名前と、2ステップ形式の印との共通化は実装者に任せる。

## Web

- 問題編集画面の判定方法に「誤差ジャッジ」を5つ目の選択肢として加える。
- 選ぶと次の入力が出る。検証コードの欄は出さない。
  - 種類：絶対誤差、相対誤差、絶対誤差または相対誤差。初期値は「絶対誤差または相対誤差」。
  - 許容誤差：$10^{-1}$〜$10^{-12}$の選択。初期値は$10^{-6}$。
  - 余裕：εに対する割合（%）の入力欄。初期値は0.1。
    スイッチで隠さず、常に表示する。
    0を入れると余裕なしになる。
    入力した値を`marginPercent`として保存する。
- 入力欄の並びと、その下の説明は次の形にする（利用者と決めた見せ方）。

  ```text
  種類        [絶対誤差または相対誤差 ▾]
  許容誤差    [10^-6 ▾]
  判定の余裕  [0.1] %

  期待出力との誤差が 1.001 × 10^-6 以下なら正解になります。
  想定解の出力も真の値からわずかにずれるので、その分だけ広げて比べます。
  ```

  - 割合そのものでなく、結果として何が正解になるかを数字で見せる。
    1行目のしきい値は、εと余裕の入力に合わせてその場で書き換える。
    値は丸めずに正確に表示する（余裕が0.1ならεの1.001倍）。
  - 1行目の言い回しは種類に合わせる（相対誤差なら「期待出力との相対誤差が…」）。
  - 余裕が0のときは、2行を「期待出力との誤差が 10^-6 を少しでも超えると不正解になります。」の1行に替える。
  - 余裕の入力が形に合わないときは、しきい値の行の代わりに誤りを出し、保存しない。
- 説明の下に、数として読めるトークンだけを誤差で比べ、それ以外は完全一致で比べることを1行で書く。
- 作問者向けドキュメントへのリンクを置く。
  ドキュメントには、期待出力の精度がεの何分の1より粗いと余裕で吸収しきれないかの目安を、表で載せる。
- ほかの判定方法へ切り替えたら`errorJudge`を`null`にし、誤差ジャッジへ切り替えたらほかの3つを`null`にする。
- 問題ページとコンテストの問題ページに、種類とεを表示する。
  例：「誤差ジャッジ：絶対誤差または相対誤差が$10^{-6}$以下なら正解です。」
  余裕は表示しない。
- 作問者向けドキュメントの判定コードのページに節を加え、比べ方、数として読む形、余裕の意味を表と箇条書きで短く書く。

## CLI

`problem.toml`に表`[error_judge]`を加える。

```toml
[error_judge]
mode = "either"
epsilon = "1e-6"
margin_percent = "0.5"  # 省略できる
```

`pull`と`push`は、`[checker]`、`[interactor]`、`[run_twice]`と同じ規則で扱い、4つのうち1つだけを指定できる。
CLIのREADME、ガイド、Webのドキュメントを更新する。

## 配置

2ステップ形式と同じ順序で配置する。
ワーカーを先に配布し、その後にAPIとbridge、Webを配置する。
2ステップ形式がまだ配置されていなければ、同じ配布にまとめてよい。

実機のsmoke testに、誤差ジャッジの検証を加える。
境界ちょうどの値がACになり、境界をわずかに超えた値がWAになることを、3つの種類で確かめる。

## 検証

- ワーカーの単体テスト
  - 3つの種類それぞれで、誤差が$T$ちょうどの値はAC、$T$を最小の桁だけ超えた値はWA。
  - 余裕の指定（0、0.1、100）でしきい値が変わる。
  - 浮動小数点では境界を誤る値（`0.1`と`0.3`の組み合わせなど）が、正確に判定される。
  - 文字列の混在、トークン数の違い、`nan`と`inf`、先頭の`+`、400バイトを超えるトークン、指数が400を超えるトークン。
  - 相対誤差で期待出力が0のとき。
  - `-0`と`0`、`1e3`と`1000`、`2.`と`2`。
  - 16 MiBの数の並びの比較時間。
  - 速い経路を作る場合、無作為な入力で有理数だけの計算と結果が一致すること。
- APIとbridgeのテスト：4つの判定方法の排他、`errorJudge`の形の検査、公開APIが`marginPercent`を返さないこと、印のない結果のJE。
- Webのテスト：判定方法の切り替え、余裕の初期値と保存される値、問題ページの表示。
- CLIのテスト：`[error_judge]`のpushとpull、ほかの3つとの置き換え。

## 実装者に任せること

- `errorJudge`以外の内部の名前、比較の関数の置き場所。
- 速い経路の有無と方法。
- 結果の印の名前と共通化。
- Webの文言の細部。

### 3. 作った経緯

時系列で話す。

1. 2024年、専門学校の卒業制作でAIbleCodeを作った（自動ジャッジと生成AIのコードレビューが付いたプログラミング学習サービス）。悔いが残った。
   - メイン：ジャッジをJudge0に任せていて、テストケースごとにコンパイルが走って遅かった。ライブラリも入れづらかった。
   - サブ：作問基盤を整えきれなかった。
2. 2026年7月末に、MojaCoderが年末でサービスを終了すると発表した。8月末に、アルゴ式の個人向けサービスが終了した。
3. 気軽に作問できる場所がなくなり、競技プログラミング界隈が縮んでいくのがいやで、今度こそと作り始めた。

AIbleCodeの悔いは、メインを5、サブを4で回収する。

### 4. コンセプトとUI

コンセプトは「気軽に誰でも、それでいてしっかりしたコンテストも開ける」。

- 気軽に：Markdownで問題と解説を書いてテストケースを置き、最後に「公開する」をポチれば完成する。
- しっかり：深い需要にも応える。「作る」「確かめる」「開く」の3段階に分けて1枚に載せる。口で説明するのは各段階で1つにし、残りは名前だけ載せる。
  - 作る：入出力の生成と検証を説明する（テストケースを手で作らなくてよく、入力が制約を守っているかも機械で確かめられる）。スペシャルジャッジ、インタラクティブ、部分点は名前だけ。AIbleCodeで整えきれなかった作問基盤への答えとして話す。
  - 確かめる：テスターを説明する（公開前に他の人に解いてもらえる）。
  - 開く：チーム戦を説明する。順位表の凍結と共同作成は名前だけ。

気軽さとしっかりさは、UIと、声にすぐ応える開発の流れで支えている。

- UI：AtCoder、Codeforces、yukicoder、MojaCoder、MOFE、Zenn（Markdown）の、使っていて嬉しいところを組み合わせた。こだわりは多いが、ここでは広げない。
- 声にすぐ応える：要望が出たらAIに修正を頼み、テストとローカルビルドでの目視確認で品質を確かめてから、CI/CDで出す。WebとAPIはGitHub Actionsでテストを通す。ジャッジの配布は6で話すので、ここでは触れない。

8のコンテストの話で、実際にその日に直せたことを答え合わせとして回収する。

### 5. ジャッジの前振り

- AIbleCodeではジャッジをJudge0に任せていたが、今回は自分で作った。コンパイルは1提出につき1回にして全ケースで使い回し、言語とライブラリも自分で固定して入れる（10月26日の時点で、言語ガイドに24の環境がある。発表前に数え直す）。
- その代わり、ジャッジにまつわる面倒も自分で背負う。OJは、他人が書いたコードを自分のサーバで動かすサービスである。
- 課題は「守る」と「詰まらせない」の2つ。

### 6. 守る：隔離とセキュリティ

1. **閉じ込める（1.5分）**：isolateで提出をケースごとに閉じ込め、ネットワークを遮断する。期待出力や認証情報は渡さない。これは最初から前提だった。
2. **予算に合わせて選び直す（0.5分）**：1枚で流す。Fargate（9/3）→ Firecracker（9/11、常時稼働で約85 USD/月）→ Lightsail 2 GB＋isolate（9/11、10 USD/月）→ EC2のプール（9/29）。提出とカーネルを共有するので、VMほど安全だとは言わない。
3. **周りも固める（2分）**：9月末ごろから企業の情報漏洩のニュースが相次ぎ、閉じ込めるだけでなく周りも固めた。社名は出さない。
   - 採点台は外からの受信を持たず、運用はSSMで行う。認証情報はインスタンスロールから得て、IMDSv2に限り、IMDSへの通信をrootに限る（9/29）。
   - 受付を止めずにOS更新を配布する仕組みを作った（10/10）。primaryにカーネルを含む25件のセキュリティ更新が溜まっていたのがきっかけ。ジャッジの配布は`rollout.py`で行い、全言語の検証と本番への提出の確認まで済ませて完了とする。
   - GuardDuty（10/10）とSecurity Hub（10/16）を入れた。日付は`~/aws-setting`のTerraformの履歴による。
4. **よかった～（0.5分）**：そのあとPHPの脆弱性がニュースになった。閉じ込めてあるうえに、4で話したとおりすぐ直して出せるので、よかった～となった。ShareOJの提出言語にPHPはないので、ShareOJでPHPを直した話にはしない。件名やCVE番号を載せるなら、スライドを作るときに確認する。

### 7. 詰まらせない：キューとスケーリング

- キューで提出を受け止め、1台で同時に採点するのは1件にする。再配信があっても確定した結果は守る、という話は1枚で済ませる。
- 負荷を見てから台を増やすのでは、コンテスト開始直後の集中に間に合わない。起動してから採点を始められるまで数分かかる。
- コンテストの開始時刻はDBに入っているので、開始30分前にburstの台を起こしておく。
- 開始15分で参加者1人あたり約22秒分の採点が要ると仮定すると、100人で約5台になる。仮定に基づく見積もりで、実測ではない。
- 予備の小ネタ：1割安いAMDのt3a.smallでは、GoやNimのコンパイルが上限を超え、通っていた提出がCEやTLEになったので、Intelのt3.smallにした。

### 8. コンテストをやった話

1. 続行できなくなるトラブルはなかった。6と7の答え合わせになる。
2. D問題で、サンプル以外の内部ケースを入れ忘れた事件。発表までにサンプルだけの問題を公開前に止められるようになっていれば、ここで「その後こう防いだ」と回収する。
3. もらった声
   - UIが全体的に使いやすい。
   - コンテスト中にヘッダの「問題」を押すと、コンテストの問題一覧ではなく全体の問題一覧に飛んでしまう。
   - 他のジャッジより提出頻度の制限に引っかかりやすい。
4. 声を受け取ったその日に直せた。4の「声にすぐ応える」の答え合わせとして短く触れる。
   - 例：提出頻度の制限を90秒に2回から60秒に2回へ緩めた（`49cbedd`、Claudeとの共同作成）。変更は制限値の1行と、テストとガイドだけ。
   - Webと採点基盤を分けているので、UIやAPIの修正はジャッジを止めずに出せる。

### 9. 今後の展望

- もらった声への対応を続ける。
- 継続して運営していく。ドメインを3年、Savings Planを3年で契約したので本気である。3の「作問できる場所がなくなっていく」を受けて、なくならない場所にする、と結ぶ。
- GitHub Sponsorsなどで寄付を募りたいが、手続きが面倒でまだしていない。知見がある人は教えてほしい。質疑や発表後の会話のきっかけにもする。

- 作問ミスを仕組みで防ぐ話は、発表時点で対応が済んでいなければここで話す。今の公開条件はテストケースが1件以上あるかを見るだけで、サンプルだけの問題は通ってしまう。

声への対応、継続運営、寄付の知見募集は確定。締めの一言は仮置き。

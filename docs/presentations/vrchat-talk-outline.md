# ShareOJ 発表構成（VRC競プロ部）

VRChatの技術・学術系グループの発表会で、VRC競プロ部としてShareOJを紹介するときの構成案。
スライドはGoogle スライドで作っている。
11月23日の時点で、下の表で「済」とした10枚がある。

## 前提

- 発表は2026年12月9日。
- 枠は30分。本編は20分前後とし、25分までは許容される見込み。残りは質疑に充てる。
- 聞き手はITに明るいが、競プロやジャッジ、インフラの中身までは知らない人たち。
- 持ち帰ってほしいのは次の3つ。
  - 技術的な知見（ジャッジをどう作ったか）
  - 個人開発を運営していく上での知見
  - ShareOJへのちょっとした興味
- 機能の紹介は並べない。コンテストを開くのに必要十分な機能がある、と軽く伝わればよい。
- ジャッジの優先順位（提出 > コード実行 > ジャッジ生成 > リジャッジ）は扱わない。
- ジャッジの話は「安全・安く・安定」の3本柱で通す。12枚目で掲げ、13〜19枚目で答え、20〜21枚目で実際にどうだったかを確かめる。

## 各スライドの中身

「済」のスライドは、直すところだけを書く。

### 4〜5. モチベはどこから？（済）

- MojaCoderは年末で終了する予定で、発表の日にはまだ動いている。「サービス終了」を「年末でサービス終了」に直す。
- 口頭で足す：2026年7月末に終了が発表され、8月末にはアルゴ式の個人向けサービスも終わった。9月初めに作り始めた。

### 6. 本当につくれそう？（旧14枚目）

5枚目の「ならば自分で作ろう！！」に自分でつっこむ1枚。
ここで出す卒業制作と生成AIは、あとのスライドで回収する。

- 載せる
  - 専門学校の卒業制作（2024年）で、競プロサイトのAIbleCodeに挑戦していた。
    - 設計やライブラリは、そのとき調べてあった。
    - ジャッジをJudge0に任せたら、テストケースごとにコンパイルが走って遅かった。リベンジしたい。
  - 生成AIが、仕様とビジョンを伝えれば実装してくれるようになった。
  - 結び：ある程度は作れそうなビジョンはあった。
- 直すところ：「使用ライブラリの制約上実現できなかったこと」は、Judge0の話に書き換える。聞き手に伝わるのは具体的な悔いのほうである。
- 回収する場所：Judge0の悔いは12〜13枚目（今回はジャッジを自分で作る）、作問基盤の悔いは9枚目、生成AIは11枚目と22枚目。

### 7. どんなものを作る？

- 載せる：「気軽に誰でも、それでいてしっかりしたコンテストも開ける」を大きく1行。

### 8. 気軽に

- 載せる
  - Markdownで問題と解説を書く。
  - テストケースを置く。
  - 「公開する」を押せば完成。
- 図：問題を書いている画面を1枚。

### 9. しっかり

「作る」「確かめる」「開く」の3列にする。
口で説明するのは各列で1つにし、残りは名前だけ載せる。

| 列 | 説明する | 名前だけ |
|---|---|---|
| 作る | 入出力の生成と検証（テストケースを手で作らなくてよく、入力が制約を守っているかも機械で確かめられる） | スペシャルジャッジ、インタラクティブ、部分点、2ステップ形式、誤差ジャッジ |
| 確かめる | テスター（公開前に他の人に解いてもらえる） | |
| 開く | チーム戦 | 順位表の凍結、共同作成 |

「作る」は、AIbleCodeで整えきれなかった作問基盤への答えとして話す。

### 10. UIのこだわり

『UXデザインの法則』（Jon Yablonski著、オライリー・ジャパン）の2つの法則で、こだわりの理由を説明する。
こだわりの中身は広げない。

- ヤコブの法則：利用者は、ほかのサイトで慣れたやり方を期待する。だから、AtCoder、Codeforces、yukicoder、MojaCoder、MOFE、Zenn（Markdown）の、使っていて嬉しいところを組み合わせた。
- ヒックの法則：選択肢が多いほど、選ぶのに時間がかかる。だから、作問画面で一度に出す選択肢を絞り、しっかり側の設定は必要な人だけが開くようにした。
- 図：採点方式の切り替えの画面を2枚並べる。部分点採点を選んだときだけ、グループと配点の設定が出る。

### 11. 声にすぐ応える

- 載せる：要望 → AIに修正を頼む → テストとローカルでの目視 → CI/CDで出す、の流れ図。
- 口頭：WebとAPIはGitHub Actionsでテストを通す。ジャッジの配布は17枚目で話すので、ここでは触れない。
- 22枚目で、実際にその日に直せたことを答え合わせにする。

### 12. ジャッジシステムがむずかしそう（済）

- 口頭で足す：卒業制作ではJudge0に任せたが、今回は自分で作る。コンパイルは1提出につき1回にして全ケースで使い回し、言語とライブラリも自分で固定して入れる（11月23日の時点で、言語ガイドに32の環境がある）。
- 口頭で足す：OJは、他人が書いたコードを自分のサーバで動かすサービスである。

### 13. 構成を決めよう（案の比較）（済）

- スライドはFargate、Firecracker、最終案の3つのままでよい。
- 間にあったLightsail（9月11日〜29日、月10 USD）は、時間があれば口頭で触れる。

### 14. 構成を決めよう（EC2の運用）（済）

- 「コンテスト終了後10分後まで」を「終了の15分後まで」に直す。10分は、提出が来なくなった台が自分で止まるまでの時間である。
- 「コンテスト前30分前」を「コンテスト開始30分前」に直す。
- 「Saving Plan」を「Savings Plans」に直す。

### 15. 構成を決めよう（ioi/isolate）（済）

- 口頭で足す：提出とカーネルを共有するので、VMほど安全だとは言わない。

### 16. 構成を決めよう（インフラ構成）（済）

- 「ジャッジキュ－」の長音を「ー」に直す。
- 口頭で足す：再配信があっても、確定した結果は守る。

### 17. 安全：周りも固める

9月末ごろから企業の情報漏洩のニュースが相次ぎ、閉じ込めるだけでなく周りも固めた。
社名は出さない。

- 載せる
  - 採点台は外からの受信を持たない。運用はSSMで行う。
  - 認証情報は台に置かない。インスタンスロールから得る（9月29日）。
  - 受付を止めずにOS更新を配る（10月10日）。
  - GuardDuty（10月10日）とSecurity Hub（10月16日）で見張る。
- 口頭：OS更新の仕組みは、常時稼働の台にカーネルを含む25件のセキュリティ更新が溜まっていたのがきっかけ。配布は全言語の検証と本番への提出の確認まで済ませて完了とする。

### 18. 安全：よかった～

- そのあとPHPの脆弱性がニュースになった。閉じ込めてあるうえに、すぐ直して出せるので、よかった～となった。
- ShareOJの提出言語にPHPはないので、ShareOJでPHPを直した話にはしない。
- 件名やCVE番号を載せるなら、スライドを作るときに確認する。

### 19. 安定：先に台を起こす

14枚目の「開始30分前から増やす」の理由を話す。

- 載せる
  - 負荷を見てから増やすのでは間に合わない。起動してから採点を始められるまで数分かかる。
  - コンテストの開始時刻はDBに入っている。だから、時刻で先に起こす。
  - 見積もり：開始15分で参加者1人あたり約22秒分の採点が要ると仮定すると、100人で約5台。
- 見積もりは仮定に基づく。実際のコンテストの数字が取れたら差し替える。
- 予備の小ネタ：1割安いAMDのt3a.smallでは、GoやNimのコンパイルが上限を超え、通っていた提出がCEやTLEになったので、Intelのt3.smallにした。

### 20. やってみた：安全と安く

12枚目の3本柱を、実際の運用で確かめる。

- 安全：発表の時点までに提出が原因の事故があったかを確かめて書く。
- 安く：実際の月額を請求から確かめて載せる。目標は12枚目の月10,000円。ジャッジの部分だけの見積もりは約32 USD/月だった。

### 21. やってみた：安定

採点は詰まらなかった。
止まったのは別の場所だった、という話にする。

- 11月15日：コンテストが2つあった日の23時23分から22分間、サイトと採点が止まった。
  - 採点台は正常で、原因はDBだった。
  - 月18.25 USDを節約するために、DBをいちばん小さい大きさにしていた。その日はAPIの呼び出しがふだんの3〜4倍あり、ディスクの転送量の残高が尽きた。
  - 翌0時6分に一段大きいDBへ戻し、残高のアラームを加えた。
  - 「安く」と「安定」がぶつかった例として話す。
- 11月22日：コンテスト中に、画面の読み込みが約11,000回失敗した。
  - 順位表が、名前1つごとにAPIを呼んでいた。100行で84回になり、APIの同時実行の上限に当たった。
  - 当日の18時41分に、まとめて取得する形に直した。19時9分に上限も上げた。
- 11月23日以降のコンテストでどうだったかを確かめて足す。

### 22. やってみた：もらった声

- D問題で、サンプル以外の内部ケースを入れ忘れた事件があった。11月11日に、テストケースがサンプルだけの問題に警告を出すようにした。
- もらった声
  - UIが全体的に使いやすい。
  - コンテスト中にヘッダの「問題」を押すと、コンテストの問題一覧ではなく全体の問題一覧に飛んでしまう。
  - 他のジャッジより提出頻度の制限に引っかかりやすい。
- 声を受け取ったその日に直せた。11枚目の答え合わせとして短く触れる。
  - 例：提出頻度の制限を90秒に2回から60秒に2回へ緩めた（`49cbedd`、Claudeとの共同作成）。変更は制限値の1行と、テストとガイドだけ。
  - Webと採点基盤を分けているので、UIやAPIの修正はジャッジを止めずに出せる。

### 23. 今後の展望

- もらった声への対応を続ける。
- 継続して運営していく。ドメインを3年、Savings Plansを3年で契約したので本気である。4〜5枚目の「作問できる場所がなくなっていく」を受けて、なくならない場所にする、と結ぶ。
- GitHub Sponsorsなどで寄付を募りたいが、手続きが面倒でまだしていない。知見がある人は教えてほしい。質疑や発表後の会話のきっかけにもする。

### 24. 締め

- 使ってほしい、部にも来てほしい、で締める。一言は仮置き。
- サイトのURLを載せる。

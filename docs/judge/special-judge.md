# スペシャルジャッジ

問題編集画面の「生成・検証・判定」にある「判定方法」タブでスペシャルジャッジを選び、検証コードと言語を入力する。
検証コードは自動保存される。
テストケースの期待出力は空でもよい。
未公開の問題は同じ画面から解答を提出して試せる。
公開済みの問題は、問題管理で公開内容を更新するまで従来の公開設定で採点する。

## 検証コードのインターフェース

標準入力から提出プログラムの出力を読む。
コマンドライン引数には、次のファイルパスが順に渡される。
Javaの`args[0]`、Pythonの`sys.argv[1]`、CとC++の`argv[1]`が入力ファイルを指す。

1. テスト入力。
2. 期待出力。空の場合もファイルを作る。
3. 提出されたソースコード。
4. 書き込み可能なスコアファイル。初期状態は空で、集計コード方式の問題でだけ書いた値を読む（[部分点](#部分点)）。

標準出力は判定に使わない。
終了コード0はAC、非ゼロ終了とシグナル終了はWAとなる。
`assert`の失敗もWAとなるため、必要な条件をすべて検証する。
Javaの検証コードには`-ea`を指定してassertを有効にする。
入力の不足や余分な出力も作問者が検証する。
提出出力はバイト列を維持し、改行コードの変換や空白の除去を行わない。

たとえば、入力整数Nに対して、0以上N以下の任意の整数を正解とするPythonの検証コードは次のように書ける。

```python
import sys

with open(sys.argv[1]) as file:
    n = int(file.read())
values = sys.stdin.read().split()
assert len(values) == 1
x = int(values[0])
assert 0 <= x <= n
```

## 実行上限

| 対象 | 上限 |
| --- | --- |
| 検証コード | UTF-8で64 KiB。NUL不可 |
| コンパイル | CPU 30秒、経過40秒、1 GiB |
| ケースごとの検証 | CPU 5秒、経過16秒、512 MiB |
| 標準出力 | 16 MiB |
| 標準エラー | 64 KiB |
| 保存する検証診断 | 提出全体でUTF-8の先頭16 KiB |
| 集計コードの実行 | 提出ごとに1回。CPU 5秒、経過16秒、512 MiB |

コンパイル失敗と実行制限超過はJEとし、検証診断を記録する。
検証コードのバグと意図的な不正解判定は区別しない。
Javaのヒープ上限例外など、隔離環境のメモリ超過として検出されない異常終了もWAとなる。
提出プログラムがCE、TLE、MLE、OLE、REになった場合、そのケースの検証は実行しない。

本番ワーカーでは採点全体の経過時間を従来どおり1,800秒に制限する。
検証時間もこの予算に含むため、ケース数と各プログラムの実行時間によっては、全ケースが個別の上限以内でもJEになる。
部分点の問題では、1,500秒を過ぎたら残りのケースを実行せずに採点し、JEにしない。
開発用Dockerジャッジは提出と同様にC++17だけを提供し、検証には経過5秒の制限を使う。
CPU時間を用いる本番ジャッジとは計測条件が異なる。

診断ログは問題作成者自身の提出詳細に表示する。
第三者の提出結果や提出一覧には公開しない。
検証コード、期待出力、入力を提出プログラムの隔離環境へ置かない。

## 部分点

[ADR 0025](../adr/0025-score-partially-with-test-groups.md)の部分点の問題では、ジョブに`scoring`が付く。
`scoring`のないジョブは、スコアファイルの扱いと打ち切りを含めて従来どおり採点する。

### ジョブの形

```json
{
  "scoring": {
    "mode": "aggregate",
    "groups": [{"name": "小課題1", "points": 30}, {"name": "小課題2", "points": 70}],
    "aggregator": {"runtime": "cpp23-gcc", "source": "..."}
  },
  "cases": [{"name": "01", "isSample": false, "groups": ["小課題1", "小課題2"], "input": "...", "output": "..."}]
}
```

- `mode`は`groups`（グループ方式）か`aggregate`（集計コード方式）で、`aggregator`は`aggregate`でだけ指定し、省略できない。
- `groups`は1〜100個とする。
  名前は64文字以内で重ならず、配点は0〜1,000,000の整数、合計は1〜1,000,000とする。
- ケースの`groups`は、属するグループの名前を重複なく並べる。
  `null`と省略は所属なしとする。
- `easyTest`、`generate`、`validate`のジョブには付けられない。
- 集計コードの言語とソースの条件は検証コードと同じとする。

### 打ち切りと時間

- TLEの回数をグループごとに数え、2回出たグループを打ち切る。
  複数のグループに属するケースのTLEは、それぞれのグループで数える。
- 属するグループがすべて打ち切られたケースは実行せず、`SKIPPED`とする。
  どのグループにも属さないケースは必ず実行する。
- 開始から1,500秒を過ぎたら、残りのケースを`SKIPPED`とし、実行したケースで採点する。
- 提出全体のTLE2回による打ち切りは使わない。
- 判定と`passed`は、`SKIPPED`以外のケースから従来の規則で決める。

### ケースの点

集計コード方式でだけ、検証コードと対話用ジャッジからケースの点を読む。
読むのは判定がACかWAのケースだけで、それ以外のケースは点なしとする。

- legacy形式では、第4引数のスコアファイルを読む。
  前後の空白を除いて空なら点なし、0以上10の18乗以下の10進の整数ならその点とする。
  それ以外の内容、4 KiBを超えるファイル、通常のファイルでないものは、提出全体をJEにする。
- testlib形式では、引数の末尾に`/box/result -appes`を足し、testlibが書く結果ファイルを読む。
  終了コード7（`quitp`）で点が整数なら、ACとしてその点を付ける。
  testlibは整数の点を`37.0`のように書く。
  `quitf(_ok)`はAC、`_wa`などは従来どおりの判定とし、どちらも点なしとする。
  小数の点、`_pc`、形式の崩れた結果ファイル、256 KiBを超えるファイルは、提出全体をJEにする。
  結果ファイルの説明文は検証診断に入れ、標準エラーは解析しない。

### 集計コード

集計コードは、提出と検証コードのコンパイルの後、ケースを実行する前にコンパイルする。
全ケースの後に1回だけ、検証コードと同じ上限で実行する。
標準入力は次の形とする。

```text
N G
各グループの配点（G行）
判定 点 サンプル K g1 … gK（N行）
```

- 判定は`AC`、`WA`、`TLE`、`MLE`、`OLE`、`RE`、`SKIPPED`のいずれかとする。
- 点は10進の整数で、点なしは`-`とする。
- サンプルは`1`、それ以外は`0`とする。
- グループは、ジョブの`groups`の順に0から数えた番号を昇順に並べる。
- ケース名とグループ名は渡さない。

標準出力には、グループの順に得点をG個書き、空白か改行で区切る。
各得点は0以上そのグループの配点以下の10進の小数（例：`37.5`、`12`）とし、小数第3位以下を切り捨てる。
符号、指数表記、`.5`や`5.`のような省略、NaN、無限大は書式違いとする。
コンパイル失敗、実行時エラー、制限超過、数の個数の違い、書式違い、範囲外、64 KiBを超える出力は、提出全体をJEにする。
集計コードの標準エラーは検証診断に入れる。

グループ方式では、属するケースが1つ以上あり、そのすべてがACのグループに配点を与える。

### 結果の形

部分点のジョブの結果には`scoring`が付く。
`scoring`の値は、すべて得点を100倍した整数である。

```json
{
  "verdict": "WA",
  "passed": 1,
  "total": 2,
  "cases": [
    {"name": "01", "verdict": "AC", "score": 37, "cpuTimeMs": 1, "wallTimeMs": 2, "memoryBytes": 1024},
    {"name": "02", "verdict": "WA", "cpuTimeMs": 1, "wallTimeMs": 2, "memoryBytes": 1024}
  ],
  "scoring": {"score": 3750, "maxScore": 10000, "groups": [{"score": 3000, "maxScore": 3000}, {"score": 750, "maxScore": 7000}]}
}
```

- `scoring.groups`は、ジョブの`groups`と同じ順に並ぶ。
- ケースの`score`は、集計コード方式で点のあるケースにだけ付き、100倍しない整数である。
- CEの結果には、すべて0点の`scoring`を付け、JEの結果には付けない。

### bridgeでの確認と保存

bridgeは、得点の合計と範囲、`SKIPPED`のケースに計測値と点がないことを確かめる。
部分点のジョブでは`SKIPPED`をどの位置にも置けるので、ジョブのグループから位置を計算し直して照らし合わせる。
打ち切られたグループだけに属するケースは`SKIPPED`でなければならず、それ以外の`SKIPPED`の後は、すべてのケースが`SKIPPED`でなければならない。
グループ方式では、ケースの判定から各グループの得点を計算し直し、一致しない結果は保存しない。
合わない結果は結果キューで再試行され、最後は結果のDLQに入る。

部分点のジョブなのに`scoring`のない結果は、JE以外ならJEとして保存し、`platform`の`unscored_result`を記録する。
古いワーカーが部分点のジョブを一括方式で採点した場合が、これに当たる。
部分点でないジョブの結果は、`scoring`もケースの`score`も持てない。

保存する結果では、`scoring.groups`の各要素に、ジョブからグループ名`name`と、属するケースの位置`cases`（0から数える）を足す。
公開の提出詳細は`scoring`とケースの`score`を返し、提出一覧は`scoring.groups`を省く。
集計コードの標準エラーは`checkerLog`に入るので、検証診断と同じく公開しない。

サンプル検証のジョブには`scoring`を付けない。
集計コード方式の提出とリジャッジは、集計コードが公開中の言語でソースが空でないときだけ受け付ける。
ローカルのDocker判定は部分点の問題の提出を受け付けず、ジョブが届いてもJEにする。

## 保存と配置

下書きの`checker`は、通常判定なら省略または`null`、スペシャルジャッジなら`{"runtime":"cpp17","source":"..."}`とする。
編集中の空コードは保存できるが、公開と提出は受け付けない。
公開と提出の受付時に、検証言語が`GET /runtimes`で公開中か検証する。
受付後に言語の公開設定を変更しても、固定済みのジョブは固定したdigestで実行する。

DBマイグレーションは不要である。
旧ワーカーは検証設定を解釈しないため、[ランタイムの再構築と公開](runtime-rollout.md)に従って受付とdispatchを停止し、待機中の提出を処理してから配置する。
ワーカー更新後にsmoke testを行い、新しいdigestをbridgeとAPIへ反映してから受付を再開する。
Webも更新し、API経由でAC、WA、JEと作問者以外へのログ非公開を確認する。

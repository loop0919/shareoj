# 誤差ジャッジ

[ADR 0037](../adr/0037-support-error-judge.md)に従い、通常判定の比較を、数のトークンだけを誤差の条件で比べる比較に替える。
提出の実行と資源上限は通常判定と同じで、検証コードは実行しない。
実機での検証は、まだ行っていない。
開発用Dockerワーカーは誤差ジャッジの提出を受け付けない。

## 作問と保存

問題編集画面の判定方法で「誤差ジャッジ」を選び、「種類」「許容誤差」「判定の余裕」を入力する。
初期値は、種類が「絶対誤差または相対誤差」、許容誤差が$10^{-6}$、判定の余裕が0.1%である。
下書きには`errorJudge`を保存する。

```json
{"mode": "either", "epsilon": "1e-6", "marginPercent": "0.1"}
```

- `mode`は`absolute`（絶対誤差）、`relative`（相対誤差）、`either`（絶対誤差または相対誤差）のいずれか。
- `epsilon`は`"1e-1"`から`"1e-12"`までの12個の文字列のいずれか。
- `marginPercent`は判定の余裕（εに対する%）で、省略と`null`は0.1として扱う。
  指定する場合は、正規表現`^[0-9]{1,3}(\.[0-9]{1,6})?$`に合い、値が0以上100以下の文字列とする（例：`"0"`、`"0.5"`、`"12.345678"`）。
  指数表記と符号は受け付けない。
  `null`は省略として保存する。
- `checker`、`interactor`、`runTwice`、`errorJudge`は、同時に2つ以上を指定できない。
  すべてなければ通常判定とし、生成用と入力検証用のジョブには`errorJudge`を指定しない。

形の誤りは下書きの保存時に拒否する。
コードを持たないので、公開準備の指摘は増やさない。
Webは、判定の余裕の入力が形に合わないあいだ、しきい値の代わりに誤りを表示し、下書きを保存しない。

公開と提出の受付時に、`errorJudge`をテストケースと一緒に固定し、ジョブにも同じ形で載せる。
リジャッジ、サンプル検証（`easyTest`）、部分点（グループ方式と集計コード方式）は、通常判定と同じく使える。
サンプル検証では、通常判定と同じく入力、期待出力、実際の出力（`sampleDetails`）を返す。
問題の公開APIは`errorJudge`の`mode`と`epsilon`だけを返し、`marginPercent`は返さない。
問題ページとコンテストの問題ページには、「誤差ジャッジ：絶対誤差または相対誤差が$10^{-6}$以下なら正解です。」のように種類とεを表示し、余裕は表示しない。

CLIでは、`problem.toml`の`[error_judge]`に`mode`、`epsilon`、`margin_percent`を文字列で書く。
`margin_percent`は省略できる。
`[checker]`、`[interactor]`、`[run_twice]`、`[error_judge]`は2つ以上を同時に指定できず、`push`は指定した1つ以外の判定方法をリモートの下書きから消す。

## 比べ方

提出の出力と期待出力を、通常判定と同じ6バイト（スペース、`\t`、`\n`、`\r`、`\v`、`\f`）で区切ってトークンに分ける。

1. 両方のトークンを数える。
   数が違えばWAとし、数の比較をしない。
2. 同じ位置のトークンを先頭から1組ずつ比べる。
   不一致の組があればそこでWAとし、すべて一致すればACとする。

1組は、次の順に判定する。

1. バイト列として同じなら一致。
2. どちらかが400バイトを超えるなら不一致。
3. 両方が[数](#数の形)なら、[条件](#条件)で比べる。
4. それ以外は不一致。

数として読めないトークンは、NULや不正なUTF-8を含んでも、バイト列として比べる。

### 数の形

次の形にトークン全体が合うものだけを数とする。
数字はASCIIの`0`〜`9`だけである。

```text
-?(数字+ | 数字+.数字* | .数字+)([eE][+-]?数字+)?
```

- 例：`3`、`-0.5`、`2.`、`.25`、`1e-3`、`6.02E+23`。
- 先頭の`+`、16進（`0x10`）、`1_000`、`nan`、`inf`、`infinity`、全角の数字は数としない。
  これらは文字列として完全一致だけを認める。
- 400バイトを超えるトークンと、指数の絶対値が400を超えるトークン（`1e401`、`1e-401`）は数としない。
  指数の値は先頭の0を除いて読むので、`1e-0400`は数である。
- 整数も数である。
- 値で比べるので、`1e3`と`1000`、`2.`と`2`、`-0`と`0`は同じ値として扱う。

### 条件

提出の値を$a$、期待出力の値を$b$、εを許容誤差、$m$を判定の余裕（%）とする。

$$T = \varepsilon \times \left(1 + \frac{m}{100}\right)$$

| 種類 | 一致の条件 |
| --- | --- |
| 絶対誤差 | $\lvert a - b \rvert \le T$ |
| 相対誤差 | $\lvert a - b \rvert \le T \times \lvert b \rvert$ |
| 絶対誤差または相対誤差 | 上のどちらかを満たす |

- εが$10^{-6}$で$m$が0.1なら、$T$は$1.001 \times 10^{-6}$になる。
- 相対誤差で$b$が0のときは、$a$も0の場合だけ一致する。
- 期待出力`0`に対しては、`0.0`と`-0`も一致する。

### 判定の余裕

真の値を$x$、期待出力と$x$の差を$\delta$とする。
$x$との誤差がε以内の解答は、期待出力から最大で$\varepsilon + \delta$離れる。
絶対誤差では、$\delta \le \varepsilon \times m/100$ならこの解答も一致する。

| 判定の余裕 | 吸収できる$\delta$ |
| --- | --- |
| 0.1%（初期値） | εの1,000分の1まで |
| 1% | εの100分の1まで |
| 0% | なし（期待出力が正確な場合だけ） |

相対誤差では、期待出力の誤差を$x$に対する比$\rho$（$\lvert b - x \rvert \le \rho \lvert x \rvert$）で考える。
$x$に対する相対誤差がε以内の解答が必ず一致するのは、$\rho \le (\varepsilon \times m/100) / (1 + T)$のときである。
εが$10^{-6}$なら、表の値との違いは$10^{-6}$程度の割合である。

### 正確な計算

比較は、トークンの10進表記を正確な値として計算する。
誤差が$T$以下なら必ず一致し、$T$をわずかでも超えれば不一致になる。
結果は、有理数（`fractions.Fraction`）だけで計算した場合と同じになる。

実装は、Pythonの`decimal`を、1,610桁の精度で使う。
数は、400桁以下の整数と$10^{-800}$以上の10のべき乗の積で、絶対値は$10^{800}$未満である。
このため、2つの数の差は1,601桁以下、しきい値（9桁以下）と数の積は409桁以下で表せ、この精度では丸めが起きない。
丸めと不正な演算は例外にする設定なので、万一丸めが起きても判定を出さず、提出はJEになる。
浮動小数点での前段の判定は使わず、数の組はすべてこの計算で比べる。

## 速さ

比較は、隔離環境の外の管理ワーカーの中で、1スレッドで動く。
提出のCPU時間には含まれないが、採点全体の経過時間の上限（1,800秒）には含まれる。
部分点の問題では、1,500秒を過ぎると残りのケースを実行しない。

提出が比較を引き延ばせないように、次の3つで量を抑える。

- 数の比較を始める前に、トークンの数を数える。
  数えるのは区切りの位置だけで、トークンを数として読まない。
  数が違えばそこでWAとするので、正確な計算の回数は期待出力のトークン数で決まる。
- 1組の計算の大きさは、トークンの上限（400バイト、指数±400）で抑える。
- 出力を16 KiBずつ読み、トークンの列をまとめて作らない。
  1つのトークンが大きい場合も複製しない。
  比較中の追加のメモリは、出力の大きさに比例しない。

開発機（Core i7-14650HX、WSL、Python 3.12）での実測は次のとおりである。

| 比べた出力 | 時間 |
| --- | --- |
| 期待出力`0`が100万個、提出`0.000001001`が100万個（絶対誤差、ε $10^{-6}$、余裕0.1%、すべてしきい値ちょうど） | 約1.1秒 |
| 期待出力`0`が約420万個（8 MiB）、提出`0.0`が同数 | 約4.5秒 |
| 期待出力が1個、提出`1.0`が200万個（トークン数が違う） | 約0.01秒 |

設計では、しきい値ちょうどの100万組を採点ホストで5秒以内に比べることを目安とした。
採点ホストでの値はまだ測っていない。
配置時の実機検証で、`smoke.py`がしきい値ちょうどの組を100万組比べる時間を、レポートの`toleranceMillionPairsMs`に記録する。
合否の条件にはしない。
測った値は、この節と作問者向けのガイドに書く。

期待出力は16 MiBまでなので、トークンは最大で8,388,608個になる。
期待出力に数が数百万個あると、採点ホストでは1ケースの比較に数十秒かかり得る。
作問者向けのガイドには、時間がかかることと、採点全体の上限に含まれることを書く。

## 結果の印

ワーカーは、誤差ジャッジのジョブの結果に`"errorJudge": true`を付ける。
CEの結果にも付け、JEの結果には付けなくてもよい。

誤差ジャッジを知らない旧ワーカーは`errorJudge`を無視し、完全一致で採点する。
正しい解答が、期待出力と桁数が違うだけでWAになる。
このため、bridgeは誤差ジャッジのジョブの印のない結果を、JE以外ならJEとして保存し、`platform`の`unmarked_error_judge_result`を記録する。
2ステップ形式の`unmarked_run_twice_result`と同じ仕組みである。
誤差ジャッジでないジョブの結果が印を持つ場合は、不正な結果として保存しない。

bridgeは印を確かめてから取り除くので、保存する結果とAPIの応答には現れない。

## 配置

旧ワーカーは`errorJudge`を解釈せず、旧bridgeは`errorJudge`をジョブに載せない。
APIだけを先に配置すると、誤差ジャッジの問題への提出が旧bridgeを通り、完全一致の結果がそのまま保存されてしまう。
新しいbridgeとワーカーは、`checker`、`interactor`、`runTwice`、`errorJudge`のうち2つ以上を持つジョブをJEにする。
ワーカーのコード（`host.py`、`tolerance.py`、`smoke.py`）が変わるので、runtime digestも変わる。
DBマイグレーションは不要である。

新しいWebは、下書きを保存するたびに`errorJudge`を送る。
旧APIは知らない項目のある下書きを拒否するので、WebをAPIより先に配置すると、作問画面で下書きを保存できなくなる。

配置は[配布と検証の定型コマンド](deployment-checks.md#通常は統合コマンドを使う)に従い、次の順で行う。
[2ステップ形式](run-twice.md#配置)がまだ配置されていなければ、同じ配布にまとめてよい。

1. 誤差ジャッジを含むコミットからワーカーとbridgeの配布物を作り、`judge/rollout.py run`で配布する。
   `run`はbridgeを更新し、新しいdigestをAPIとbridgeの設定へ同期する。
   `state.json`が`status: passed`と`step: complete`になるまで完了させる。
2. そのコミットを`main`へ入れてpushする。
   GitHub Actionsが、API、Webの順に配置する。

`main`へのpushはAPIを自動で配置するので、手順1が終わるまで、誤差ジャッジを含むAPIの変更を`main`へpushしない。

配置の後にワーカーを誤差ジャッジのない版へ戻すと、[結果の印](#結果の印)がないので、誤差ジャッジの提出はJEになる。
新しい版へ戻した後に、それらの提出をリジャッジする。
bridgeも誤差ジャッジのない版へ戻すと、ジョブに`errorJudge`が載らず、印も確かめないので、完全一致の結果がそのまま保存される。

`rollout.py run`の実機検証では、`smoke.py`の部分点の検証の後に、誤差ジャッジの検証が次を確かめる。
CPython 3.14の検証が通ったときに実行する。
条件はε $10^{-6}$、余裕の指定なし（$T = 1.001 \times 10^{-6}$）とする。

| 種類 | 期待出力 | 提出の出力 | 結果 |
| --- | --- | --- | --- |
| 絶対誤差 | `0` | `0.000001001`（誤差が$T$ちょうど） | AC |
| 絶対誤差 | `0` | `0.0000010011` | WA |
| 相対誤差 | `1000` | `1000.001001`（誤差が$T \times 1000$ちょうど） | AC |
| 相対誤差 | `1000` | `1000.0010011` | WA |
| 絶対誤差または相対誤差 | `0` | `0.000001001` | AC |
| 絶対誤差または相対誤差 | `1000` | `1000.001001` | AC |
| 絶対誤差または相対誤差 | `0` | `0.0000010011` | WA |
| 絶対誤差または相対誤差 | `1000` | `1000.0010011` | WA |

どの結果にも印が付いていることも確かめる。
1つでも合わなければ、smokeはすべての言語を不合格として報告し、配布は完了しない。

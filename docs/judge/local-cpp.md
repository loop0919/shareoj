# ローカルでC++を提出する

公開問題のページからC++17のソースコードを提出し、`/my/submissions`で自分の結果を確認できる。
ログインとプロフィール登録が必要になる。
ソースコードは128 KiBまでとし、提出後のコードと結果は本人だけが閲覧できる。

この実装は、Lightsailとisolateによる本番版に先立って提出から採点までを確認するローカル開発用である。
APIとは別のGoワーカーがPostgreSQLから順番に提出を取得し、Dockerでコンパイルと実行を行う。
このローカルワーカーはOutboxとSQSには接続しない。
ファイル参照を使うテストとジェネレータには、APIと共通の開発用`TEST_DATA_BUCKET`とAWS認証情報を設定する。

## 起動する

Docker Engineが起動しているLinux環境で、リポジトリのルートから実行する。
Dockerを操作できるユーザーで`make dev`を起動する。

```console
docker pull gcc:14.2.0
export JUDGE_CPP_IMAGE="$(docker image inspect --format '{{.Id}}' gcc:14.2.0)"
make dev
```

`JUDGE_CPP_IMAGE`にはタグではなく、取得したイメージの`sha256:`から始まるIDを設定する。
提出時にイメージIDを保存するため、後でタグが変わっても既存提出の環境は変わらない。
コンパイル引数は`g++ -std=c++17 -O2 -pipe`で固定している。
このコマンドや実行条件を変更する場合は、`cpp17-local`とは別のランタイム識別子を追加する。

`JUDGE_CPP_IMAGE`を設定すると、`make dev`がAPIとフロントエンドに加えてワーカーも起動する。
Ctrl+Cでまとめて停止できる。
開発用DBにはマイグレーション009までが自動適用される。
外部DBの場合は、従来どおり`api/`から`go run ./cmd/migrate`を実行する。
未設定時も公開問題は閲覧できるが、提出要求には503を返す。

## 採点用テストを登録する

問題作成画面のサイドバーで「テストケース」を選び、「テストケースを追加」を押す。
各ケースの入力と期待出力を入力する。
ケース名は64文字まで設定でき、同じ問題内で指定した名前の重複は許可しない。
名前を省略した既存ケースも編集できる。
入力と期待出力は左右の行番号付きエディタで編集し、狭い画面では縦に並べる。
ファイル名の一覧は入出力共通で、選択したケースの入力と期待出力が同時に切り替わる。
名前変更と削除も入出力の組を単位として行う。
空の入力と期待出力も有効なケースとして登録できる。
個別の「削除」、問題管理の「一括削除」で不要なケースを削除できる。

変更は問題文と一緒に自動保存される。
保存ボタンとCtrl+S / ⌘Sも利用でき、再読み込みすると保存済みのケースを復元する。
「問題管理」から「公開する」または「公開内容を更新」を押すと、保存したケースを採点に反映する。
ケースの編集中も、公開内容を更新するまでは以前の公開版で採点する。

ケース数はTLに関係なく0〜100件、各入力と期待出力はそれぞれ64 KiB、全ケースの合計は256 KiBまでとする。
本番版の16 MiB対応は[S3保存](large-test-files.md)を使うため、このローカルワーカーの対象外である。
サイズはUTF-8のバイト数で検査する。
NUL文字は受け付けない。
ケースが0件の問題も保存と公開はできるが、その問題への提出は409で拒否する。

ケースの入出力は作成者の認証付き問題APIだけが返す。
公開問題の本文とAPIには含めない。
入力例を読者へ見せたい場合は、問題文にも記載する。

提出時に、公開済みのケース、コード、イメージID、問題の版、制限値を同じDB操作で固定する。
受付済みの提出は、その後に問題やケースを編集しても採点条件が変わらない。
旧実装の`JUDGE_TEST_DIR`と手動JSONファイルは使用しない。
以前ファイルで登録したケースは、この画面から登録して公開内容を更新する。
本番では[ADR 0003](../adr/0003-store-test-sets-in-amazon-s3.md)に従ってテスト本体をS3へ移す。

## 実行条件と結果

コンパイルは一度だけ行い、成果物を読み取り専用で各ケースへ渡す。
ケースごとに新しいコンテナを起動するため、プロセスと作業ファイルは持ち越さない。
コンパイル時も実行時も、外部ネットワークを無効にし、非rootユーザーで実行する。
期待出力、DB接続情報、テストファイルのディレクトリはコンテナへ渡さない。

| 項目 | ローカル版の値 |
| --- | --- |
| CPU | 1 CPU相当の上限 |
| コンパイル | 起動を含め30秒、1536 MiB、成果物32 MiBまで |
| 実行時間 | 問題の時間制限をコンテナ内の`timeout`で適用 |
| 実行メモリ | 問題のメモリ制限（64〜1024 MiB）、追加swapなし |
| 標準出力 | 16 MiBまで |
| 標準エラー | 64 KiBまで |
| プロセス数 | コンテナ全体で64まで |
| 一時領域 | ケースごとに128 MiBのtmpfs |
| 採点全体 | 5分まで。超過時はJE |

この試作では、既存の問題画面に設定されたメモリ制限を使用する。
本番向けに決定した「ユーザープロセス群512 MiB」とは異なる。
tmpfsや`timeout`もコンテナのメモリ制限に含まれるため、本番の言語間比較や性能評価には使わない。
実行時間と最大メモリ使用量の数値表示は未実装である。

標準出力と期待出力はASCII空白で区切ったトークン列として比較する。
末尾改行や空白の数は無視するが、`1`と`1.0`、`Yes`と`YES`は異なる。
最初の失敗で採点を終了し、全ケースが成功した場合だけACとする。
返す判定はAC、WA、CE、RE、TLE、MLE、OLE、JEである。
部分点の問題（[ADR 0025](../adr/0025-score-partially-with-test-groups.md)）は、サンプル検証を除いて提出を受け付けない。
Dockerが記録したOOMをMLEとし、Dockerの起動失敗や状態取得失敗はJEとする。

結果画面は2秒ごとに取得し、採点が完了したら更新を止める。
コンパイル診断は表示するが、ケースの入力、期待出力、標準出力、標準エラーは返さない。
提出履歴には最新50件を表示する。

## 中断時の扱いと制限

待機中の提出はDBに残り、ワーカー再起動後に処理を再開する。
実行中のまま中断した提出は、ワーカーが動いていれば開始から10分後にJEへ変更する。
自動再採点と再送の冪等性は未実装なので、提出要求の通信が切れた場合は履歴を確認してから再提出する。
同じ結果を重複して保存しても、完了済みの結果は上書きしない。

ローカル版ではコンパイルと各ケースで別々のコンテナを使う。
本番は[Lightsail上のisolateワーカー](../../judge/README.md)を使用し、ローカル版の計測値とは区別する。
このワーカーを公開サービスの実行基盤として有効にしない。

## 検証する

Nix開発シェルの`api/`で実行する。
DBテストは一時スキーマを作成し、終了時に削除する。

```console
TEST_JUDGE_CPP_IMAGE=gcc:14.2.0 go test ./internal/submissions -v
TEST_DATABASE_URL='postgresql://openoj:openoj-local@127.0.0.1:15432/openoj?sslmode=disable' go test -race ./...
```

Dockerの設定は[コンテナ実行オプション](https://docs.docker.com/reference/cli/docker/container/run/)と[リソース制限](https://docs.docker.com/engine/containers/resource_constraints/)に従う。

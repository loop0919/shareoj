# ADR 0032: 作問の生成と検証を提出と別の枠で数え、空きがあるときに送る

- 状態：Accepted
- 決定日：2026-10-24
- 範囲：入力生成・出力生成・入力検証の受付回数、採点の送り出しの順番
- 一部変更：[ADR 0019](0019-rejudge-submissions.md)の、新しい提出を先に送る決定（作問の処理は新しい提出の後ろ、リジャッジの前に送る）

## 背景

作問画面の入力生成・出力生成・入力検証は、通常提出・コンテスト提出と同じ「60秒に2回」の枠で数えていた。
作問では「入力生成→出力生成→入力検証」と続けて使い、そのあと解答を提出して確かめる。
3回目の操作で枠を使い切り、同じ枠の提出もできなくなるので、制限を緩めてほしいという要望があった。

作問の処理は、TLEが2件出ても打ち切らず、全ケースを実行する。
1回で最大100件、各ケース5秒まで実行するので、1回で8分を超えることがある。
採点台は1台につき同時に1件ずつ処理し、平常時はprimaryの1台だけが動く（ADR 0012）。
送り出しは受け付けた順なので、枠の回数を増やすだけでは、作問者1人の処理の後ろで参加者の提出が待たされる。

## 決定

### 作問の3操作を、提出とは別の枠で60秒に3回まで受け付ける

入力生成、出力生成、入力検証は、合わせて直近60秒で3回まで受け付ける。
通常提出とコンテスト提出の「60秒に2回」、サンプル検証の「60秒に3回」とは別に数え、互いの枠を消費しない。
3回あれば、入力生成、出力生成、入力検証を1分の中で続けて使える。

超過時の応答は提出と同じく429と`submission_rate_limited`で、画面では「生成と検証の頻度制限」と示す。

### 作問の処理は、新しい提出の後ろ、リジャッジの前に送る

送り出しの順番は、新しい提出、作問の処理、リジャッジの順にする。
作問の処理は、リジャッジと同じく、SQSにある採点と採点中の採点が合わせて2件未満のときだけ送る。
新しい提出の前に並ぶ作問の処理とリジャッジは、合わせて多くても2件になる。

作問者は結果を見てから次の操作に進むので、あとでまとめて結果を見るリジャッジより先に送る。

増設台の起動判定は変えない。
作問の処理は、リジャッジと違い、これまでどおり滞留の判定に数える。
作問者が画面で結果を待っているからである。

## 代替案

- **共通の枠の回数を増やす**：変更は1行で済む。ただし、作問者が重い処理を参加者の提出より前に積めるようになる。作問中に提出の枠が減ったままなのも変わらないので採らなかった。
- **作問の処理を1人1件ずつに限る**：前の結果を見て次へ進む使い方に合い、処理の重さにも自然に合う。ただし、ほかの枠はすべて時間で数えている。また、終わらない処理が残ると、期限切れの6時間後まで次を受け付けられなくなる。送り出しを後ろに回せば提出は守れるので採らなかった。
- **作問の処理をリジャッジの後ろに送る**：問題の全提出をリジャッジしている間、作問者が操作のたびに長く待つので採らなかった。

## 影響

- 作問者は、1分の中で作問の3操作と提出2回を両方使える。1人が1分に受け付けられる採点は、サンプル検証を含めて最大8件になる。
- 提出が続くと、作問の処理は空きができるまで待つ。コンテスト中に作問すると、結果が出るまで時間がかかる。画面は1時間で結果の確認を打ち切る。
- 作問の処理はリジャッジより先に送るので、作問が続くとリジャッジの完了が遅れる。
- [ADR 0031](0031-run-code-without-problem.md)（Proposed）の送り出しの順番には、作問の処理が入っていない。コード実行を実装するときに、作問の処理との順番を決める。

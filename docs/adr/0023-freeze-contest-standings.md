# ADR 0023: 順位表を凍結し、結果を公開するまで凍結後の提出を伏せる

- 状態：Accepted
- 決定日：2026-10-18
- 範囲：順位表の凍結の設定、一般向けとスタッフ向けの順位表、コンテストの提出と解いた人数を公開する条件、凍結の解除
- 一部変更：[ADR 0016](0016-anonymize-deleted-accounts.md)の「開催予定・開催中の自分のコンテストがある間は、削除を受け付けない」（退会を断る条件を広げる）と、背景の「終了したコンテストの順位表には、参加者全員の結果が載る」

## 背景

ICPC形式のコンテストでは、終了前の一定時間に出た提出の結果を順位表に出さず、終了後に発表することが多い。
この仕組みを順位表の凍結と呼ぶ。
ShareOJの順位表には、凍結の仕組みがなかった。

順位表は提出から都度集計し、公開の経路1本で、閲覧者に関係なく同じ表を返している。
開催中にほかの人の提出と判定を見られるのはスタッフだけで、スタッフは順位表の対象外である。
終了すると、コンテストの提出一覧、終了時に公開される問題のページの提出一覧、問題の解いた人数などが、それぞれ独立に終了を条件として結果を公開する。
凍結を順位表だけに入れても、これらの箇所から凍結後の判定を集めれば、順位を組み立て直せる。

ICPCのコンテストシステムの要件（CCS）とDOMjudgeは、凍結を次のように扱っている。

- 凍結後の提出は、凍結した順位表で判定待ちとして件数だけを出す。
- 管理者や審判の画面では、凍結しない最新の順位表を見られる。
- 凍結の対象は提出時刻で決め、凍結前の提出が後から判定されれば一般の順位表にも反映する（DOMjudge）。
- 判定の済んでいない提出が残る間は、結果を確定できない（CCS）。
- 解除は、設定した時刻か手動の操作で行う（DOMjudge）。
- チームが見る自分の行は凍結後も更新し、順位を「?」と出す（DOMjudge）。

## 決定

### 凍結の長さをコンテストごとに設定する

コンテストの設定に、終了の何分前から順位表を凍結するかを加える。
値は「なし」か、1分からコンテスト時間までの分数とする。
下書きでも公開済みのコンテストでも設定でき、開始後は変えられない。
開始後に変えられると、どの提出の結果を伏せるかが競技の途中で変わるためである。

凍結の対象は、終了のN分前から終了までに作られた提出とする（Nは設定した分数）。
この提出を、以下**凍結後の提出**と呼ぶ。
終了後の練習の提出は含めない。
判定がいつ終わったかは問わず、凍結前の提出の判定とリジャッジは、凍結中でも一般向けの順位表に反映する。
判定の完了時刻で決めると、同じ時刻の提出でも、採点の混み具合によって伏せるかどうかが変わるためである。

### 結果確定の時点を定める

凍結のあるコンテストでは、終了しても凍結後の提出の結果を見せず、凍結を解除した時点で見せる。
この時点をコンテストの**結果確定**とする。
凍結のないコンテストでは終了の時点が結果確定であり、今の動きは変わらない。

結果確定は、ほかの機能でも期間の境として使う。
共同作成者の招待を受けられる期間、参加者がスタッフになれない期間、セッターにテスターと同じ権限を与える期間（[ADR 0022](0022-share-contests-among-setters.md)）、セッターがチーム名とオンサイト区分を直せる期間（[ADR 0024](0024-team-and-onsite-participation.md)）、コンテストに入っている問題の保存に内容の条件を求める期間（[ADR 0025](0025-score-partially-with-test-groups.md)）は、どれも結果確定までとする。

### 凍結後の提出は、結果確定まで行ごと見せない

凍結後の提出は、結果確定まで、本人、チームメイト、スタッフ以外には一覧にも詳細にも出さない。
判定だけを伏せて行を残すことはしない。
提出の状態、採点途中の最悪の判定、通過したケースの数、実行時間、リジャッジの時刻、ソースコードのどれからも、判定を推し量れるためである。

凍結前の提出と終了後の練習の提出は、これまでどおり終了時に公開する。
凍結前の提出の結果は凍結した順位表ですでに公開しているので、伏せても守れるものがない。
したがって、コンテストの提出を一般に公開する条件は、「コンテストが結果確定している、または、コンテストが終了していてその提出が凍結後の提出でない」となる。

### 終了で結果を公開していた箇所を、すべてこの条件に置き換える

これまで終了を条件に結果を公開していた箇所は、すべて前節の条件に置き換える。
対象は次の箇所である。

- コンテストの提出一覧と提出詳細、コンテストの問題ごとの提出一覧
- 終了時に公開される問題のページの提出一覧と提出詳細
- 提出のURL単体での表示
- 問題一覧と問題詳細の解いた人数
- コンテストの提出一覧を見られるかを画面に伝える項目と、公開APIの説明文

条件は1か所で定義し、これらの箇所はすべてそれを使う。
箇所ごとに条件を書き写すと、1か所の直し漏れが、そのまま終了直後の結果の漏れになるためである。

解いた人数は、凍結後の提出を結果確定まで数えない。
一方、本人の「解いた」の印（問題一覧のAC済みと、コンテストの解いた印）は、凍結に関係なく本人の結果で決める。
凍結中に解いた問題が、結果確定まで本人の画面で未解決に見えることを避けるためである。
チーム戦のコンテストの解いた印は、同じ理由で、凍結に関係なくチームの結果で決める（ADR 0024）。

### 一般向けの順位表は、凍結前の提出だけで計算する

公開の順位表は、凍結前の提出だけで計算する。
凍結後の提出は、判定に関係なく、セルに件数だけを「?3」のように出す。
件数にはCE、JE、判定待ちも含め、凍結前に満点を取った問題では数えない。
今の順位表の数え方（CEとJEを数えず、最初のACより後も数えない）で件数を出すと、件数の差からCEやACがあったことが分かる。
満点を取った問題を数えないのは、その後の提出が順位に影響しないためである。

APIでは、この件数を判定待ちの件数とは別の項目で返す。
DOMjudgeは両者をまとめて判定待ちとして出すが、まとめると、判定の済んだ提出まで画面に「判定待ち」と出る。
部分点の問題（ADR 0025）では、凍結前の提出から得た得点、時刻、誤答だけを出す。
結果確定の後は、公開の順位表もすべての提出で計算する。

### 凍結なしの順位表は、スタッフ全員が非公開の経路で見る

スタッフ（セッター、コンテストの問題の作者、テスター。ADR 0022）は、全員が凍結なしの順位表に切り替えて見られる。
スタッフは開催中からコンテストの全提出の判定を見られ、作者とテスターはリジャッジもできる。
順位表だけをセッターに限っても、作者とテスターは提出一覧から最新の順位を組み立てられる。
参加者は結果確定までスタッフになれない（ADR 0022）ので、参加者がテスターの招待を受けて凍結なしの順位表を見ることはない。

凍結なしの順位表は、スタッフ専用の非公開の経路（`/my/contests/{id}/standings`）でだけ返す。
公開の経路（`/contests/{id}/standings`）は、閲覧者が誰でも凍結した表を返す。
1つの経路で閲覧者を見て切り替えると、閲覧者の判定かWebサーバーの中継に誤りが1つあるだけで、凍結なしの表が一般に出るためである。

画面の既定の表示は、スタッフにも凍結した表とし、スタッフにだけ凍結なしへの切り替えを出す。
会場で順位表を映すとき、スタッフの画面から凍結なしの表が出ないようにするためである。

### 参加者の順位表の行も凍結する

参加者は、凍結中も自分（チーム戦ではチーム）の提出の結果を、提出一覧と提出詳細で見られる。
順位表では、自分の行も凍結した表示のままにする。
自分の結果は提出一覧で分かるので、順位表は誰に対しても同じ表にする。

### 終了後に、セッターか運営者が結果を公開する

凍結は、終了後にセッターか運営者（`OPERATOR_SUBJECTS`）が「結果を公開」を押したときに解除する。
参加者の開催時間中の提出に判定待ち（リジャッジ中を含む）が残っている間は押せない。
判定の済んでいない提出を残したまま発表すると、発表した後に順位が動くためである。
凍結前の提出も、判定が済めば順位表が動くので待つ。
スタッフの提出と終了後の練習の提出は順位表に載らないので待たない。

結果の公開は取り消せない。
一度公開した結果は、伏せ直しても、すでに見た人からは取り戻せないためである。

自動では解除しない。
解除する人がいなくなって凍結が残り続けることは、次の2つで防ぐ。

- 凍結があり結果確定していないコンテストで、最後に残ったセッターは退会できない。
- 運営者が解除できる。

運営者の操作は、セッターが押せない事情への備えであり、運営者が終了したコンテストを見回ることは前提にしない。

### 凍結していることをコンテストのページに示す

順位表が動かないことを閲覧者が不具合と取り違えないように、凍結の状態を公開する。
公開のコンテストの情報に、凍結を始める時刻と、結果を公開したかどうかを載せる。
開始前の概要には「終了N分前から順位表を凍結します」と出す。
凍結中と、終了後で結果を公開する前は、順位表の上に「HH:MM以降の提出の結果は、結果発表まで伏せています」と出す。

## 代替案

凍結なしの順位表をセッターだけに見せる案は採らない。
作者とテスターは提出一覧で全提出の判定を見られるので、順位表だけを限っても結果は伏せられない。
伏せるには、作者とテスターにも凍結後の提出の判定と採点の進み具合を見せず、作者への初AC通知も止める必要がある。
そうすると、凍結中に見つかったテストケースの誤りを、テスターが確かめてリジャッジすることができなくなる。

コンテストの提出をすべて結果確定まで伏せる案は採らない。
凍結前の提出の結果は凍結した順位表で公開済みなので、伏せても守れるものがない。
結果を公開しないままのコンテストでは、提出が非公開のまま残り、問題ページの提出一覧と解いた人数からもコンテストの分が抜け続ける。

終了から一定の日数（例：7日）が過ぎたら自動で結果を公開する案は採らない。
結果を発表する時点はセッターが選ぶもので、明示的な操作でだけ公開する。
解除する人がいなくなる問題は、退会の制限と運営者の操作で防げる。

参加者が見る自分の行だけを凍結せず更新する案（DOMjudgeの方式）は、今回は採らない。
公開の順位表が閲覧者ごとに変わり、閲覧者によらず同じ表を返す公開の経路では返せない。
自分の行だけを最新にしても、凍結したほかの行と比べた順位は出せない（DOMjudgeも順位を「?」と出す）。
自分の結果は提出一覧と提出詳細で分かるので、順位表で見せる必要は小さい。

## 影響

- `contests`に、凍結の長さと結果を公開した時刻を持たせる。
  APIはマイグレーションより先に配布されるので、マイグレーションだけのコミットを先にpushする。
- 公開の`Contest`に凍結を始める時刻と結果を公開したかどうかを足し、順位表の各セルに凍結後の件数を足す。
- 順位表のAPIは配列のまま、項目を足すだけにする。
- 順位表の計算は、チーム戦（ADR 0024）と部分点（ADR 0025）の変更と合わせて一度だけ作り直す。
- 非公開の経路`/my/contests/{id}/standings`を足す。
- Webサーバーは、スタッフが凍結なしの表示を選んだときだけ、順位表の要求を非公開の経路へ送る（今は常に公開の経路へ送っている）。
- 結果を公開する操作は、開始後の変更を拒むコンテストの保存とは別のAPIにする。
  判定待ちが残っているときに公開を断るエラーコードは、Webサーバーの許可リストに足す。
- 問題と解説は、これまでどおり終了時に公開する。
- 作者への初AC通知は、宛先の作者がスタッフなので、凍結中も止めない。
- 凍結後の提出のリジャッジの結果は、結果確定まで凍結なしの順位表にだけ反映する。
- オンサイトのみの絞り込み（ADR 0024）は、凍結中も凍結した表を絞り込む。
- ADR 0016の退会を断る条件に、「凍結があり結果確定していないコンテストの、最後に残ったセッターである」を加える。
- 退会画面では、結果を公開してから退会するよう案内する。
- ADR 0016の背景にある「終了したコンテストの順位表には、参加者全員の結果が載る」は、凍結のあるコンテストでは結果確定まで成り立たない。
- 凍結を設定しないコンテストの動きは変わらない。
- ガイドの「コンテストのルール」（得点と順位、公開範囲）と「コンテストを開く」（終了したあと）に、凍結と結果の公開を書き足す。

# ADR 0031: 問題に結び付けずにコードを実行する「コード実行」を加える

- 状態：Proposed
- 決定日：2026-10-24
- 範囲：サイトのヘッダーとコンテストのメニュー、コード実行の画面とAPI、採点台での実行、送り出しの順番
- 一部変更：[ADR 0030](0030-list-own-contest-submissions.md)の、コンテストのメニューを狭い幅でも1行に収める前提（収まらない幅ではメニューの行を横にスクロールする）。[ADR 0032](0032-count-authoring-runs-separately.md)の、作問の処理を新しい提出のすぐ後ろに送る決定（コード実行を作問の処理より先に送る）

## 背景

解答を試すには、問題ページの「サンプル検証」か「提出」を使うしかなかった。
どちらも問題のテストケースで判定するので、自分で用意した入力でプログラムの出力を確かめることはできない。
AtCoderの「コードテスト」のように、プログラムと入力を渡して出力を見る場所がほしいという要望があった。

採点台は1台につき同時に1件ずつ処理する（ADR 0012）。
コンテスト中にコード実行が増えると、提出の採点が待たされる。
リジャッジと作問の処理（入力生成、出力生成、入力検証）では、新しい提出を先に送り、空きがあるときだけ送る形をすでに採っている（ADR 0019、ADR 0032）。

## 決定

### メニューの2か所に「コード実行」を置く

サイトのヘッダーでは「記事」と「作成」の間に置き、コンテストのメニューでは「質問」の右に置く。
どちらも同じ機能を開く。
コンテスト内では、コンテストのヘッダーとメニューを表示したまま開く。
コンテストの中の画面は、ほかの画面と同じく`/contests/<ID>?view=run`の形にする。
コンテスト外の画面は`/run`にする。

どちらのメニューも、狭い幅では今の項目だけで1行にほぼ収まっており、「コード実行」を足すと収まらない。
収まらない幅では、メニューの行だけを横にスクロールできるようにし、どの幅でも全項目を使えるようにする。
ページ全体には横スクロールを出さない。

コンテスト内のコード実行は、参加していない人も、開始前や終了後も使える。
実行はコンテストに結び付けず、記録もしない。

### 言語、ソースコード、標準入力を渡し、出力を返す

使えるのはログインしている人だけである。
ログインしていなければ、提出フォームと同じく、ログインを促す案内を出す。
ジャッジのメンテナンス中や言語一覧を取れないときは、提出フォームと同じく受付停止を知らせ、実行ボタンを押せなくする。

受け取るのは、言語、ソースコード、標準入力の3つである。
言語の一覧は提出と同じものを使う。
問題には結び付けず、期待出力との比較も判定もしない。

| 項目 | 上限 |
| --- | --- |
| ソースコード | 128 KiB（提出と同じ） |
| 標準入力 | 1 MiB |
| 実行時間 | CPU 5秒（今のジャッジで指定できる最大） |
| メモリ | 512 MiB |
| 回数 | 60秒に3回（サンプル検証とは別に数える） |

返すのは、状態、終了コード、実行時間、メモリ使用量、標準出力、標準エラーである。
コンパイルに失敗したときは、提出と同じくコンパイルのメッセージを返す。
出力の上限と判定は提出と同じにし、コード実行で試した結果が提出でも同じになるようにする。
標準出力が16 MiBを超えたとき、標準エラーが64 KiBを超えたときは、提出と同じく`OLE`にする。
標準出力は上限の内でも長くなり得るので、画面に返すのは先頭64 KiBまでとし、省いたかどうかを添える。

### 結果は直近の1件だけを見せる

画面に出すのは、自分が最後に実行した1件の結果だけである。
実行の一覧や履歴の画面は作らない。
実行中や実行の直後に別の画面へ移って戻ったときも、その1件の状態と結果を出す。
混雑時は待ち時間が長くなり、コンテスト中は問題ページと行き来するのが普通なので、戻るたびに実行し直さずに済むようにする。
結果は、サーバーに1日だけ残して消す。

### 新しい提出を先に送り、コード実行は空きがあるときに送る

送り出しの順番は、新しい提出、コード実行、作問の処理、リジャッジの順にする。
コード実行は、作問の処理やリジャッジと同じく、SQSにある採点と採点中の採点が合わせて2件未満のときだけ送る。
この2件には、提出の採点、作問の処理、リジャッジ、コード実行をすべて数える。
新しい提出の前に並ぶコード実行、作問の処理、リジャッジは、合わせて多くても2件になる。

コード実行を作問の処理より先に送るのは、処理の長さが大きく違うからである。
コード実行は入力1件を1回動かすだけで、長くてもコンパイル30秒と実行5秒で終わる。
作問の処理は最大100ケースを実行し、1回で8分を超えることがある。
作問の処理を先にすると、後ろのコード実行は数分待って10分の打ち切りに届きかねないが、逆なら作問の処理の遅れは数十秒で済む。
また、コンテスト中に多いのは参加者のコード実行で、作問の処理はふつう開催前に行う。

ただし、コンテスト中にテストケースの誤りを直すときは、作問の処理を急ぐ。
コード実行が途切れずに続いても作問の処理が止まらないよう、受け付けてから5分以上待った作問の処理は、コード実行より先に送る。

受け付けてから10分たっても始まらない実行は打ち切り、混雑で実行できなかったと返す。
増設台の起動判定にはコード実行を数えず、コード実行のために台を起動しない。

### 画面は左右2列にする

広い画面では、左に言語とソースコード、右に標準入力、実行ボタン、結果を並べる。
書き換えては実行する繰り返しで、スクロールしなくて済むようにするためである。
狭い画面では、言語、ソースコード、標準入力、実行ボタン、結果の順に縦一列にする。

エディタは提出フォームと同じものを使い、エディタ設定も反映する。
言語は、提出フォームが覚えている前回の言語を初期値にする。
ソースコードと標準入力はブラウザに保存し、別の画面へ移って戻っても残す。
保存先は1つにし、`/run`とコンテスト内の画面で同じ下書きを使う。

実行中は、実行ボタンにスピナーを出して押せなくする。
結果欄には、提出一覧と同じWJのバッジ（スピナー付き）を出す。
終わったら、提出と同じ見た目のバッジで状態を示す。
正常に終わったときは`AC`、そうでなければ`CE`、`RE`、`TLE`、`MLE`、`OLE`などのジャッジの判定を出す。
期待出力と比べていないので、ここでの`AC`は「正常に終了した」ことだけを表す。

## 代替案

- **コード実行を提出の表に入れる**：送り出しと結果の受け取りをそのまま使える。ただし、提出は問題に結び付いていることを前提に、提出一覧、順位表、通知、リジャッジ、公開APIが集計している。どこか1か所でも除き忘れると、コード実行が提出として数えられるので採らなかった。
- **コード実行を新しい提出と同じ順で送る**：コンテスト中にコード実行が増えると提出の結果が遅れるので採らなかった。
- **コード実行を作問の処理の後ろに送る**：ADR 0032の順番を変えずに済む。ただし、8分を超える作問の処理の後ろで、数十秒で終わるコード実行が待たされるので採らなかった。
- **狭い幅ではメニューから外す、2行に折り返す、「実行」と短く書く**：外すとスマホから開く手段がなくなり、折り返すとヘッダーが1行分高くなり、短い表記では何を実行するのか伝わりにくいので採らなかった。
- **実行の履歴を残して一覧にする**：AtCoderのコードテストも直近の結果だけを見せる。下書きをブラウザに残せば試行の繰り返しには足りるので、作らなかった。

## 影響

- コード実行は提出とは別に保存する。提出一覧、順位表、通知、リジャッジ、公開APIには現れない。
- アカウントを削除すると、その人のコード実行も消える。
- 配布の`run`は待ち状態のコード実行も排出の対象にし、`runtimeDigest`の切り替えでも提出と同じく扱う（ADR 0014）。
- 採点台は、提出の標準エラーをこれまで返していなかった。コード実行のときだけ、先頭64 KiBまで返す。
- コンテスト中に提出が続くと、コード実行は空きができるまで待つ。
- コード実行が続くと、作問の処理は最大5分ほど後回しになり、リジャッジの完了はさらに遅れる。
- 狭い幅では、両方のメニューの右端の項目が、横に送るまで隠れる。ADR 0030の幅のテストは、ページ全体に横スクロールが出ないことを確かめる形に合わせる。

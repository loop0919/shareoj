# ADR 0022: コンテストを複数のセッターで作り、スタッフと参加者を兼ねさせない

- 状態：Accepted
- 決定日：2026-10-18
- 範囲：コンテストの役割とその判定、共同作成者の招待と権限、コンテストに入れられる問題、セッターが問題に持つ権限、作成者の表示、アカウント削除でのコンテストの扱い
- 一部変更：
  - [ADR 0015](0015-save-contests-as-drafts.md)の、下書きを作った人だけが編集して公開する扱いと、「画像の参照判定には下書きの説明を加え、作者だけに見せる」
  - [ADR 0016](0016-anonymize-deleted-accounts.md)の「開催予定・開催中の自分のコンテストがある間は、削除を受け付けない」と、コンテストの下書きをすべて削除する扱い
  - [ADR 0019](0019-rejudge-submissions.md)の「コンテストの問題は作成者が作者なので、コンテストの作成者もここに含まれる」

## 背景

コンテストを作れるのは1人だけだった。
`contests.owner_id`と`contest_drafts.owner_id`はどちらも1人を指し、設定の編集、下書きの保存と公開は、その人にしかできなかった。
説明に使える画像も、その人がアップロードしたものに限られていた。
ほかの人が準備を手伝うには問題ごとにテスターとして招待されるしかなく、コンテストの設定や公開には手を出せなかった。

誰がスタッフかは、保存された役割ではなく、クエリのたびに行から求めている。
スタッフの条件（オーナーか、コンテストのいずれかの問題のテスター）と、開始前に問題を見られる条件は、合わせて約15か所に手で写されている。
写しはすでに食い違っている。
開始前に問題を見られる条件には問題の作者が入っているが、スタッフの条件には入っていない。
そのため、テスターが作者の問題を自分のコンテストに入れると、作者は開始前に問題を見られるのに、参加登録して順位表に載れる。

参加者とスタッフの間の移り変わりも決まっていなかった。
参加登録した人は、開催中でも問題のテスター招待を受けられる。
受けた人はスタッフになって全提出を見られるようになり、順位表からは黙って外れる。
順位表は要求のたびに集計するので、終了後にテスター招待を受けても、終わったコンテストの順位表からその人の行が消える。
逆に、開始前に問題をコンテストから外すと、その問題のテスターはスタッフでなくなり、問題を見た後でも参加登録できる。

順位表の凍結（[ADR 0023](0023-freeze-contest-standings.md)）とチーム戦（[ADR 0024](0024-team-and-onsite-participation.md)）も、誰がセッターで誰がスタッフかの判定に依存する。

## 決定

### 役割を5つに分ける

コンテストに関わる人を、次の役割で扱う。

- **オーナー**：コンテストの下書きを作った人。
  誰が公開しても変わらない。
- **共同作成者**：招待リンクを受けて加わった人。
- **セッター**：オーナーと共同作成者。
- **スタッフ**：セッター、コンテストの問題の作者、コンテストの問題に招待されたテスター。
- **参加者**：参加登録した人。
  チーム戦ではチームのメンバー（ADR 0024）。

スタッフは、これまでのオーナーとテスターと同じく、開催中もコンテストの全提出を見られ、参加登録できず、順位表に載らない。
開始前に問題を見られるのは、セッターと、その問題の作者とテスターである。

問題の作者をスタッフに加えるのは、背景に挙げた食い違いの修正である。
作者は開始前から問題文もテストケースも知っているので、テスターと同じく公式順位の対象から外す。

### 役割の判定をSQLの関数にまとめる

セッターかどうかとスタッフかどうかは、`can_manage_problem`と同じくSQLの関数で判定する。
手で写した条件は、すべてこの関数の呼び出しに置き換える。
共同作成者、凍結、チーム戦の条件を写しのそれぞれに足すと、食い違いがさらに増えるためである。

### スタッフと参加者を兼ねさせない

参加者は、結果確定まで、そのコンテストのスタッフにならない。
結果確定は、凍結のないコンテストでは終了、凍結のあるコンテストでは凍結の解除を指す（ADR 0023）。
結果確定までは、参加者がスタッフになる次の経路をすべて拒否する。

- 共同作成者の招待を受ける。
- コンテストに入っている問題のテスター招待を受ける。
- 参加者が作者かテスターである問題を、コンテストに入れる。
  コンテストの保存と公開の判定で問題点として示し、拒否する。

招待の受諾は、どちらも409で拒否する。

逆に、一度スタッフになった人は、抜けた後も、外された後も、問題がコンテストから外れた後も、そのコンテストに参加できない。
スタッフの判定は今の行から求めるので、共同作成者が抜けたときや外されたとき、問題をコンテストから外したときに、スタッフでなくなる人を除外として記録する。
参加登録とチームへの参加では、この記録も確かめる。

結果確定の後に参加者が問題のテスターになっても、順位表からは外さない。
確定した順位を後から変えないためである。

### 共同作成者を招待リンクで加える

招待リンクは1つのコンテストに1本とし、セッターが発行して表示できる。
作り直すと、古いリンクは使えなくなる。
オーナーが共同作成者を外したときは、外された人が手元のリンクで戻れないよう、リンクを自動で作り直す。
リンクはセッター向けの応答でだけ返し、公開の`Contest`には載せない。

招待は下書きの段階からできる。
共同作成者と招待リンクは、下書きと公開済みのコンテストに共通のIDで記録し、公開しても引き継ぐ。
オーナーが下書きを削除すると、共同作成者と招待リンクも消える。

招待は、参加者を除いて結果確定まで受けられる。
結果確定までは、リジャッジや結果の公開など、セッターが行う操作が残るためである。
誰かが招待を受けたら、オーナーに通知する。
漏れたリンクで知らない人が加わっても、オーナーが気付いて外せるようにするためである。

### 共同作成者はオーナーとほぼ同じ操作ができる

共同作成者は、次の操作をオーナーと同じようにできる。

- 開始前の設定の編集
- 下書きの保存と公開
- 問題の追加と削除
- 招待リンクの発行、表示、作り直し
- ADR 0023とADR 0024で加える操作（結果の公開、会場の合言葉の設定、オンサイト区分の切り替え、チーム名の修正）

オーナーだけができるのは、共同作成者を外すことと、下書きを削除することである。
共同作成者は自分で抜けられる。

公開しても、オーナーは下書きのオーナーのまま変わらない。
今の公開処理は公開した人を`contests.owner_id`に書き込むので、そのまま共同作成者に公開を許すと、元のオーナーがオーナーだけの操作を失う。

### セッターが直接管理している問題だけをコンテストに入れられる

問題を管理する立場のうち、問題の作者であることと、問題に招待されたテスターであることを、以下では**直接の管理**と呼ぶ。
コンテストに入れられるのは、今のセッターの誰かが直接管理している問題である。
これは、今の「オーナーが管理している問題」をセッター全体に広げたものである。
問題を追加できるのは、その問題を自分で直接管理しているセッターだけとする。

下書きの公開と公開済みのコンテストの保存では、操作した人ではなく、今のセッターの誰かが各問題を直接管理しているかを確かめる。
今は操作した人がすべての問題を管理していることを求めているので、このままでは共同作成者がオーナーの問題を含む下書きを公開できない。

公開済みの問題、公開予約中の問題、ほかのコンテストに入っている問題、定期便に応募中の問題、内容の条件（ADR 0021）を満たさない問題を入れられないことは、これまでどおりである。

### セッターは公開済みのコンテストの問題をテスターと同じ権限で扱える

公開済みのコンテストに入っている問題について、セッター全員が、問題に招待されたテスターと同じ権限を持つ。
問題の編集、リジャッジ、テストファイルの取得、判定用コードのログと解説の閲覧などである。
この権限を、以下では**コンテストから生じる権限**と呼ぶ。
セッターの誰かが入れた問題を、ほかのセッターも確かめて直せるようにするためである。

コンテストから生じる権限には、次の制限を置く。

- 下書きの問題リストからは生じない。
  下書きには任意の問題IDを保存でき、問題も確保しない（ADR 0015）。
  下書きから権限を与えると、他人の問題IDを書いて別のアカウントを共同作成者にするだけで、その問題を編集できてしまう。
- 下書きの段階では、ほかのセッターの問題は題名と準備状況だけを見られる。
- 問題のテスター招待リンクは、発行も表示もできない。
  問題のテスター招待リンクは作り直せず、テスターも外せないので、リンクを出せると、結果確定で切れるはずの権限が外せないテスターの権限に変わる。
- 問題をコンテストに入れてよいかの判定には数えない。
  数えると、コンテストに入っていることが、そのコンテストに入れてよい根拠になる。
- 結果確定までとする。
  結果確定の後は、作者と招待されたテスターだけが問題を管理する。

問題を管理できるかの判定は、直接の管理だけを見るものと、コンテストから生じる権限も含めるものの2つに分ける。
問題のテスター招待リンクの発行と表示、コンテストに入れてよいかの判定には、直接の管理だけを見るものを使う。
コンテストから生じる権限は`problem_testers`に行を作らず、判定のたびにコンテストから求める。
この判定は、読み取りと同じく文の開始時刻で結果確定を見る。
問題の保存などの書き込みでは、行のロックを待つあいだに結果確定を過ぎても通るが、その差はロック待ちの間にとどまるので許す。
多くの提出を待ち行列に戻すリジャッジだけは、ロックを取った後に判定し直す。

リジャッジもコンテストから生じる権限に含まれる。
コンテストの問題をリジャッジできるセッターは、結果確定までは全員、その後は問題を直接管理している人だけになる。

### 作成者としてセッター全員を表示する

コンテストとコンテストの問題の公開ページでは、「作成者」にオーナーを先頭としてセッター全員を並べる。
コンテストから生じる権限を持つセッターは、テスター欄には出さない。

非公開の画面では、権限がどこから来たかを示す。
作者の問題管理画面と、マイページの「テスト中の問題」では、セッターを「コンテスト『…』の作成者」として出す。
作者は、テスターが自分の問題をコンテストに入れたとき、誰が編集できるようになったかをここで確かめられる。

解説を見られるかどうかは、サーバーが返す。
今は画面が作者とテスターのユーザーIDから判定しており、共同作成者には解説へのリンクが出ない。

説明には、セッターの誰がアップロードした画像でも使える。
下書きの説明の画像は、セッター全員が見られる。

### アカウント削除では共同作成者にオーナーを移す

共同作成者がアカウントを削除したときは、共同作成者から抜けたものとして扱う。

オーナーがアカウントを削除するとき、結果確定していないコンテストか、共同作成者のいる下書きがあれば、最も早く加わった共同作成者にオーナーを移す。
結果確定までは招待を受け付けるので、受諾の通知を受けて、漏れたリンクで加わった人を外せるオーナーが要る。
共同作成者がいなければ、終了していないコンテストではこれまでどおり削除を受け付けない。
凍結があり結果確定していないコンテストでも削除を受け付けないことは、ADR 0023で決める。
共同作成者のいない下書きは、これまでどおり削除する。

終了していないコンテストに未公開の問題が入っている作者は、セッターかどうかにかかわらず、削除を受け付けない。
今は、未公開の問題を削除しようとしてコンテストの問題の参照に当たり、503になる。

## 代替案

- **共同作成者を問題の`problem_testers`に行として加える**：今のテスターの判定がそのまま使える。
  しかし、開始前に問題をコンテストから外しても、共同作成者が抜けても、行が残る。
  残った行で、その問題をほかのコンテストに入れることも、公開後に非公開へ戻すこともできる。
  行を加えるたびに作者へテスター追加の通知が届き、招待されたテスターとも区別できないので採らなかった。
- **コンテストから生じる権限に期限を設けない**：`contest_problems`の行は消せないので、セッターは何年後でも、ほかの作者の公開済みの問題を編集し、非公開に戻せる。
  作者が招待していない人に恒久的な権限が残るので採らなかった。
- **招待を開始前まで受け付ける**：漏れたリンクで開催中に人が加わることはなくなる。
  しかし、開催中に問題の不備が見つかったとき、提出の確認やリジャッジを手伝う人を加えられない。
  漏れたリンクには、オーナーへの通知と作り直しで対処できるので採らなかった。
- **招待の受付に期限を設けない**：結果確定の後に加わっても行える操作がなく、作成者の表示に名前が増えるだけなので採らなかった。
- **作者がセッターである問題だけをコンテストに入れられるようにする**：作者が常にセッターになり、作者の知らない人に編集を許すこともなくなる。
  しかし、テスターが担当の問題を自分のコンテストに入れる今の使い方（ADR 0013）ができなくなるので採らなかった。
- **参加者がスタッフになったら、黙って順位表から外す（今の動き）**：確定した順位表が後から変わる。
  チーム戦では、スタッフになったメンバーがチームに残ったまま全チームの提出を見られ、チームメイトに伝えられるので採らなかった。
- **共同作成者を問題のテスター欄にも並べる**：作者が招待したテスターと区別がつかず、すべての問題のテスター欄に同じ名前が並ぶので採らなかった。
- **共同作成者がいる間はオーナーの退会を受け付けない**：共同作成者のいる下書きやコンテストが残る限りオーナーが退会できず、オーナーを譲る手段もないので採らなかった。

## 影響

- 作者をスタッフに加える修正は、終了したコンテストにも及ぶ。
  テスターが作者の問題を入れたコンテストに作者が参加していた場合、過去の順位表からその行が消え、ほかの参加者の順位が変わる。
  開始前と開催中のコンテストでは、参加登録している作者がスタッフになり、全提出を見られるようになる。
  配布前に、該当するコンテストと人数を数える。
- 問題のテスター招待は、その問題が入っているコンテストの参加者からは、結果確定まで受けられなくなる。
- テスターが共同作成者として加わったコンテストに問題を入れると、作者の問題は、そのコンテストのセッター全員が結果確定まで編集できるようになる。
  作者に確認を求める手順はなく、作者は問題管理画面の表示で確かめる。
- 共同作成者が抜けたり外されたりして、どのセッターも直接管理していない問題が残ると、開始前はその問題を外すまでコンテストを保存も公開もできない。
- 問題のテスター招待リンクを作り直せず、テスターも外せないという既存の穴は残る。
  コンテストから生じる権限ではリンクを出せないので、共同作成者がこの穴を広げることはない。
- マイページのコンテスト一覧と下書きの一覧に、共同作成者として加わったものも出す。
- 招待を受けたことの通知は問題に紐付かないので、通知にコンテストを指すものを加える。
- 共同作成者、招待リンク、除外の記録を置く表と、役割を判定する関数を、マイグレーションで追加する。
  APIはマイグレーションより先に配布されるので、マイグレーションだけのコミットを先にpushする。
- 新しいエラーコードは、Webサーバーの許可リストに加える。
- ガイドの「公式順位の対象外」を、共同作成者と問題の作者を含むスタッフ全体に改める。
  問題のテスター招待リンクの説明にある「自分のコンテストへの登録」は、セッターを務めるコンテストへの登録に改める。

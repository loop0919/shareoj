# ADR 0012: EC2の常時稼働1台とコンテスト時の増設で採点する

- 状態：Accepted
- 決定日：2026-09-29
- 置き換え対象：[ADR 0006](0006-use-lightsail-and-isolate.md)の採点ホスト基盤（isolateによる隔離と計測の決定は引き継ぐ）
- 範囲：採点ホストの種類と台数、台数の制御、配布の前提。実装済み（本番への切り替えは別途）

## 背景

採点は、Lightsailの2 GBインスタンス2台がそれぞれ1件ずつ行っている。
コンテストの開始直後はA問題の提出とサンプル実行が集中し、2台では待ちが伸びる。
参加者1人あたり開始15分で約22秒分の採点が必要だと仮定すると、ピーク時に必要な台数は25人で約1.2台、100人で約5台になる。
この値は採点時間を仮定した見積もりであり、実測で見直す。

Lightsailは停止中も課金されるので、コンテストの時間帯だけ台数を増やしても費用は下がらない。
EC2のオートスケーリングで負荷に応じて台数を増やす方法も、開始直後の集中には間に合わない。
起動からOSが立ち上がるまでに数十秒かかり、さらにワーカーが起動時に全ランタイム（展開後に約20 GB）のハッシュを照合するため、採点を始められるまで数分かかるからだ。

一方、コンテストの開始時刻は事前にDBに登録されている。
開始前に台を起動しておけば、起動の遅さは待ち時間に影響しない。

## 決定

### 台の種類と構成

採点ホストをEC2のt3a.small（2 vCPU、2 GiB）に移し、常時稼働する**primary**1台と、平常時は停止しておく**burst**（既定2台）で構成する。
1台で同時に採点するのは1件という制限は変えない。
primaryは1年のEC2 Instance Savings Plansで賄い、購入は安定稼働を確認してから運用者が手動で行う。
burstは停止中もディスクを保持しており、配布済みのランタイムを読み込み済みの状態で起動できる。

CPUクレジットはunlimitedモードにする。
standardモードで停止から起動した台は、クレジット残高がないため、vCPUあたり20%の速度でしか動けない。
primaryは提出の少ない時間にクレジットを貯められるので、3時間程度のコンテストなら追加料金なしで乗り切れる。

全台を同じAMIから作り、パッケージとカーネルを一致させる。
runtime digestにはカーネルとパッケージ一覧が含まれ、digestが違う台は受け取った提出をJEにしてしまうからだ。

### 採用しなかった構成

1 vCPUで性能が一定のc7a.medium（SMTなしの物理1コア）は計測が安定する。
ただし、常時稼働させると割引後でもt3a.smallの約3倍の費用になるため採用しなかった。

常時稼働の1台だけをLightsailに残す案は、費用はもっとも低い。
しかし、LightsailとEC2ではカーネルが異なり、runtime digestが一致しない。
同じキューを両方で処理するにはdigestの設計を変える必要があり、さらにコンテスト中にどちらで採点されたかで実行時間が変わるため採用しなかった。

### ネットワークと権限

採点ホストは専用のIPv6専用VPCに置き、APIのVPCとはピアリングしない。
セキュリティグループは受信を持たず、運用はSSMで行う。
認証情報はIAMユーザーのアクセスキーをやめ、インスタンスロールから得る。
IMDSはIMDSv2だけを受け付け、ホストのnftablesでIMDSへの通信をrootに限る。
提出は外部につながらないネットワーク名前空間で動くため、IMDSには届かない。

GitHubの配布ロールは、アプリケーションのタグが付いたEC2のネットワークリソースを変更できる。
採点ホストとその専用VPCには`Component=judge-worker`タグを付け、配布ロールからの参照以外の操作を拒否する。

### 台数の制御

judge-bridgeが毎分の定期実行で、あるべき稼働状態を計算して台を起動し、保持期限を延ばす。
提出ごとの即時dispatchではEC2を操作しない。
burstを起動する条件は次のとおりである。

- **コンテスト**：参加登録が10人以上のコンテストについて、開始30分前から`min(終了, 開始+3時間)+15分`まで、burstをすべて動かす。
- **primaryの停止**：primaryが止まっていて採点待ちがあれば、burstを1台起動する。
- **採点待ちの滞留**：SQSに送った提出が2分以上受け取られていなければ、burstをもう1台起動する。

コンテストは誰でも作れるため、コンテストによる起動期間は24時間で合計8時間までに制限する。
予備の起動（primaryの停止と採点待ちの滞留）の保持期限は30分とする。

burstを止めるのはburst自身である。
10分以上提出を受け取らず、bridgeと配布ツールが付けた保持期限の遅いほうを60秒以上過ぎたら、採点と採点の間で電源を切る。
bridgeが外から止めないのは、採点中の台を止めると、その提出が可視性タイムアウトの35分後まで戻らないからだ。

bridgeが起動するのは、配布ツールが付けた導入済みdigestのタグがbridgeのdigestと一致する台だけである。
配布から漏れた台を起動すると、受け取った提出をすべてJEにしてしまう。

### 配布

配布ツールは、停止中の台も含めて全台を起動してから作業する。
配布対象と`JudgePool`タグの付いた台が一致しなければ、作業を中断する。
作業中は4時間の保持期限を付け、完了時に15分へ縮めて、使われないburstが止まるようにする。

## 影響

### 待ち時間

条件を満たすコンテストでは、開始時点でprimaryとburst 2台の計3台が採点できる。
見積もりでは25人規模なら余裕があり、50人規模では開始直後に待ちが出る可能性がある。
条件を満たさないコンテストや予定外の集中では、予備のburstが採点を始めるまで数分かかる。
順位表は提出時刻で集計するため、採点の待ちは順位とペナルティに影響しない。

### 計測

t3a.smallの2 vCPUは、物理1コアをSMTで分けたものである。
提出と管理側の処理が同じコアを使うので、提出のCPU時間が揺れる可能性がある。
LightsailもバーストするCPUであり、同種のばらつきは今もある。
切り替え前に同じ提出を繰り返し実行し、Lightsailとばらつきを比べる。
CPUの速度も変わるため、既存の問題の制限時間がこれまでより緩く、または厳しくなる可能性がある。

### 費用

月額はAWSの公開料金（東京、2026年9月）で約30 USDと見込む。
内訳は次のとおりである。

- primaryのSavings Plans：約11.2 USD
- ディスク（gp3で60 GB × 3台。展開後のランタイムが約20 GBあり、更新中は新旧が同居する）：約17.3 USD
- burstの稼働（毎週4時間、unlimitedの追加料金を含む）：約1.9 USD

Lightsail 2台の20 USDより高い。
増加分の大半は、停止中も課金されるディスク代である。

### セキュリティ

提出と管理処理が同じカーネルを共有するという、ADR 0006の影響は変わらない。
長期間有効なアクセスキーをホストに置かなくなり、IMDSで得られる一時的な認証情報にはrootの処理だけが届く。

# ADR 0037: 出力の数を誤差の条件で比べる誤差ジャッジを加える

- 状態：Accepted（実機検証は未実施）
- 決定日：2026-11-12
- 範囲：判定方法の追加、数の読み方と比べ方、下書きとジョブの形、結果の印、Web、CLI、配布の順序。公開前に実機検証を行う

## 背景

通常判定は、提出の出力と期待出力を空白で区切り、トークンの完全一致で比べる。
答えが実数の問題では、正しい解答でも桁数や丸めが期待出力と食い違うので、完全一致では採点できない。
このため作問者は、誤差を認める検証コードをスペシャルジャッジとして問題ごとに書いていた。

作問者が「絶対誤差または相対誤差が$10^{-6}$以下」のような条件を選ぶだけで、実数の問題を出せるようにする。
以下の設計を採用し、実機での検証に合格してから公開する。

## 決定

### 利用者と決めたこと

- 出力は、実数1個か、空白や改行で区切った実数の並びが多い。
  文字列が混ざることもある。
- 条件の種類は、絶対誤差、相対誤差、絶対誤差または相対誤差の3つとする。
- 許容誤差εは、$10^{-1}$から$10^{-12}$までの12個から選ぶ。
  初期値は$10^{-6}$とする。
- 期待出力は真の値からわずかにずれていることがあるので、εに余裕を上乗せして比べる。
- 余裕の初期値はεの0.1%とし、作問者が割合を変えられる。
  答えが無限小数になる問題が多いので、余裕は初期状態で効かせ、入力欄も最初から見せる。
- 編集画面では、余裕の割合そのものでなく、結果として正解になる誤差の上限を数字で見せる。

### 比べ方

提出の出力と期待出力を、通常判定と同じ規則でトークンに分ける。
トークンの数が違えばWAとする。
同じ位置のトークンを1組ずつ比べ、バイト列として同じなら一致、両方が数なら条件で比べ、それ以外は不一致とする。
すべての組が一致すればACとする。

数として読むのは、`-?(数字+ | 数字+.数字* | .数字+)([eE][+-]?数字+)?`の形にトークン全体が合うものだけとする。
先頭の`+`、16進、`1_000`、`nan`、`inf`は、文字列として完全一致だけを認める。
400バイトを超えるトークンと、指数の絶対値が400を超えるトークンも数としない。
1組の計算の大きさをこの上限で抑え、極端な値で採点を止められないようにするためである。

提出の値を$a$、期待出力の値を$b$とし、しきい値を$T = \varepsilon \times (1 + m/100)$とする（$m$は余裕の割合で、単位は%）。
絶対誤差は$\lvert a - b \rvert \le T$、相対誤差は$\lvert a - b \rvert \le T \times \lvert b \rvert$を一致の条件とし、絶対誤差または相対誤差はどちらかを満たせばよい。

### 余裕を上乗せする理由

作問者の期待出力は、想定解が浮動小数点で計算して有限の桁で書いた値であることが多く、真の値からわずかにずれる。
真の値を$x$、期待出力と$x$の差を$\delta$とすると、$x$との誤差がε以内の解答は、期待出力から最大で$\varepsilon + \delta$離れる。
しきい値をεちょうどにすると、真の値との誤差がε以内の解答が、期待出力の側の誤差のせいでWAになり得る。

しきい値をεの$(1 + m/100)$倍に広げると、絶対誤差では$\delta \le \varepsilon \times m/100$の範囲でこの解答をACにできる。
初期値の0.1%では、期待出力の誤差がεの1,000分の1まで吸収される。
εが$10^{-6}$なら、小数第10位まで書いた期待出力の丸めの誤差（$5 \times 10^{-11}$以下）は、この範囲に収まる。

代わりに、真の値との誤差がεをわずかに超える解答もACになり得る。
期待出力が正確なら、超える幅は最大で余裕の分（初期値ではεの0.1%）である。
作問者が期待出力を正確に書ける問題では、余裕を0にすれば、しきい値はεちょうどになる。

### 値を正確に比べる理由

10進の値を浮動小数点に直すと丸めが入るので、境界の近くで判定が変わる。
たとえばε $10^{-6}$、余裕0.1%（$T = 1.001 \times 10^{-6}$）の絶対誤差で、期待出力`1`に対する`1.000001001`は誤差が$T$ちょうどなのでACであるべきだが、倍精度で引き算すると$1.0010000000004737 \times 10^{-6}$になり、WAと判定される。
逆に、ε $10^{-1}$、余裕0%で期待出力`0.19999999999999999`に対する`0.3`は、誤差が$0.10000000000000001$で$T$を超えるが、倍精度では差が`0.1`と同じ値に丸められ、ACと判定される。

提出は出力を自由に選べるので、境界ちょうどの値を出すことも、境界をわずかに超える値を出すこともできる。
作問者が選んだ条件と判定を食い違わせないために、トークンの10進表記を正確な値として計算する。
誤差が$T$以下なら必ず一致し、$T$をわずかでも超えれば不一致になる。
結果は、有理数だけで計算した場合と同じになる。

数の上限（400バイト、指数±400）から、2つの数の差と、しきい値と数の積に要る桁数の上限が決まる。
実装は、その桁数で丸めが起きない精度の10進演算を使い、万一丸めが起きたら判定を出さずにJEにする。

### トークン数を先に数える理由

比較は、隔離環境の外の管理ワーカーで、1スレッドで動く。
提出は出力を自由に決められるので、すべての組を正確な計算へ送る出力を作れる（`0`に対する`0.0`の並びや、しきい値ちょうどの値の並びなど）。
数の比較を始める前にトークンの数を数え、違えばそこでWAとする。
数えるのは区切りの位置だけで、トークンを数として読まない。
これで正確な計算の回数は期待出力のトークン数で決まり、提出ではなく作問者が決める量になる。

出力はまとめてトークンの列に展開せず、少しずつ読みながら比べる。
比較中の追加のメモリは、出力の大きさに比例しない。

### 古いワーカーへの備え

誤差ジャッジを知らないワーカーは`errorJudge`を無視し、完全一致で採点する。
正しい解答が桁数の違いだけでWAになり、それが採点の誤りだと分からない。
このため、[ADR 0036](0036-support-run-twice-judge.md)の2ステップ形式と同じ仕組みで、ワーカーが誤差ジャッジのジョブの結果に印を付ける。
bridgeは、誤差ジャッジのジョブの印のない結果を、JE以外ならJEとして保存し、`platform`に記録する。
印は保存せず、APIの応答にも出さない。

### 保存と配布

下書きとジョブに、`checker`、`interactor`、`runTwice`と排他の`errorJudge`を加える。
コードを持たないので、公開準備の指摘は増やさず、形の誤りは下書きの保存時に拒否する。
問題の公開APIと問題ページは、種類とεだけを出し、余裕は出さない。
CLIは、`problem.toml`の`[error_judge]`で同じ設定を読み書きする。
DBマイグレーションは不要である。

旧bridgeは`errorJudge`をジョブに載せないので、APIを先に配置すると、誤差ジャッジの問題への提出が完全一致で採点される。
新しいWebは下書きを保存するたびに`errorJudge`を送り、旧APIは知らない項目のある下書きを拒否する。
このため、ワーカーとbridgeを先に配布し、その後にAPI、Webの順に配置する。
手順は[仕様](../judge/error-judge.md#配置)に記載する。

## やらないこと

- 10のべき乗以外のε。
- トークンごとに条件を変える指定（1個目は整数、2個目は実数など）。
- 行の数や行内の区切り方の検査。
  通常判定と同じく、空白と改行を区別しない。
- 開発用Dockerワーカーでの対応。
- スペシャルジャッジ、対話形式、2ステップ形式との併用。
- 採点ホストに追加のパッケージやコンパイル済みの補助プログラムを入れて、比較を速くすること。

## 代替案

浮動小数点で比べる案は採らない。
[値を正確に比べる理由](#値を正確に比べる理由)のとおり、境界ちょうどの値と、境界をわずかに超える値の判定を誤る。

浮動小数点で明らかに条件の内側か外側と分かる組をそこで決め、境界に近い組だけを正確に計算する案も採らない。
比較を遅くする最悪の入力は、すべての組がしきい値ちょうどの出力であり、その組は浮動小数点では決められない。
最悪の場合には、前段の判定が手間を増やすだけになる。
正確な計算だけでも、開発機では1組あたり約1.1マイクロ秒で比べられた。

余裕をスイッチで隠し、初期状態では余裕なしで比べる案は採らない。
答えが無限小数になる問題が多く、そうした問題の期待出力は真の値と一致しない。
余裕なしを初期値にすると、真の値に十分近い解答がWAになり得る。

# ADR 0039: 要求キューのレーンで採点環境を切り替える

- 状態：Accepted（実機検証は未実施）
- 決定日：2026-11-14
- 一部変更：[ADR 0014](0014-roll-out-os-updates-without-stopping-judging.md)の切り替えの手順（送り出しの一時停止）と「使う場面」
- 範囲：要求キューのレーン、`judge/rollout.py rolling`の順序、`rolling-revert`、`rolling`を使える配布の条件。設計は[提出も採点も止めないジャッジ更新の設計](../superpowers/specs/2026-11-14-zero-wait-judge-rollout-design.md)にある

## 背景

ADR 0014の`rolling`は、切り替えのあいだbridgeの送り出しを止める。
旧ワーカーの処理中の提出が終わるまで新ワーカーへ流せないからで、2026-10-29の配布では採点待ちが約6分伸びた。
それ以外の配布は`run`で、2026-11-13には約60分、提出を受け付けられなかった。
利用者が提出でき、採点もすぐ始まる状態を、更新中も保つ必要がある。

## 決定

### 要求キューを固定の2レーンにする

- レーンaは既存の要求キュー、レーンbは新しい`requests-b`とする。
  設定（保持期間、可視性タイムアウト、受信3回でDLQ）は同じにする。
- 結果キューと要求のDLQは1本のまま共有する。
  DLQは両レーンを再送元として許可し、既存のアラームがそのまま両方を見る。
- 使用中のレーンは、bridgeの`JUDGE_REQUEST_QUEUE_URL`が指すキューである。これを唯一の正とする。
- ワーカーが取るキューは、いまと同じく`worker.env`で決まる。ワーカーのコードは変えない。
- Terraformの変数`request_lane`でbridgeの送り先を決める。
  既定値は置かず、稼働中のbridgeの送り先と違えばplanを失敗させる。
  古い入力ファイルからのapplyで、ワーカーのいないレーンへ送り先が戻ると、提出が溜まるだけである。ワーカーのアラームは鳴らず、5分の`pending`アラームでしか気づけない。
  bridgeがまだない最初の構築だけは、変数`check_live_request_lane = false`でこの照合を外す。
  レーンを変えるのは配布ツールだけで、切り替え後に`zz-rollout.auto.tfvars.json`へ書く。
- 要求のDLQの許可ポリシーは、キューのARNではなくDLQ自身のARNから両レーンのARNを作る。SQSはDLQを指すキューを作るときに許可を確かめるので、許可はレーンbより先に入れる。

### `rolling`の順序

新しい環境のワーカーを空いているレーンで先に待たせ、bridgeの送り先、digest、直前のdigestを1回の更新で切り替える。
送り出しは止めず、旧ワーカーは旧レーンの残りを終えてから止める。

1. 空いているレーンが空であることと、全primaryが使用中のレーンを公開中のdigestで読んでいることを確かめる。後者は、切り替えと旧ワーカーの停止の間で止まった前の実行を見分ける。
2. 停止中のburst 1台を更新し、全言語のsmokeを通して新しいdigestを得る。digestが公開中と同じなら切り替えるものがないので、burstとアラームを戻して`status: unchanged`で終える。同じdigestを切り替えると、旧レーンの排出が新しい環境の提出まで送り直してしまう。
3. その台を空いているレーンに向けて起動し、キューの受信に失敗していないことを確かめる。ここまでは利用者に影響しない。
4. コンテストの期間を確かめ、bridgeを切り替える。
5. bridgeのタイムアウト＋5秒待ってから、APIのdigestを切り替える。待つのは、切り替え前の設定で動くbridgeの実行が、新digestの提出をJEにするのを防ぐためである。
6. 旧レーンのキューと処理中の提出が空になるまで待ち、旧ワーカーを止める。旧レーンに取り残された提出は、bridgeの操作`requeue-digest`で新しい環境へ送り直す。
7. 残りの台を更新し、使用中のレーンに向けて起動する。

切り替えの前に失敗すれば旧環境のまま採点している。ただし、ワーカーのアラームのアクションは止まり、burstは増設に使えない。
bridgeの更新を送った後の再開は、コンテストの期間が近くても拒まない。止まったままのほうが影響が大きいからである。
新しい環境が壊れていたときは、切り替えの後、旧ワーカーを止める前に限り、`rolling-revert`で旧環境へ戻す。
戻す前に旧ワーカーが動いていることを確かめる。
bridgeとAPIを戻し、新ワーカーと壊れた台を止め、取り残された提出を旧環境へ送り直し、設定とアラームのアクションを戻す。
残りのburstを採点に戻すのは、その後である。ワーカーの起動にはランタイムの検証で数分かかり、失敗もあり得るので、戻した状態をそろえてから行う。
本番APIテストが通ってから`status: reverted`で終わり、以後は再開できない。
切り替え後の自動ロールバックは行わない。

`run`はレーンを切り替えないが、全台を使用中のレーンに向けて起動する。

### 切り替えの計測

すべての`rolling`が、切り替えの前後の採点待ちを測り、合格しなければ`passed`にしない（`step: switch-watch-failed`）。
目標の「待ちの増加10秒以内」を、配布のたびに確かめるためである。

- 8人の一時的な利用者で、5秒ごとに提出する。1人あたりの提出制限には当たらない。
- APIには採点開始の時刻がないので、提出の状態を0.5秒ごとに読み、待ちの状態を抜けた時点を採点開始とする。APIは変えない。
- 切り替えの時点で待っていた提出とその後の提出の待ちの最大が、その前の中央値より10秒を超えて長いか、拒否かJEが1件でもあれば不合格とする。
- 計測が始められない、または報告を残さずに終わった場合も不合格とする。`rolling`自体が切り替えの途中で落ちた場合だけは、測れなかったこと（`switchWatch: "interrupted"`）を記録して完了を認める。終わった配布を、計測の都合で失敗にしないためである。

手順は[配布と検証の定型コマンド](../judge/deployment-checks.md#切り替えの計測)にある。

### `rolling`を使える配布

次の3つを満たす配布は`rolling`で行う。

- 新しいbridgeは、旧ワーカーの結果も新ワーカーの結果も受け取れる。
- 新しいbridgeが既存の機能の提出について送るジョブは、旧ワーカーがそのまま採点できる。
- 新しいジョブの項目や結果の項目を使う機能は、`rolling`が完了してからAPIで有効にする。

DBのスキーマは、APIの配布（GitHub Actions）で入るので、この手順の外にある。
列やテーブルを足すだけの変更は、旧bridgeと旧ワーカーが動いたまま入れられる。
旧bridgeが読めなくなる変更（列の削除や意味の変更）を伴う配布は`run`を使う。
3条件を満たせない配布も`run`を使う。

mainへpushするとAPIが自動で配布される。
そのため、ワーカーの配布物は「APIが新機能の設定の保存を拒む版」のコミットから作り、新機能を有効にするコミットは`rolling`の完了後にpushする。
この順序は配布ツールでは検査せず、運用者が守る。
コンテストの期間中と、その前後の4時間は、どちらの手順も実行しない（ADR 0014のとおり）。

### 要求のDLQ

要求のDLQから、レーンへ再送しない。
どちらのレーンへ戻しても、メッセージのdigestと受け取るワーカーのdigestが合うとは限らず、JEか採点の停止になる。
DLQに落ちたメッセージは消さず、原因を調べるために残す。

## 採用しなかった方法

### 切り替え前に試験用の提出を新レーンへ流す

新しい環境を通る最初の提出を、切り替えの前に確かめられる。
しかしbridgeに、使用中のレーンと別の送り出し経路が要る。
待機の確認はキューを受信できることだけを見て、壊れた環境は`rolling-revert`で戻す。

### 切り替え後の自動ロールバック

失敗の判定を誤ると、正常な環境から戻してしまう。
戻すかどうかは運用者が決める。

### digestごとにキューを動的に作る

ADR 0014で、キューとbridgeの送り先をdigestごとに作り替えるのは複雑すぎるとして不採用にした。
固定の2レーンなら、キューは作り替えず、使用中のレーンを切り替えるだけで済む。
その形で採用に変える。

## 影響

### 利用者

更新中も提出でき、採点待ちの増加は10秒以内を目標にする。
切り替えの瞬間に採点中だった提出は、旧ワーカーが最後まで採点する。

### 運用

- 導入では、`infra/judge`を`request_lane = "a"`でapplyし、`rollout.json`に`request_queue_b`を足す。最初の`rolling`が、新しい項目に対応したbridgeを配布する。手順は[配布と検証の定型コマンド](../judge/deployment-checks.md#レーンを使う導入の順序)にある。
- 導入のplanに出てよいのは、レーンbの作成と、DLQの許可ポリシーとIAMポリシーのその場の更新だけである。bridgeの環境変数は変わらず、破棄は0件である。bridgeのパッケージを本番と違うコミットからビルドしていると、bridgeのコードの更新も出る。そのままapplyしない。
- 手順4から7が終わるまでは、新しい環境の台が1台だけである。ふだんもprimary 1台で採点しているので、同時に採点できる数は変わらない。
- 切り替えによる待ちの増加（10秒以内）と、拒否とJEが0件であることは、すべての`rolling`で計測する。実機ではまだ測っていない。

### 費用

準備と更新の間だけburstを動かす。レーンbのキューは、使わないあいだ費用がほとんどかからない。

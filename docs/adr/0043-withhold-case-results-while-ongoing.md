# ADR 0043: コンテストと定期便の開催中は、テストケースごとの結果を件数だけにする

- 状態：Accepted
- 決定日：2026-11-24
- 範囲：提出詳細のAPI、提出結果の画面

## 背景

提出結果の画面は、テストケースごとの結果を、テストケース名を付けた表で見せていた。
テストケース名は`max_`や`corner_`のように入力の性質を表すことが多い。
入力生成では、名前の接頭辞を作問者が決められる。
どの名前のケースで落ちたかが分かると、解法や落とし穴の手がかりになる。

問題のタグは、同じ理由で定期便とコンテストの開催中に隠している（[ADR 0018](0018-tag-problems-and-posts.md)）。

## 決定

### 開催中は、結果ごとの件数だけを返す

次の提出は、テストケースごとの結果を返さない。

| 提出 | 返さない期間 |
| --- | --- |
| コンテストへの提出 | コンテストの終了まで |
| 定期便に出ている問題への提出 | その回の解説公開（翌22時）まで |

定期便は、新作か復刻かを問わない。
復刻の問題では、出題より前の提出も同じ期間は返さない。
開催中かどうかは、タグと同じ`problem_tags_hidden`で判定する。

この間、提出詳細は次の内容を返す。

- `cases`を省き、`caseVerdicts`に結果ごとのケース数を入れる。たとえば`{"AC":12,"WA":3}`である。
- 部分点のグループは、名前と得点を残し、`cases`（グループに属するケースの位置）を空にする。
- 提出全体の結果、得点、正解したケースの数、最大の実行時間とメモリ使用量は、これまでどおり返す。

自分の提出、コンテストの提出、問題の提出の3つの提出詳細で、同じ判定を使う。
提出一覧は、もともとテストケースごとの結果を返さない。

### 運営側には、これまでどおり返す

次の人には、開催中もテストケースごとの結果を返す。

- 問題を管理できる人（作者とテスター、開催中のコンテストの作成者と共同作成者）
- コンテストのスタッフ（コンテストのどれかの問題の作者とテスターを含む）

参加者の提出を調べるときに、どのケースで落ちたかが要るためである。

### サンプル検証は対象にしない

サンプル検証が実行するのはサンプルケースだけで、その入出力は問題文に載っている。
開催中も、ケースごとの入力、期待される出力、実際の出力を返す。

### 画面は件数を並べる

提出結果の「ジャッジ結果」には、表の代わりに`AC × 12`のような件数を並べる。
「グループごとの得点」は、ケースの列を出さない。

## 代替案

- **表を残し、名前だけを番号に置き換える**：何番目のケースで落ちたかと、ケースごとの実行時間が分かる。ケースは登録順に並ぶので、番号からも入力の性質を推測できる。
- **画面だけで隠す**：APIを直接呼べば読めるので採らない。
- **開催中に出した提出だけを対象にする**：復刻の問題では、出題より前の提出からテストケース名を読める。
- **運営側にも返さない**：参加者からの質問に答えるときに、作問画面と見比べる手間が増える。

## 影響

- 参加者は、開催中、どのケースで落ちたかを知ることができない。分かるのは、結果ごとの件数と、提出全体の結果である。
- 復刻された問題は、解説公開までの間、以前からある提出もテストケースごとの結果が見えなくなる。
- APIを使うプログラムは、`cases`がないときに`caseVerdicts`を読む。
- データベースの変更はない。

# ADR 0036: 提出を1ケースにつき2回実行する2ステップ形式を加える

- 状態：Accepted（実機検証は未実施）
- 決定日：2026-11-11
- 範囲：判定方法の追加、isolateワーカーでの2回の実行、下書きとジョブの形、Web、CLI、配布の順序。公開前に実機検証を行う

## 背景

符号化と復号、圧縮と展開のように、2回目の実行が1回目の入力を知っていると成立しない問題がある。
たとえばDOJ #644では、1回目に二進文字列Sを受け取って符号を出力し、作問者側が1文字を挿入し、2回目にSを復元する。
既存の判定方法（通常判定、スペシャルジャッジ、対話形式）は、提出を1ケースにつき1回だけ実行するので、この種の問題を出せない。
出すには、提出を2回実行し、2回のあいだで情報を渡せるのを作問者のプログラムだけにする必要がある。
提出側のファイルやメモリが2回目に残ると、提出が1回目の入力を持ち越せてしまい、問題が成立しない。

完成の目安は、DOJ #644に相当する問題（集計コード方式の得点）をShareOJで作れることとした。
以下の設計を採用し、実機での検証に合格してから公開する。

## 決定

### 利用者と決めたこと

- 判定方法に「2ステップ形式（Run-twice）」を、通常判定、スペシャルジャッジ、対話形式と並ぶ4つ目の選択肢として加える。
  対話形式のスイッチにはしない。
- 作問者はプログラムを1本だけ書く。
  これを**2ステップ用ジャッジ**と呼ぶ。
  2ステップ用ジャッジは1回目と2回目の両方で提出の相手をし、1回目に書いた**引き継ぎファイル**を2回目に読む。
- 2ステップ用ジャッジの書き方は対話用ジャッジと同じにする。
  標準入力で提出の出力を読み、標準出力が提出の標準入力になる。
- 提出からは、どちらの回も標準入力を読んで標準出力へ書くだけに見える。
- 時間制限とメモリ制限は1回ごとに適用する。
  提出結果に表示するCPU時間と最大メモリは、2回のうち大きいほうとする。
- 1回目で判定が確定したら、2回目を実行しない。
- 点は2回目のものだけを読む。
- 何回目かを提出へ伝える方法は、システムで決めない。
  作問者が問題文と2ステップ用ジャッジで決める。
- 開発用Dockerワーカーは対応しない。

### 引き継ぎの渡し方を形式で分ける

何回目かと引き継ぎを2ステップ用ジャッジへ渡す方法は、現行形式とtestlib形式で変える。

現行形式では、対話用ジャッジの4つの引数の後ろに、何回目か（`1`か`2`）と引き継ぎファイルのパスを足す。
現行形式のジャッジは引数を自分で読むので、後ろに足しても既存の4つの引数の意味は変わらない。
テスト入力と期待出力は2回とも同じものを渡すので、2回目も元のテスト入力を読める。

testlib形式では引数を足さず、Polygonと同じく、1回目に`tout`へ書いた内容を2回目の`inf`にする。
testlibの`registerInteraction`は受け付ける引数の数が決まっていて、余分な引数があると`_fail`で終わるからである。
この受け渡しなら、Polygon用に書かれたinteractorをほぼそのまま使える。
代わりに、2回目は元のテスト入力を読めず、何回目かも引数で渡らない。
作問者は、テスト入力と`tout`の先頭に別々の値を置くなどして、何回目かを見分ける。

### 実行と判定

各回は、対話形式の1ケースと同じ手順と資源上限で実行する。
2回目の隔離環境は新しく作り、1回目から残すのは、管理ワーカーが読み取った引き継ぎの内容だけとする。
引き継ぎは1回目がACのときだけ読み、大きさに上限を設ける。
上限を超えた場合と、通常のファイルでない場合は、提出全体をJEにする。
通常のファイルに限るのは、2ステップ用ジャッジが引き継ぎをリンクやFIFOに置き換えても、管理ワーカーがホストのファイルを読んだり、待たされたりしないようにするためである。

1回目がAC以外なら、その判定をケースの判定とし、2回目を実行しない。
ACには、2回とも提出が正常に終了することを求める。
1回目のスコアファイルと結果ファイルからは点を読まない。
testlib形式の1回目が`quitp`で終えた場合は、集計コード方式の問題とそのサンプル検証でだけ、`_ok`と同じく通過として扱う。
それ以外の問題では、対話形式と同じくJEとする。

採点全体の経過時間の上限は変えない。
1ケースが最長で2回分の時間を使うので、ケース数の多い問題は全体の上限に届きやすくなる。
このことは作問者向けのガイドに書く。

### 診断の公開範囲

診断は対話形式と同じく`checkerLog`に入れ、同じ認可と保存量の上限を適用する。
各ケースの診断は回ごとに見出しで分け、2回目を実行しなかったケースには理由になった1回目の判定を残す。

### 保存と配布

下書きとジョブに、`checker`、`interactor`と排他の`runTwice`を加える。
問題の公開APIはコードを返さず、2ステップ形式であることだけを返す。
DBマイグレーションは不要である。

旧ワーカーは`runTwice`を解釈せず、旧bridgeは`runTwice`をジョブに載せない。
APIを先に配置すると、2ステップ形式の問題への提出が通常判定として採点される。
このため、ワーカーとbridgeを先に配布し、APIとWebはその後に配置する。
手順は[仕様](../judge/run-twice.md#配置)に記載する。

## やらないこと

- 3回以上の実行。
- 1回目の出力をそのまま2回目の標準入力にする、ジャッジを書かない簡易な方式。
- 2ステップ用ジャッジの後に別の検証コードを実行する方式。
  正誤と点は2ステップ用ジャッジ自身が決める。
- 2回の実行のあいだでの、提出側のファイルやメモリの持ち越し。
  これができると問題が成立しないので、誤って可能にしないようにする。

## 代替案

対話形式にスイッチを足す案は採らない。
スイッチの有無で、現行形式のジャッジの引数と、testlib形式の2回目の`inf`の中身が変わり、同じ対話用ジャッジの欄が2通りの意味を持つことになる。

現行形式でも、1回目に書いたファイルを2回目のテスト入力として渡す案は採らない。
現行形式は引数を足せるので、何回目かを引数で伝えられ、2回目にも元のテスト入力を読める。
作問者がデータの中に印を置いて回を見分ける手間は、引数を足せないtestlib形式にだけ残す。

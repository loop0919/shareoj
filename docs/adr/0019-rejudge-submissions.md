# ADR 0019: 提出を今の問題の内容でリジャッジし、新しい提出の採点を優先する

- 状態：Accepted（コンテストの問題をリジャッジできる人は[ADR 0022](0022-share-contests-among-setters.md)で一部変更）
- 決定日：2026-10-17
- 範囲：受け付け済みの提出の再採点、リジャッジできる人、採点の送り出しの順番と量、増設台の起動判定

## 背景

提出は、受け付けた時点のテストケース、制限、判定方法を`job`に写して採点する。
作問者がテストケースの誤りを直しても、採点済みの提出の結果は変わらなかった。
コンテスト中にテストケースの誤りが見つかると、順位を正しい結果に直す手段がなかった。

採点台は常時稼働の1台が同時に1件ずつ採点し、SQSで2分以上待つ提出があると増設台を起動する（ADR 0012）。
送り出しは`created_at`の順で、6時間の期限切れと滞留時間の監視も`created_at`を基準にしていた。
古い提出をそのまま待ち状態に戻すと、新しい提出より先に送られ、戻した直後に期限切れのJEになる。

## 決定

### 保存済みの問題の内容で採点し直す

リジャッジは、終わった提出を待ち状態に戻し、`job`を問題の今の内容で作り直す。
採点内容の選び方は提出時と同じで、コンテストの提出は`contest_problems`の写しを、それ以外は公開版か下書きを使う。
`judge_attempt`を振り直すので、前の試行の結果が遅れて届いても反映しない。
非公開時の提出かどうか（`privateDraft`）は元の提出から引き継ぎ、公開範囲を変えない。

採点中の提出、サンプル検証、生成と検証の実行、現在使えない言語の提出は対象にしない。
採点中の提出を除くので、同じ提出が二重に待ち行列へ入ることはない。
問題の行をロックしてから戻すので、1回のリジャッジに2つの版が混ざらない。

### 作者、テスター、運営がリジャッジできる

リジャッジできるのは、`can_manage_problem`を満たす作者とテスターと、`OPERATOR_SUBJECTS`の運営である。
コンテストの問題は作成者が作者なので、コンテストの作成者もここに含まれる。
問題の全提出をまとめて戻すか、最大100件の提出を選んで戻す。

### 新しい提出を先に送り、リジャッジは空きがあるときだけ送る

送り出しは新しい提出を先にし、リジャッジは`rejudged_at`の順に後ろへ回す。
リジャッジは、SQSにある採点と採点中の採点が合わせて2件未満のときだけ送る。
新しい提出の前に並ぶリジャッジは、多くても2件になる。
採点結果を受け取るたびに送り出しを呼び、毎分の実行を待たずに次のリジャッジを送る。

期限切れと滞留時間は、リジャッジした提出では`rejudged_at`から数える。
増設台の起動判定にはリジャッジを数えず、リジャッジのために台を起動しない。

## 代替案

- **提出時の`job`のまま採点し直す**：採点環境の不調は直せるが、テストケースの誤りは直らない。リジャッジを使いたい場面の多くは後者なので採らなかった。
- **リジャッジを新しい提出と同じ順で送る**：古い提出が先に送られ、新しい提出の結果が遅れる。増設台も起動するので採らなかった。
- **リジャッジ中の問題では次のリジャッジを受け付けない**：一覧で提出を選んで順にリジャッジする使い方を妨げる。採点中の提出を対象外にすれば二重に並ばないので採らなかった。

## 影響

- `submissions.rejudged_at`を追加し、送信中の採点を数えるための部分インデックスを作る。
- リジャッジした提出は結果が出るまで判定待ちに戻る。コンテストの順位、正解者数、定期便の順位表は都度集計なので、結果が出れば反映される。
- 大量のリジャッジは常時稼働の1台で順に進むので、終わるまで時間がかかる。
- 配布の`run`は待ち状態の提出がなくなるまで待つので、リジャッジが残っていると配布の完了が遅れる。
- 採点環境は、提出時ではなくリジャッジ時のものを使う。旧環境での再採点は引き続き扱わない。

# ADR 0010: testlibとC#、Java 25、Nim、Goを採点環境へ追加する

- 状態：Accepted（testlibの部分点の扱いは[ADR 0025](0025-score-partially-with-test-groups.md)で一部変更）
- 提案日：2026-09-14
- 変更対象：ADR 0007の言語とライブラリの範囲、ADR 0008と0009の判定プロトコル、ADR 0009のJava公開保留方針
- 範囲：実装と配布。本番公開は実機smokeと受付再開をもって完了する
- 適用：2026-09-14に全14ランタイムの実機検証と本番APIの検証提出16件が成功し、12言語の受付を再開した。[適用記録](../judge/runtime-rollout.md)を参照

## 背景

C++からtestlibを利用し、C#、Java 25、Nim、Goと指定された競技向けライブラリを追加したいという要望がある。
既存環境は[ADR 0006](0006-use-lightsail-and-isolate.md)に従う2 GBのLightsailとisolateであり、言語ごとのコマンドを`judge/runner/runtimes.py`に定義している。
配布物を別のビルド環境で作り、同じランタイムを通常提出、スペシャルジャッジ、対話用ジャッジで使う。

Java 24は保守状況を理由に公開を保留している。
Nimの要求には、現在のC++環境のACLとBoostとは異なる版が含まれる。
Goのライブラリ名には版が記載されていないため、名前だけで再現可能な環境は決まらない。

## 決定

### 既存の配布方式と隔離を拡張する

既存の`runtime.tar.gz`と`/opt/judge-runtimes`を拡張し、言語別コンテナ、別worker、動的なプラグイン機構は導入しない。
ランタイム名とruntime digestの組で実行条件を識別し、コンパイラ、引数、依存ライブラリ、実行用設定を変更するときは新しいdigestを発行する。
現実装のdigestはランタイム群とホスト環境をまとめて指すため、新言語の追加時にも既存言語を回帰検証する。

ダウンロードと依存解決はビルド時に完了させる。
提出には単一ソースだけを受け付け、依存定義、ビルドスクリプト、コンパイラオプションは運用側で固定する。
コンパイル時もisolateで資源を制限し、外部通信を許可しない。
共有ライブラリと依存ソースは読み取り専用にし、提出ごとの生成物と書き込み可能なキャッシュはbox内に置く。
Nimのコンパイル時実行も、この隔離と制限の対象とする。

### C++でtestlib形式の判定コードを動かす

C++23のGCC版とClang版に、同一commitの`testlib.h`を提供する。
`#include <testlib.h>`で参照できるようにし、既存のC++用ACLとBoostの版は変更しない。
既存の`cpp23-gcc`と`cpp23-clang`をtestlib対応の構成へ更新し、testlibなし版と対応版を別の公開ランタイムとして併設しない。
GCC版とClang版の区別は維持する。
追加するヘッダーをincludeしない通常提出への直接の影響は限定的と見込むが、無条件に互換とせず、既存のコンパイル引数と依存の維持および回帰smokeの成功を更新条件とする。
実体の更新時にはruntime digestを変更し、旧digestの受付済み提出は更新前に処理する。
復旧用で公開保留中のC++17は今回の追加対象に含めず、公開状態も変更しない。

ユーザーの意図は、Codeforcesで使われるtestlib形式の判定コードをそのまま利用できることである。
ヘッダー提供に加え、`registerTestlibCmd`を使うcheckerと`registerInteraction`を使うinteractorの呼び出しに対応する。
現行形式とは引数と終了コードの意味が異なるため、判定コードに`protocol`を追加し、`legacy`と`testlib`を明示的に区別する。
省略時は`legacy`と解釈し、既存問題と受付済み提出の動作を保つ。
UIでは新規C++判定コードにtestlib形式を案内し、現行形式も選べるようにする。
ソースのincludeから形式を自動検出しない。

下書き、公開版、提出受付時のスナップショット、dispatch、workerまでprotocolを引き継ぐ。
未知の値は受け付けず、初期の`testlib`形式はtestlibを提供するC++23の2ランタイムに限定する。
新言語を含む全公開言語では従来どおり`legacy`形式を使える。
この区別は言語の公開一覧とは別の、判定コードの呼び出し契約である。
`legacy`を選んでも、使用するC++環境は同じtestlib対応版であり、旧ランタイムを保持するための設定ではない。
現行checkerは提出出力を標準入力から読み、引数に入力、正解、提出ソース、スコアファイルを受け取るため、testlib形式への一律変更には既存判定コードを壊す具体的な互換性問題がある。
判定形式まで統一する場合は、保存済みの下書きと公開版を調査し、対象コードの移植と再検証を終えてから別途決定する。
この設計調査では本番の保存済み判定コードを確認しておらず、移行対象が存在しないとは判断しない。

checkerの呼び出しは次の形とする。
入力、提出出力、正解は管理側が判定boxへ読み取り専用で配置し、標準入力は空にする。
提出出力はサイズ確認後のバイト列をそのまま保存する。

```text
checker /box/test-input /box/submission-output /box/expected-output
```

interactorは次の形で呼び出す。
標準入出力は既存の中継を使い、提出との通信に割り当てる。
第2引数はtestlibの`tout`が書く通常ファイルであり、提出への通信路とは別にする。

```text
interactor /box/test-input /box/test-output /box/expected-output
```

interactor自身が`quitf`で正誤を決める構成を対象とする。
`test-output`はケースごとに作る書き込み可能なファイルとし、16 MiBを上限に、ケース終了後に破棄する。
制限超過はJEとして扱い、管理側はその内容を集計したり後段checkerへ渡したりしない。
Polygonのパッケージ取り込み、generator/validatorの登録方式、部分点、testset/group設定、interactor出力を別checkerへ渡す二段階判定は今回の範囲外とする。
これらを必要としない単一ソースのtestlib判定コードは、初期化部分の書き換えなしで使える。

終了コードの解釈は[testlibの初期化と終了処理](https://raw.githubusercontent.com/MikeMirzayanov/testlib/master/testlib.h)に合わせて、testlib形式だけ次の対応とする。
コードを独自のマクロで変更する判定コードは互換対象に含めない。

| 判定コードの終了 | 本サーバの判定 |
| --- | --- |
| 0（`_ok`） | AC候補。対話では提出側の正常終了も必要 |
| 1、2、4、8（不正解、形式違反、余分な出力、入力不足） | WA |
| 3（`_fail`） | JE |
| 7（`_points`）、未対応コード | JE。部分点の集計は未対応と診断する |
| 自発的なシグナル終了、実行基盤異常、判定側の資源制限超過 | JE |

部分点の`_pc(...)`は標準の終了コードと衝突し得るため、終了コードだけでは完全に検出できない。
利用ガイドと作問時の注意で対象外と明示し、互換性を保証するコードはAC/WA形式に限定する。
標準エラーの文言を解析して判定を推測しない。
`legacy`形式の非ゼロ終了やassert失敗によるWAは変更しない。

提出側のCE、TLE、MLE、OLE、REと管理側の強制停止の扱いは、既存の優先規則を維持する。
対話では強制停止した相手のシグナルを新たなJEへ変換せず、判定側が実際に完了した結果にだけprotocol別の終了解釈を適用する。
非公開入力、正解、判定用ファイルを提出側へ渡さず、診断は既存どおり問題作成者自身の提出詳細にだけ公開する。

### 新言語の実行方式を固定する

| 対象 | 採用する構成 | 成果物と実行 |
| --- | --- | --- |
| C# | C# 14、.NET 10 LTS、MathNet.Numerics、ac-library-csharp | Roslynでコンパイルしたアセンブリを固定した.NETランタイムで実行 |
| Java 25 | Eclipse Temurin 25、ac-library-java | `javac --release 25`でコンパイルし、既存のclass収集とJAR実行を利用 |
| Nim | Nim 2.2系の安定版、C++バックエンド、指定された全14依存 | 固定したGCCでネイティブ実行ファイルを生成 |
| Go | Go公式gcコンパイラの保守中の安定系列、指定された全6モジュール | vendor済み依存でビルドしたネイティブ実行ファイルを実行 |

.NET 10は[Microsoftのサポート方針](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)にあるLTS系列を選ぶ。
Native AOTはコンパイル負荷とライブラリ互換性の検証を増やすため初期対象に含めない。
NuGetでビルド時に依存を解決し、コンパイル時には固定した参照アセンブリをRoslynへ渡す。
提出ごとのrestoreとMSBuildプロジェクト評価は不要にする。
成果物は提出アセンブリ1個とし、runtimeconfig、依存DLL、必要なdeps設定は運用側の固定ファイルから実行boxへ配置する。
MathNet.Numericsはmanaged providerを初期構成とする。

Javaは[Temurinのサポート方針](https://adoptium.net/support/)に従う25 LTS系列を採用し、25.0.4.1+1 LTSの配布物とチェックサムを固定する。
プレビュー機能は有効にしない。
Java 25には既存採用版のac-library-java 2.0.0を互換性検証の出発点とする。
今回要求されたライブラリ構成はac-library-javaだけとし、BifurcanはJava 24環境に残す。
`java24`を`java25`へ読み替えず、Java 24の受付は保留のまま、Java 25を別IDで公開する。

Nimは`nim cpp`を使い、C++ヘッダーを参照できる構成にする。
指定されたNim-ACLは`zer0-star/Nim-ACL`の0.1.0を対象とし、同名の別プロジェクトへ置き換えない。
要求の版一覧は[AtCoderのNim構築定義](https://img.atcoder.jp/file/language-update/2025-10/072-2-2-0_nim.toml)と対応するが、そこでの動作実績は本サーバの資源制限下での動作保証とはしない。
Nim 2.2.10を採用し、neo 0.3.5が使用する`shallowCopy`に合わせてメモリ管理を`refc`に固定する。
Nim-GMP 0.2.7とbignum 1.0.6には、Nimのmajor versionだけでARC/ORC用destructorの型を選ぶ箇所がある。
この条件にメモリ管理方式の確認を加え、refcでは既存の`var`引数の分岐を使う。
修正は各1行の`judge/runtime/deps/nim/nim-gmp-refc.patch`と`judge/runtime/deps/nim/bignum-refc.patch`として保持し、指定版の取得元・SHA-256とパッチ原文を配布物へ記録する。
要求にあるcommit固定の依存を、最新版や「安定版」という名前の別revisionへ変更しない。

既存C++の再ビルドを避けるため、追加配布物は検証済みのベースアーカイブをSHA-256で確認してから拡張する。
`judge/runtime/runtime-extension.Dockerfile`はそのベースを展開し、追加分だけを構築する。
既存GCC、Clang、ACL、Boostはそのバイナリとファイルを引き継ぎ、C++の共有includeには`testlib.h`だけを追加する。

Goは運用側の`go.mod`、`go.sum`、vendorツリーを提供し、`go build -mod=vendor`でコンパイルする。
`GOTOOLCHAIN=local`と`GOPROXY=off`を指定し、外部からのtoolchainやモジュールの取得を防ぐ。
初期構成は`CGO_ENABLED=0`とし、指定6モジュールのCPU向け利用を検証する。
Go 1.27は`go.mod`の読み取りとビルドキャッシュの整理で`flock`を必要とする。
固定したGoコンパイル処理に限り、isolate 2.7の`--syscalls=65531`でファイルロック制限を外す。
Goのコンパイルでは提出コードや`go generate`を実行せず、モジュールとキャッシュの書き込み先をbox内に限定する。
ネットワークや他のsyscall制限は引き続き適用し、提出・checker・interactorの実行には既定の全制限を適用する。
実行時の`flock`が`ENOSYS`になることをsmokeに含める。
また、Roslynは多数の参照アセンブリを開くため、C#のコンパイル工程だけは同時オープンファイル数を256とする。
実行時の上限は64とする。
未指定版は互換性のあるタグを優先し、タグのないモジュールはcommitに対応するpseudo-versionへ固定する。
この方式は[Go Modules Reference](https://go.dev/ref/mod)に基づく。

### Nim専用の依存を分離する

Nim用のACL 1.5.1とBoost 1.88.0は`/opt/judge-runtimes/nim-deps`へ配置し、C++用の共有includeディレクトリへ上書きしない。
Eigen、GMP、MPFR、FFTWと必要なBLAS/LAPACKもNim用の構成として記録する。
ヘッダー探索順と動的ライブラリ探索先を固定し、ホストOSの同名ライブラリへ意図せず解決されないことを確認する。
要求にあるネイティブライブラリの版は、aptのパッケージ名だけで満たした扱いにしない。

Arraymancerなどの必須の推移的依存も取得元とrevisionを固定する。
CPU向け機能を対象にし、GPUデバイスやCUDA実行環境は提供しない。
依存解決上必要なGPU用ラッパーが含まれても、GPU機能を利用可能と表示しない。
数値計算ライブラリの内部スレッド数は既存方針に合わせて制限する。

### 三つの採点用途で公開条件を揃える

新言語も通常提出、checker、interactorの共通一覧に追加する。
公開判定は「コンパイルできた」だけで完了させず、全要求ライブラリの代表操作と三つの用途を対象とする。
JavaやC#だけ対話用ジャッジから黙って除外しない。

初期の検証上限は、コンパイル1 GiB、CPU 30秒、経過40秒、提出と逐次checkerは512 MiB、interactorは256 MiBとする。
Javaと.NETはGCヒープ以外にもメモリを消費するため、用途別のヒープ設定を運用側で決め、実際のcgroup上限から余裕を取る。
GoのGCメモリ目標も強制上限とは扱わず、最終的な制限はcgroupで適用する。
VM内のメモリ例外とcgroup OOMは既存の判定規則で区別する。

全ライブラリの代表操作、JIT起動、子孫プロセス、スレッド、tmpfsを含めて2 GB実機で計測する。
制限内に収まらない言語は公開を保留し、具体的な測定結果をもとに制限または基盤の変更を別途判断する。
メモリ上限やコンパイル時間を実装中に暗黙に引き上げない。

### 適用中のメンテナンス表示と受付停止を連動させる

適用作業中はサイト上部に、次のバナーを表示する。
ログイン状態にかかわらず、通常ページとヘッダーを省略する編集ページの両方に表示する。

> ジャッジ機能のメンテナンスを行っています。この期間中は提出等ができません。

表示は既存の受付停止操作と連動させ、フロントエンドだけの独立した表示スイッチは設けない。
`judge/admission.py --pause`が設定する`JUDGE_ENABLED_RUNTIMES=none`を計画メンテナンス状態とし、既存の`GET /runtimes`へ`maintenance`フィールドを追加する。
言語一覧が空であることだけからメンテナンスと推測しない。
設定不備やAPI取得失敗は、計画メンテナンスとは区別して利用不可と案内する。

メンテナンス中は通常提出、コンテスト提出、試験実行、テスト入力と期待出力の生成、入力検証など、新たなジャッジ処理を作る操作を停止する。
画面で操作を無効にするだけでなく、APIもジョブを作る前に`503 judge_maintenance`で拒否する。
問題と結果の閲覧、ジャッジを起動しない編集と下書き保存は継続できるようにする。
受付済みのジョブは旧環境で処理し、利用者による再提出は求めない。

バナーと操作可否は同じ状態を参照し、初期表示、ページ遷移、開いたままの画面でも更新する。
操作直前に状態が変わった場合はAPIのメンテナンス応答を画面へ反映し、入力済みのソースを保持する。
公開停止の確認後にキューを排出して適用を始め、実機検証と復旧確認が成功して受付を再開した後にバナーを消す。
失敗時は停止状態と表示を維持し、切り戻し後も復旧を確認してから解除する。

## 代替案

| 案 | 採用しない理由 |
| --- | --- |
| 提出時にNuGet、Nimble、Goから依存を取得する | ネットワーク隔離と依存の固定が崩れ、採点ごとの取得失敗も発生する |
| 言語ごとにworkerとキューを増やす | 現在の同時1提出という運用に対して構成と配布の管理が増える |
| AtCoderのインストールスクリプトをそのまま使う | 未固定の依存解決、ホスト全体への配置、異なるメモリ前提を持ち込む |
| Java 24の実体だけ25へ置換する | 過去に固定した実行条件とランタイム名の意味が変わる |
| Nim用にC++のACLとBoostをダウングレードする | 既存C++提出への不要な変更となる |
| testlibを検出して引数と判定を自動変更する | 既存問題の判定契約をソース内容によって変えてしまう |

## 実装と公開の計画

1. [依存一覧と検証計画](../judge/runtime-extension-plan.md)に沿って、未指定版、推移的依存、配布元、SHA-256を固定する。
2. 既存ビルドを拡張し、C++のtestlibとJava 25、Go、C#、Nimの順にオフラインのコンパイルと実行を確認する。
3. ランタイム定義、C#の成果物配置、用途別VM設定、APIの許可一覧、画面の表示、配布とfingerprintの対象を更新する。
4. testlibのprotocol保存、引数とファイル配置、終了コード解釈を実装し、既存形式との混在を検証する。
5. 各ライブラリ、異常系、checker、interactorのfixtureを追加し、2 GB実機で新旧言語のsmokeを実施する。
6. 受付停止と連動するバナーを先に利用可能にし、停止と表示を確認してから旧キューの排出、worker停止、配布、fingerprint更新を行う。同じdigestの検証結果に合格した言語を公開する。
7. `GET /runtimes`、通常提出、checker、対話問題をAPIから確認し、公開設定とCI変数、利用ガイドを同期する。

旧digestの未処理提出を新環境へ付け替えない。
切り戻し時も受付を止め、新digestの処理中と遅延中のジョブを整理してから、保存した旧配布物と対応するホスト状態、公開設定を復元する。
現時点では任意の旧digestへルーティングして再採点する仕組みはない。
具体的な操作は[既存の公開手順](../judge/runtime-rollout.md)を拡張する。

## 影響と実装時の確定事項

指定ライブラリの追加により、配布容量、展開時のディスク使用量、ビルド時間と更新対象が増える。
容量とコンパイル性能はビルド後に記録し、依存の欠落を容量削減の手段にしない。
配布物には各依存のライセンス情報も保存する。

採用パッチ版、未指定のライブラリ版、Nimの推移的依存、用途別VM設定は互換性試験で確定した。
採用値と互換パッチは[実装計画](../judge/runtime-extension-plan.md)、配布物のハッシュと実機検証は[適用記録](../judge/runtime-rollout.md)に記録する。
testlibは上記のcheckerと自己完結するinteractorに対応する方針を、2026-09-14のユーザーの追加要望に基づいて決定した。
本ADRの承認と実機smokeの成功は別の条件であり、この文書の追加だけでは本番の受付対象は変わらない。

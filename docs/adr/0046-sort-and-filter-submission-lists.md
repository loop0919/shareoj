# ADR 0046: 提出一覧に、並び替えと絞り込みのパネルを足す

- 状態：Accepted（Chromium以外のブラウザーと、本番の提出の件数でのマイグレーションの所要時間と、公開後の本番での応答時間は未確認）
- 決定日：2026-11-28
- 範囲：問題ページの「すべての提出」「自分の提出」、コンテストの「提出一覧」「自分の提出」（コンテストの問題の一覧を含む）、その一覧のAPI、処理系の一覧（`GET /runtimes`）、`submissions`の索引と関数。設計は[提出一覧の並び替えと絞り込みの設計](../superpowers/specs/2026-11-28-submission-list-sort-filter-design.md)にある

## 背景

提出の一覧は提出日時が新しい順に並ぶだけで、絞り込めるのはコンテストの「問題」だけだった。
提出が多い問題やコンテストでは、目当ての提出を探すのに何ページも送ることになる。
Issue #36は、いちばん短いコードやいちばん速いコードを見る、特定の人の提出だけを見る、特定の結果や言語の提出だけを見る、という使い方を求めている。

画面の形は、[ADR 0045](0045-sort-and-filter-problem-list.md)で作った「絞り込み・並び替え」のパネルと札に合わせる。
この決定は、そのパネルを提出一覧に広げ、並び替えと絞り込みを速く返すための索引を足す。

## 決定

### 2つの画面に、同じパネルを出す

問題ページの「すべての提出」「自分の提出」と、コンテストの「提出一覧」「自分の提出」に、「絞り込み・並び替え」のパネルを出す。
コンテストの問題の一覧のAPIも、同じ条件を受ける。
閉じているときの札、ボタンの数、「条件をすべて外す」、条件に合う提出がないときの文言は、問題一覧と同じにする。
条件を変えたら1ページ目に戻り、パネルは開いたままにする。

欄は、並び順、結果、言語、提出者、問題の5つである。
問題の欄はコンテストだけにある。
自分の提出とチームの提出には、提出者の欄を出さず、`user`も送らない。

コンテストの「問題」の選択欄は、パネルの中へ移した。
URLの値は今までどおり問題の記号（`A`など）のままで、古いリンクは開ける。

コンテストの「オンサイトのみ表示」のスイッチは、順位表と共用の切り替えなので、パネルの外に残した。
札にせず、ボタンの数にも数えず、「条件をすべて外す」でも変えない。

パネルの骨組み（`ConditionsPanel.vue`と、条件の変更を積む`useConditionChanges`）は、問題一覧と共用する。
提出の欄は`SubmissionConditions.vue`、提出者の入力は`UserFilter.vue`、URLと条件の読み書きは`useSubmissionConditions`が持つ。

### 条件はURLのクエリに入れる

| クエリ | 値 | 初期 |
| --- | --- | --- |
| `sort` | `newest` `oldest` `shortest` `fastest` | `newest` |
| `verdict` | `AC` `WA` `TLE` `MLE` `OLE` `RE` `CE` `JE` | なし |
| `language` | 言語のキー（`cpp` `python`など） | なし |
| `runtime` | 処理系のID（`cpp23-gcc`など。接尾辞は付けない） | なし |
| `user` | ユーザーID | なし |
| `problem` | 今までどおり（Webは問題の記号、APIはUUID） | なし |

初期値はURLに出さない。
APIは、知らない値や形の合わない値に`400 invalid_request`を返す。`language`と`runtime`を同時に指定したときも同じである。
Webは、URLの知らない値を初期値として読み、`language`と`runtime`が両方あれば`runtime`を読む。
条件を変えたときは、履歴を増やさずに、今の項目を置き換える。戻るボタンは一覧の前のページへ戻る。

問題一覧と違い、条件は覚えない。Cookieも足さない。
提出一覧は、共有されたリンクや自分で絞った一覧を見るために使い、次に開いたときまで条件が残る理由が薄い。
覚えると、一覧が減っていることに気づかないままになるおそれもある。

### 言語は、まとめて選べる。まとめ方は、APIの一覧だけに持つ

利用者は、GCCとClang、CPythonとPyPyのように、同じ言語の処理系を「C++」「Python」として絞り込めることを望んだ。
`language`は言語全体を、`runtime`は1つの処理系を指す。

- どの処理系がどの言語に入るかは、APIの処理系の一覧（`api/internal/submissions/runtimes.go`）だけに書く。
- `GET /runtimes`が`languages`を返し、Webはそれを読んで言語の欄を組む。Webに対応表は持たない。
- 処理系が2つ以上ある言語（C、C++、Python、Java、JavaScript、TypeScript、Ruby）は、先頭に「（言語名）（すべて）」を置き、その下に処理系を並べる。CとC++、JavaScriptとTypeScriptは別の言語である。
- `language`は、今は提出に選べない処理系の提出も含む。処理系が増えても、リンクの意味は変わらず、新しい処理系の提出も含む。
- 保存されている処理系のIDには、実行環境の接尾辞（`-isolate`、`-local`）が付く。接尾辞の有無にかかわらず、同じ処理系として絞り込む。

### 結果と実行時間と並びの決まり

- `verdict`は、採点が終わった提出（`status='DONE'`）の`result.verdict`で絞る。これは一覧の「結果」の列と同じ値である。採点中の提出は、`verdict`を指定した一覧には出ない。部分点の問題でも、得点ではなく`result.verdict`で絞る。
- 実行時間は、ケースごとのCPU時間（`result.cases[].cpuTimeMs`）の最大で、一覧の「実行時間」の列に出す値と同じである。SQL関数`submission_cpu_time_ms`（マイグレーション051）が取り出す。並び替えと列の値がずれないよう、取り出しを1か所にした。
- コード長は、`source`のバイト数である。
- 並びが同じ値の提出は、提出日時が新しい順、次にIDの降順で並べる（`oldest`だけは古い順、IDの昇順）。ページを送っても、同じ提出が2回出たり抜けたりしない。
- 実行時間のない提出（採点中、CEなど）は、実行時間が短い順では最後に置く。
- 誰に何が見えるかの決まり（凍結中の提出、下書きの実行、開始前のスタッフ限定の提出）は変えない。条件は、見える提出の中だけで効く。コンテストの`total`は、条件を当てたあとの件数である。

### リジャッジとの関係

リジャッジした提出は、結果が出るまで採点中になる。
結果で絞った一覧からは、採点中の間は外れ、結果が出たあと、条件に合えば次の更新で戻る。
絞り込みや並び替えをしていても、リジャッジの選択と実行は使える。
条件つきの一覧では採点中の行が見えなくなり、3秒ごとの更新が止まる。そこで、この一覧からリジャッジを頼んだあとは、頼んだ提出の結果が出そろうまで、長くても60秒、3秒ごとに更新を続ける。

## 代替案

- **処理系ごとの選択肢だけにする形**：利用者が言語のまとめを求めたので選ばなかった。
- **列見出しを押して並び替える形**：結果や言語や提出者のような絞り込みを置く場所がなく、問題一覧のパネルとも形がそろわない。
- **メモリ、コード長が長い順、実行時間が長い順で並べる形**：使い方に挙がらなかったので入れなかった。
- **条件を覚える形**：上に書いたとおり、提出一覧では要らない。
- **表の形を変える形（結果や実行時間を列に持つ）**：索引と関数で、基準の時間に収まったので要らなかった。提出と判定の結果を書くすべての経路で列を保たなければならない負担も避けられた。

## 速さ

`TestSubmissionListSpeedPostgres`（`OPENOJ_LIST_SPEED=1`のときだけ動く）で、本番に近い形のデータを測った。
ADR 0045で、小さな行の計測が本当の遅さを見逃したので、提出の`job`と`result`は数KB（平均でそれぞれ約4KBと約1.7KB。TOASTに置かれる）にした。
基準は、1ページと件数の問い合わせの合計で200ミリ秒である。

データは、1つの問題に提出5,000件、1つのコンテストに提出20,000件（その問題の開催後の通常の提出2,000件を含む）、小さなコンテスト40個、問題291問、コンテスト41個、利用者200人である。
手元のPostgreSQL 17で測った。

### 索引を足す前

- 問題の一覧（条件なし、新しい順）は9ミリ秒だった。
- コンテストの一覧は、条件がなくても約800ミリ秒かかった。ページの問い合わせも件数の問い合わせも、`submissions`の全行を順に読み、行ごとに`job`を読んでいたためである。かかる時間は、コンテストの提出ではなく、表全体の大きさで決まる。
- 並び替えと絞り込みを加えると、いちばん遅いコンテストの実行時間の順で約1.2秒になった。

### 足したもの

マイグレーション051は関数`submission_cpu_time_ms`を、052は索引4つと拡張統計2つを足し、表を解析する。

| 索引 | 持つもの | 答える一覧 |
| --- | --- | --- |
| `submissions_problem_shortest` | `(problem_id, octet_length(source), created_at DESC, id DESC)` | 問題とコンテストの問題の一覧、コード長の順 |
| `submissions_problem_fastest` | `(problem_id, submission_cpu_time_ms(result), created_at DESC, id DESC)` | 同じ一覧、実行時間の順 |
| `submissions_contest_shortest` | `(contest_id, octet_length(source), created_at DESC, id DESC)`。コンテストの提出で、数える条件を満たすものだけ | コンテストの一覧、コード長の順と、件数 |
| `submissions_contest_fastest` | `(contest_id, submission_cpu_time_ms(result), created_at DESC, id DESC)`。同じ条件 | コンテストの一覧、実行時間の順と、件数 |

- 新しい順と古い順は、既存の`submissions_problem_order`などで答える。
- 問題側の2つには条件を付けない。条件を付けると、準備した文の汎用の計画で、条件なしの新しい順が別の索引へ引かれ、全行を読んで並べ替える形になったためである。
- コンテストの一覧は、コンテストの提出と、そのコンテストの問題のコンテスト外の提出（スタッフにだけ見える）の2つに分け、`UNION ALL`で読む。件数もコンテストの索引から数える。書き直したあとの文が、書き直す前の文と同じ結果を返すことは、基準の文を持つテストで突き合わせる。
- 拡張統計は、3つのフラグ（`easyTest`、`generate`、`validate`）と`result->>'verdict'`について足す。これがないと、絞り込んだ一覧で、索引を順に読む計画が選ばれない。
- 統計は、`ANALYZE`までは使われない。そこで052の中で、統計を足した直後、索引を作る前に`ANALYZE submissions`を行う。後ろに置くと、索引の`ShareLock`を持ったまま解析するので、書き込みの待ちが約3.2秒増える。前に置けば、解析の間は書き込みを待たせない。

### 呼ぶたびに計画させる

pgxは、文を接続ごとに1度準備して使い回す。PostgreSQLの既定の`plan_cache_mode=auto`では、5回呼んだあとに、平均の大きさのコンテストに合わせた汎用の計画へ切り替わることがある。
汎用の計画では、コンテストの絞り込みと、見える条件の`OR`のため、行数が1行と見積もられる。1行なら、索引を順に読むのと、どの索引でも読んで並べ替えるのが同じ安さに見え、いちばん小さい索引が選ばれる。
大きなコンテストの新しい順と古い順の一覧は、全行を並べ替える計画になり、1つの接続で繰り返し呼ぶと240〜277ミリ秒になった。

そこで3つの一覧の問い合わせは、`plannedPerCall`で`pgx.QueryExecModeCacheDescribe`を使い、名前のない文として送り、呼ぶたびに値に合わせて計画させる。
計画の費用は、コンテストの一覧1回で約10ミリ秒である。
`TestSubmissionListsArePlannedPerCallPostgres`が、一覧が接続に準備した文を残さないことを確かめる。

単純プロトコルは選ばなかった。値をクライアントで埋め込み、pgx自身が避けるよう勧めており、過去にSQL注入の脆弱性もあったためである。

### 結果（ミリ秒、3回のうちの最短）

| 一覧 | 前（条件なし、新しい順） | 後（いちばん遅い組み合わせ） |
| --- | ---: | ---: |
| 問題の一覧 | 9 | 11 |
| コンテストの一覧 | 約800 | 115 |
| コンテストの一覧（スタッフ） | 約840 | 206 |
| コンテストの問題の一覧 | 9 | 13 |

どの一覧も、4つの並び順と5つの絞り込みの組み合わせすべてで、基準の200ミリ秒に収まる。
スタッフが読む一覧は、開催後の通常の提出も読むので、基準を400ミリ秒にしてある。

書き込みの費用は、提出1件の追加と結果の更新で、それぞれ約0.1ミリ秒増える。
索引を作る時間は、この試験データで合計約1.6秒で、その間は`submissions`への書き込みが待たされる。

## 影響

- 索引の定義と、一覧のSQL（`internal/submissions/conditions.go`の並びの式と、`contestPublic`と`contestOwn`の最初の3つの条件）は、一緒に変える。ずれると、結果は正しいまま、索引が使われず遅くなる。`TestSubmissionListsUseTheirIndexesPostgres`が、名前を挙げて、索引を使うことを確かめる。
- `submission_cpu_time_ms`を置き換えるときは、2つの`_fastest`索引を作り直す（`REINDEX`）。索引は、古い関数が取り出した値を持ったままになるためである。
- 新しい一覧の問い合わせは、`plannedPerCall`を通す。通さないと、汎用の計画に切り替わる条件が戻る。
- データベースの`plan_cache_mode`を`force_generic_plan`にしてはならない。`plannedPerCall`は準備した文を避けるだけで、この設定がある場合は効かない。この設定で測ると、大きなコンテストの新しい順と古い順の一覧は249〜269ミリ秒になる。
- マイグレーション051と052の番号を使う。052は、索引を作る間、`submissions`への書き込みを待たせる。試験データでは約1.6秒だが、本番の提出の量では長くなる。コンテストの開催中を避けて配布する。
- コンテストの一覧の件数は、コンテストの提出の数に比例して増える。件数の問い合わせは、コンテストの索引を全部読む。
- コンテストの`total`は条件を当てたあとの数なので、条件を変えるとページ数が変わる。
